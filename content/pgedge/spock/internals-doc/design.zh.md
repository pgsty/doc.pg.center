说明 Spock 输出插件各项设计的缘由。

## 已有 wal2json 等插件，为什么还需要 spock_output？ {#why-does-spock_output-exist-when-theres-wal2json-etc}

`spock_output` 除了把逻辑解码得到的变更消息转换为传输格式并发给客户端，还承担其他工作。

它负责格式协商，并通过可插拔的钩子在发送端过滤数据，同时管理相应的插件。协议本身也支持二进制数据值传输，这类操作用 JSON 很难高效实现。

## 自定义二进制协议 {#custom-binary-protocol}

为什么在 walsender 的 COPY BOTH 协议内使用自定义二进制协议？

主要考虑速度和数据量。生成 JSON 需要大量内存分配，解码也有开销。原始二进制数据必须先编码才能放入 JSON，对某些数据类型代价尤其高。选用直观、易解码的 JSON 表示，也会妨碍协议和解码器后续的改进，例如缓存行元数据。

协议实现的封装较好，将来有望按客户端请求输出 JSON。已有 wal2json 等工具提供这种能力，因此目前优先级较低。

## 列元数据 {#column-metadata}

在首次发送引用某个关系的行之前，输出插件会发送该关系的列元数据，至少包括列名。

上下游表的列编号（attnum）未必一一对应。即使列名和排列次序相同，删除列或改变列类型，都可能在一侧留下已删除列的编号。两张表对用户看起来一样，内部列号却已不同。按列号复制就可能把数据写入错误的列。

可以要求下游严格通过 DDL 复制维护表定义，以免出现这种问题，但有以下限制。

* 我们希望 DDL 复制保持可选。
* 多个上游向同一张表复制时，这种做法行不通。
* 如果原表含已删除的列，首次建表就可能无法还原列号，除非借用 `pg_dump` 的 `--binary-upgrade` 功能来生成带已删除列的表。我们不打算采用这种方式。

所以，即使会多用一些带宽，仍须发送元数据。

协议还为类型元数据预留了位置。这样，即使客户端没有表定义（如队列引擎），也有望自行解码数据。逻辑复制的应用端也能据此校验类型。

上游要求客户端缓存元数据，再次收到同一关系的数据时复用。缓存大小控制、LRU 淘汰和清除通知留待后续实现。目前客户端必须一直保留所有条目。

## 控制关系元数据缓存的大小 {#relation-metadata-cache-size-controls}

计划允许下游控制关系元数据缓存大小。下游将通过参数声明支持缓存，并给出期望的缓存上限。

启动参数发出后，下游没有与上游协商缓存的通道，难以在自行清除条目时通知上游。因此，下游缓存必须遵从上游缓存的决定。下游在启动时告知上游如何管理缓存，此后按上游的通知行事。

为了保证上游发送行时下游一定有对应的元数据，下游每次收到关系元数据都必须缓存。在收到上游针对该关系的清除消息前，不能删除条目。若同一关系来了新的元数据，*必须*用它替换旧条目。

收到上游的清除消息后，下游无须立即清除条目或将其标为失效。该消息只是通知下游：上游不再要求它保留该条目，以后再用到时会上送新的元数据。

## 插件与 SQL 扩展 {#not-an-extension}

spock_output 有意不提供扩展安装脚本。使用它的应用可以自行定义所需的 SQL 目录，并通过钩子访问这些目录。

应用的目录数据因此能集中存放，无须分别管理 spock_output 扩展目录和自己的目录。

转储和恢复也由应用完全控制，spock_output 无须为此规定策略或提供工具。

spock_output 旨在作为可供其他方案复用的组件，用户无须直接管理它。

## 钩子 {#hooks}

输出插件将许多功能交给可插拔的钩子，包括按复制来源过滤。

spock_output 尽量不依赖复制集群的拓扑，这类知识由使用插件的应用掌握。


## 以 SQL 函数作为钩子入口 {#hook-entry-point-as-a-sql-function}

钩子入口是一个 SQL 函数。它在传入的 `internal` 结构中填入各个钩子的函数指针。

钩子由远端通过网络指定。出于安全考虑，远端不能任意指定要动态加载的函数及其参数。若允许这样做，至少所有使用钩子的复制都必须仅对超级用户开放。

每个解码会话只调用一次 SQL 入口，此后均直接通过 C 函数指针调用。

## 启动应答消息 {#the-startup-reply-message}

`spock` 作为逻辑解码插件，工作在前后端协议的 COPY BOTH 子协议内，这限制了可用的协议设计。插件无法直接访问网络套接字，只能在 walsender 和逻辑解码框架调度时收发消息。

客户端只有在 `START_REPLICATION` 的参数中才能直接向逻辑解码插件提供数据，在此之前插件也不能给客户端发送任何内容。

客户端和服务器因此不能来回多轮协商。双方只能交换一次启动参数和复制启动消息。若客户端无法接受服务器给出的选项，只能断开连接，换一组参数重试。

启动消息会报告插件的能力，以及客户端请求的哪些选项已生效。客户端据此决定继续使用连接，还是换一组选项重连。由此可以跨连接逐次协商。

## 客户端和服务器必须忽略无法识别的参数 {#unrecognised-parameters-must-be-ignored-by-client-and-server}

为同时保持向前和向后兼容，输出插件必须忽略不认识的客户端参数，客户端也必须忽略服务器启动应答中不认识的参数。

这样，旧客户端可以连接新服务器，新客户端也可以连接旧服务器。

因此，除非客户端通过启动参数明确表示支持，服务器绝不能擅自启用新的消息类型、行格式等功能。每项能力都须经过协商。

同理，新客户端可以请求旧服务器启用某项能力，但必须检查启动应答，确认服务器确已启用。若服务器未按请求处理，客户端可以断开并向用户报错。当应用依赖具有安全作用的钩子时，这项检查尤其重要。

## 流式传输事务 {#support-for-transaction-streaming}

在这份设计所述的实现中，逻辑解码要等事务提交后才能*开始*向客户端发送它。长事务可能因此耗时两倍：主库提交之前，副本无法开始应用。

大事务也会推迟较小事务的应用。逻辑解码按严格的提交顺序重排和重放事务。大事务之后提交的小事务，必须等大事务传输完毕才能重放，而大事务运行期间又无法提早传输。

大事务会在重排序缓冲区累积，直到传给副本后才能释放。上游除了保留一份 WAL，还要有足够空间暂存整个事务。要等确认重放位置越过事务提交点，保留的 WAL 才可清除。暂存文件可以从 WAL 重新生成，本身不提供额外的数据保护。

等到提交也有明显好处。已回滚的事务和子事务完全无须发送。下游不必在应用时处理事务重排、事务依赖及相互冲突，逻辑大为简化。从重放开始就能知道提交时间戳，也有利于多主环境下的冲突处理。不过，有些场景仍需要在提交前传输变更。

因此，希望上游一读到 WAL 中的事务变更就能开始传输，让下游立即应用，或先在下游暂存到事务提交。这需要逻辑解码框架本身配合，单靠 spock_output 无法实现。插件已为将来的支持预留空间。

* 多数消息类型含有标志位，可按需增加字段。例如，设置 HAS_XID 标志并附加事务 ID，便能区分交错传输的并发事务。不需要时无须占用该字段的空间。

* 若客户端未声明相应能力，上游不能发送新的消息类型。因此，只有客户端通过额外的启动参数声明能处理交错事务，才会在逻辑解码中启用该功能。

为了一致性，下游仍须按原顺序提交。流式传输旨在缩短大事务前最后一笔事务与其后第一笔事务之间的提交间隔，让下游观察到的小事务停顿时间尽量短。

事务流式传输也使下游并行应用成为可能。即使串行应用，也能从流式传输获益。并行应用还有额外的复杂性，超出了输出插件设计的范围。
