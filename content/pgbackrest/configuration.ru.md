## Введение {#introduction}

pgBackRest может работать исключительно с параметрами командной строки, однако для сложных установок или большого числа параметров практичнее использовать файл конфигурации. По умолчанию он расположен в `/etc/pgbackrest/pgbackrest.conf`. Если файла там нет, проверяется прежнее расположение по умолчанию: `/etc/pgbackrest.conf`.

Используются следующие типы параметров:

**Строка**: текстовая строка, обычно идентификатор, пароль и т. п.

Пример командной строки: `--stanza=demo`<br/>Пример файла конфигурации: `repo1-cipher-pass=zWaf6XtpjIVZC5444yXB...`

**Путь**: однозначно определяет расположение в структуре каталогов. Путь должен начинаться с /; двойной // не допускается, завершающий / не ожидается.

Пример командной строки: `--repo1-path=/var/lib/pgbackrest`<br/>Пример файла конфигурации: `repo1-path=/var/lib/pgbackrest`

**Логическое значение**: включает или отключает параметр. Допустимы только значения аргумента y/n.

Примеры командной строки: `--start-fast`, `--no-start-fast`, `--start-fast=y`, `--start-fast=n`<br/>Примеры файла конфигурации: `start-fast=y`, `start-fast=n`

**Целое число**: используется для портов, количества хранимых копий или повторных попыток, допустимого числа параллельных процессов и т. п.

Пример командной строки: `--compress-level=3`<br/>Пример файла конфигурации: `pg1-port=5432`

**Размер**: используется для размеров буферов, объёма дискового пространства и т. п. Размер можно указать в байтах (по умолчанию) либо в KiB, MiB, GiB, TiB или PiB, где множитель равен степени 1024. Например, вместо 5368709120 можно использовать значение 5GiB (или 5GB, 5g) без учёта регистра. Дробные значения, такие как 2.5GiB, не допускаются; вместо них следует использовать 2560MiB.

Пример командной строки: `--archive-get-queue-max=1GiB`<br/>Пример файла конфигурации: `buffer-size=2MiB`

**Время**: время в секундах.

Пример командной строки: `--io-timeout=90`<br/>Пример файла конфигурации: `db-timeout=600`

**Список**: параметр можно указать несколько раз.

Пример командной строки: `--db-exclude=db1 --db-exclude=db2 --db-exclude=db5`

Пример файла конфигурации, каждое значение на отдельной строке:

```ini
db-exclude=db1
db-exclude=db2
db-exclude=db5
```

**Ключ/значение**: параметр можно указать несколько раз в форме `key=value`.

Пример командной строки: `--tablespace-map=ts_01=/db/ts_01 --tablespace-map=ts_02=/db/ts_02`

Пример файла конфигурации, каждое значение на отдельной строке:

```ini
tablespace-map=ts_01=/db/ts_01
tablespace-map=ts_02=/db/ts_02
```

## Параметры архивирования {#archive-options}

Секция `archive` определяет параметры команд `archive-push` и `archive-get`.

### Параметр асинхронного архивирования (`--archive-async`) {#asynchronous-archiving-option---archive-async}

Асинхронная отправка и получение сегментов WAL.

Включает асинхронный режим работы команд `archive-push` и `archive-get`.

Асинхронный режим эффективнее, поскольку позволяет повторно использовать соединения и выполнять операции параллельно. Дополнительные сведения приведены в описании параметров `spool-path`, `archive-get-queue-max` и `archive-push-queue-max`.

```text
default: n
example: archive-async=y
```

### Параметр максимального размера очереди получения из архива (`--archive-get-queue-max`) {#maximum-archive-get-queue-size-option---archive-get-queue-max}

Максимальный размер очереди archive-get в pgBackRest.

Задаёт максимальный размер очереди `archive-get` при включённом `archive-async`. Очередь хранится в `spool-path` и ускоряет передачу WAL в PostgreSQL.

```text
default: 128MiB
allowed: [0B, 4PiB]
example: archive-get-queue-max=1GiB
```

### Параметр повторного запроса отсутствующего сегмента WAL (`--archive-missing-retry`) {#retry-missing-wal-segment-option---archive-missing-retry}

Повторный запрос отсутствующего сегмента WAL

Повторно запрашивает сегмент WAL, об отсутствии которого ранее сообщила команда `archive-get` в асинхронном режиме. Это предотвращает использование уведомлений в каталоге очереди, оставшихся от предыдущего восстановления, которые могли бы привести к сбою восстановления, если согласованность ещё не достигнута.

Отключение этого параметра позволяет PostgreSQL надёжнее определять достижение конца WAL в архиве и переключаться на потоковую передачу с первичного сервера. Если повторные запросы включены, непрерывное поступление WAL в архив заставляет PostgreSQL продолжать получать WAL из архива вместо переключения на потоковую передачу.

При отключении этого параметра важно убедиться, что каталог очереди для stanza пуст. Команда `restore` очищает его автоматически, если каталог очереди настроен на момент восстановления. В противном случае пользователь должен самостоятельно обеспечить его очистку.

```text
default: y
example: archive-missing-retry=n
```

### Параметр размера пакета отправки в архив (`--archive-push-batch-size`) {#archive-push-batch-size-option---archive-push-batch-size}

Максимальный объём WAL, отправляемый за один асинхронный запуск.

В асинхронном режиме процесс `archive-push` отправляет все готовые сегменты WAL за один запуск. Поскольку `archive-push-queue-max` проверяется только в начале каждого запуска, при обработке очень большого числа сегментов очередь может значительно превысить предел до следующей проверки.

Этот параметр ограничивает объём WAL, обрабатываемый за один запуск, после чего процесс завершается и вновь запускается следующим вызовом `archive-push`, который повторно проверяет очередь. Меньшие значения позволяют проверять очередь чаще, но требуют более частого запуска асинхронного процесса. Значение округляется вниз до целого числа сегментов WAL, однако всегда обрабатывается хотя бы один сегмент.

```text
default: 16GiB
allowed: [1MiB, 4PiB]
example: archive-push-batch-size=1GiB
```

### Параметр максимального размера очереди отправки в архив (`--archive-push-queue-max`) {#maximum-archive-push-queue-size-option---archive-push-queue-max}

Максимальный размер очереди архивирования PostgreSQL.

При достижении предела произойдёт следующее:

- pgBackRest сообщит PostgreSQL об успешном архивировании WAL, а затем **УДАЛИТ ЕГО**.
- В журнал PostgreSQL будет выведено предупреждение.

В этом случае поток архивного журнала прервётся, и PITR за этой точкой станет невозможен. Чтобы вновь обеспечить полные возможности восстановления, потребуется новая резервная копия.

В асинхронном режиме удаляется вся очередь, чтобы отдельные сегменты WAL не успевали попадать в архив до повторного превышения предела очереди.

В асинхронном режиме этот предел проверяется только в начале каждого запуска `archive-push`, поэтому за один запуск очередь может превысить его. Уменьшите `archive-push-batch-size`, чтобы проверять очередь чаще.

Эта возможность предотвращает заполнение тома с журналом, при котором PostgreSQL полностью остановится. Лучше потерять резервную копию, чем допустить остановку PostgreSQL.

```text
allowed: [0B, 4PiB]
example: archive-push-queue-max=1TiB
```

Устаревшее имя: archive-queue-max

### Параметр тайм-аута архивирования (`--archive-timeout`) {#archive-timeout-option---archive-timeout}

Тайм-аут архивирования.

Задаёт максимальное время в секундах, в течение которого ожидается поступление каждого сегмента WAL в архивный репозиторий pgBackRest. Тайм-аут применяется к командам `check` и `backup`, когда они ожидают архивирования сегментов WAL, необходимых для согласованности резервной копии.

```text
default: 1m
allowed: [100ms, 1d]
example: archive-timeout=30
```

## Параметры резервного копирования {#backup-options}

Секция `backup` определяет параметры резервного копирования.

### Параметр аннотации резервной копии (`--annotation`) {#backup-annotation-option---annotation}

Добавление к резервной копии пользовательских пар «ключ — значение».

Пользователи могут добавлять к резервной копии информационные пары «ключ — значение». Этот параметр можно указывать несколько раз для добавления нескольких аннотаций.

Аннотации включаются в текстовый вывод команды `info`, если резервная копия указана через `--set`, и всегда присутствуют в выводе JSON.

```text
example: annotation=source="Sunday backup for website database"
```

### Параметр проверки архива (`--archive-check`) {#check-archive-option---archive-check}

Проверка наличия сегментов WAL в архиве перед завершением резервного копирования.

Проверяет, что все сегменты WAL, необходимые для согласованности резервной копии, присутствуют в архиве WAL. Рекомендуется оставить значение по умолчанию, если не используется другой способ архивирования.

Этот параметр должен быть включён, если включён `archive-copy`.

```text
default: y
example: archive-check=n
```

### Параметр копирования архива (`--archive-copy`) {#copy-archive-option---archive-copy}

Копирование в резервную копию сегментов WAL, необходимых для согласованности.

Этот параметр обеспечивает дополнительную предосторожность: он защищает от повреждения архива сегментов WAL, сохраняя сегменты, необходимые для согласованности, непосредственно в резервной копии. Сегменты WAL по-прежнему сохраняются и в архиве, поэтому параметр увеличивает расход места.

При использовании этого параметра желательно, чтобы команды `archive-push` и `backup` имели одинаковый `compress-type` (например, `lz4`). Иначе сегменты WAL потребуется повторно сжать с `compress-type`, используемым резервной копией, что может потребовать значительных ресурсов в зависимости от объёма WAL, созданного во время резервного копирования.

При восстановлении сегменты WAL будут находиться в `pg_xlog/pg_wal`, и PostgreSQL предпочтёт использовать их, а не вызывать `restore_command`.

Параметр `archive-check` должен быть включён, если включён `archive-copy`.

```text
default: n
example: archive-copy=y
```

### Параметр проверки режима архивирования (`--archive-mode-check`) {#check-archive-mode-option---archive-mode-check}

Проверка настройки PostgreSQL `archive_mode`.

Этот параметр включён по умолчанию и запрещает использовать в PostgreSQL `archive_mode=always`.

Сегменты WAL, отправляемые с резервного сервера, могут логически совпадать с сегментами WAL с первичного сервера, но иметь другие контрольные суммы. Во избежание конфликтов рекомендуется отключить архивирование из нескольких источников.

ОСТОРОЖНО:

Если этот параметр отключён, крайне важно обеспечить, чтобы в репозиторий через команду `archive-push` писал только один процесс архивирования.

```text
default: y
example: archive-mode-check=n
```

### Параметр резервного копирования с резервного сервера (`--backup-standby`) {#backup-from-standby-option---backup-standby}

Резервное копирование с резервного кластера.

Включает резервное копирование с резервного сервера для снижения нагрузки на первичный кластер. Этот параметр требует настройки как первичного, так и резервного сервера.

Поддерживаются следующие режимы:

- `y` - Для резервного копирования необходим резервный сервер.
- `prefer` - Копирование с резервного сервера, если он доступен; иначе с первичного.
- `n` - Копирование только с первичного сервера.

```text
default: n
example: backup-standby=y
```

### Параметр контрольных сумм страниц (`--checksum-page`) {#page-checksums-option---checksum-page}

Проверка контрольных сумм страниц данных.

Указывает pgBackRest проверять контрольные суммы всех страниц данных при резервном копировании кластера. Этот параметр включается автоматически, если в кластере включены контрольные суммы страниц данных.

По умолчанию ошибки проверки контрольных сумм не прерывают резервное копирование. Вместо этого в журнал (а при настройках по умолчанию и на консоль) выводятся предупреждения, а список неверных страниц сохраняется в манифесте резервной копии. Чтобы вместо этого завершать резервное копирование, задайте `checksum-page-error=y`.

```text
example: checksum-page=n
```

### Параметр исключения путей и файлов (`--exclude`) {#pathfile-exclusions-option---exclude}

Исключение путей и файлов из резервной копии.

Все исключения задаются относительно `$PGDATA`. Если исключение заканчивается на /, исключаются только файлы в указанном каталоге: например, `--exclude=junk/` исключит все файлы в каталоге `$PGDATA/junk`, но сохранит сам каталог. Если исключение не заканчивается на /, файл может либо точно совпадать с исключением, либо соответствовать исключению с добавленным /: например, `--exclude=junk` исключит каталог `$PGDATA/junk` и все содержащиеся в нём файлы.

**Используйте эту возможность осторожно: очень легко исключить важные данные и нарушить согласованность резервной копии. Обязательно проверяйте восстановление!**

Все исключённые файлы записываются в журнал на уровне `info` вместе с правилом исключения. Обязательно проверяйте список исключённых файлов, чтобы убедиться, что ничего не исключено случайно.

ПРИМЕЧАНИЕ:

При дельта-восстановлении исключения не учитываются. Все файлы и каталоги, исключённые при резервном копировании, будут *удалены* при дельта-восстановлении.

Этот параметр не следует использовать для исключения журналов PostgreSQL из резервной копии. Журналы можно вынести за пределы каталога `PGDATA` с помощью настройки PostgreSQL `log_directory`; при этом они также сохранятся после восстановления.

В командной строке или файле конфигурации можно задать несколько исключений.

```text
example: exclude=junk/
```

### Параметр автоматического удаления устаревших копий (`--expire-auto`) {#expire-auto-option---expire-auto}

Автоматический запуск команды `expire` после успешного резервного копирования.

Этот параметр включён по умолчанию. Отключать его следует с осторожностью: в этом случае все резервные копии и архивы будут храниться бессрочно, что может привести к исчерпанию места в репозитории. Чтобы избежать этого, необходимо регулярно запускать команду `expire`.

При автоматическом запуске после успешного резервного копирования `expire` использует конфигурацию команды `backup`, поэтому параметры, заданные только в секции команды `expire` (например, `[global:expire]`), не применяются. Чтобы применялась конфигурация, специфичная для `expire`, отключите этот параметр и запускайте команду `expire` отдельно.

```text
default: y
example: expire-auto=y
```

### Параметр порога сохранения манифеста (`--manifest-save-threshold`) {#manifest-save-threshold-option---manifest-save-threshold}

Порог сохранения манифеста при резервном копировании.

Определяет, как часто манифест сохраняется во время резервного копирования. Сохранять его важно, поскольку он содержит контрольные суммы и обеспечивает эффективное возобновление. Фактический порог равен большему из двух значений: 1% размера резервной копии или `manifest-save-threshold`.

```text
default: 1GiB
allowed: [1B, 1TiB]
example: manifest-save-threshold=8GiB
```

### Параметр возобновления (`--resume`) {#resume-option---resume}

Разрешение возобновления неудавшегося резервного копирования.

Определяет, включена ли возможность возобновления. Она может значительно сократить время резервного копирования после сбоя предыдущей попытки того же типа. Однако она усложняет работу, поэтому в средах, где она не нужна, может быть желательно её отключить.

```text
default: y
example: resume=n
```

### Параметр быстрого запуска (`--start-fast`) {#start-fast-option---start-fast}

Принудительная контрольная точка для быстрого начала резервного копирования.

Принудительно выполняет контрольную точку, передавая `y` в параметр `fast` функции начала резервного копирования, чтобы копирование началось немедленно. Иначе резервное копирование начнётся после следующей плановой контрольной точки.

```text
default: n
example: start-fast=y
```

## Общие параметры {#general-options}

Секция `general` определяет параметры, общие для многих команд.

### Параметр разрешения запуска от root (`--allow-root`) {#allow-run-as-root-option---allow-root}

Разрешение запуска команды от пользователя root.

По умолчанию только команда `restore` может выполняться от пользователя root, поскольку она предназначена для тщательного управления принадлежностью файлов. Выполнение других команд от пользователя root может привести к созданию файлов (например, в репозитории), принадлежащих root, и, как следствие, недоступных для пользователя PostgreSQL, что вызовет сбой последующих команд.

Включите этот параметр, чтобы запустить команду от имени root. Однако гораздо лучше запускать pgBackRest от пользователя, владеющего репозиторием и кластером PostgreSQL.

```text
default: n
example: allow-root=y
```

### Параметр размера буфера (`--buffer-size`) {#buffer-size-option---buffer-size}

Размер буфера для операций ввода-вывода.

Размер буфера, используемый для копирования, сжатия, шифрования и других операций. Количество используемых буферов зависит от параметров, и каждая операция может использовать дополнительную память, например, сжатие `gz` может потребовать дополнительно 256KiB памяти.

Допустимые значения: `16KiB`, `32KiB`, `64KiB`, `128KiB`, `256KiB`, `512KiB`, `1MiB`, `2MiB`, `4MiB`, `8MiB` и `16MiB`.

```text
default: 1MiB
example: buffer-size=2MiB
```

### Параметр команды pgBackRest (`--cmd`) {#pgbackrest-command-option---cmd}

Команда pgBackRest.

pgBackRest может формировать командную строку, например когда команда `restore` создаёт настройку restore_command. В этом случае используется команда, которой был запущен процесс pgBackRest, если не задан параметр `cmd`.

ОСТОРОЖНО:

Использование обёртки для команды pgBackRest может привести к непредсказуемому поведению и не рекомендуется.

```text
default: [path of executed pgbackrest binary]
example: cmd=/var/lib/pgsql/bin/pgbackrest_wrapper.sh
```

### Параметр команды SSH-клиента (`--cmd-ssh`) {#ssh-client-command-option---cmd-ssh}

Команда SSH-клиента.

Позволяет задать конкретную команду SSH-клиента, если нужен другой клиент или команда `ssh` отсутствует в $PATH.

### Параметр сжатия (`--compress`) {#compress-option---compress}

Сжатие файлов.

Файлы резервных копий совместимы с утилитами сжатия командной строки.

Этот параметр устарел. Вместо него следует использовать `compress-type`.

```text
default: y
example: compress=n
```

### Параметр уровня сжатия (`--compress-level`) {#compress-level-option---compress-level}

Уровень сжатия файлов.

Задаёт уровень сжатия файлов, когда `compress-type` не равен `none` или задано `compress=y` (устаревший вариант).

```text
default (depending on compress-type):
    bz2 - 9
    gz - 6
    lz4 - 1
    zst - 3

allow range (depending on compress-type):
    bz2 - [1, 9]
    gz - [-1, 9]
    lz4 - [-5, 12]
    zst - [-7, 22]

example: compress-level=9
```

### Параметр уровня сжатия для сети (`--compress-level-network`) {#network-compress-level-option---compress-level-network}

Уровень сжатия для передачи по сети.

Задаёт уровень сетевого сжатия, когда `compress-type=none` и команда выполняется на другом сервере, чем репозиторий. Сжатие уменьшает сетевой трафик. Когда `compress-type` не равен `none`, настройка `compress-level-network` игнорируется и вместо неё используется `compress-level`, чтобы файл сжимался только один раз.

```text
default: 1
allowed: [-5, 12]
example: compress-level-network=1
```

### Параметр типа сжатия (`--compress-type`) {#compress-type-option---compress-type}

Тип сжатия файлов.

Поддерживаются следующие типы сжатия:

- `none` - без сжатия
- `bz2` - формат сжатия bzip2
- `gz` - формат сжатия gzip
- `lz4` - формат сжатия lz4 (доступен не на всех платформах)
- `zst` - формат сжатия Zstandard (доступен не на всех платформах)

```text
default: gz
example: compress-type=none
```

### Параметр тайм-аута базы данных (`--db-timeout`) {#database-timeout-option---db-timeout}

Тайм-аут запроса к базе данных.

Задаёт тайм-аут запросов к базе данных в секундах. Он распространяется и на функции начала и завершения резервного копирования, каждая из которых может выполняться довольно долго. Поэтому следует задавать большой тайм-аут, если нет уверенности, что эти функции завершатся быстро (то есть если задано `start-fast=y` и известно, что кластер базы данных не создаст много сегментов WAL во время резервного копирования).

ПРИМЕЧАНИЕ:

Параметр `db-timeout` должен быть меньше `protocol-timeout`.

```text
default: 30m
allowed: [100ms, 7d]
example: db-timeout=600
```

### Параметр дельта-восстановления и копирования (`--delta`) {#delta-option---delta}

Восстановление или резервное копирование с использованием контрольных сумм.

При восстановлении по умолчанию предполагается, что каталоги данных и табличных пространств PostgreSQL существуют, но пусты. Этот параметр выполняет дельта-восстановление с использованием контрольных сумм.

При резервном копировании этот параметр использует контрольные суммы вместо временных меток, чтобы определить, нужно ли копировать файлы.

```text
default: n
example: delta=y
```

### Параметр тайм-аута ввода-вывода (`--io-timeout`) {#io-timeout-option---io-timeout}

Тайм-аут ввода-вывода.

Тайм-аут, в секундах, используемый для соединений и операций чтения/записи.

Операция чтения или записи не обязана полностью завершиться за это время, но *какое-то* продвижение должно произойти, хотя бы на один байт.

```text
default: 1m
allowed: [100ms, 1h]

```

Путь для хранения файлов блокировок.

В каталоге блокировок pgBackRest создаёт файлы блокировок, предотвращающие одновременное выполнение конфликтующих операций.

### Параметр нейтральной маски umask (`--neutral-umask`) {#neutral-umask-option---neutral-umask}

Использование нейтральной маски umask.

Устанавливает umask в 0000, чтобы объекты в репозитории создавались с подходящими правами. По умолчанию права каталогов — 0750, файлов — 0640.

Чтобы вместо этого использовать umask пользователя, выполняющего команду, укажите `neutral-umask=n` в файле конфигурации или `--no-neutral-umask` в командной строке.

```text
default: y
example: neutral-umask=n
```

### Параметр приоритета процесса (`--priority`) {#set-process-priority-option---priority}

Установка приоритета процесса.

Определяет приоритет процесса (то есть значение nice) для планировщика ядра. Положительные значения понижают приоритет, отрицательные — повышают. В большинстве случаев процессы не имеют права повышать свой приоритет.

```text
allowed: [-20, 19]
example: priority=19
```

### Параметр максимального числа процессов (`--process-max`) {#process-maximum-option---process-max}

Максимальное число процессов для сжатия и передачи данных.

Каждый процесс выполняет сжатие и передачу, ускоряя выполнение команды, однако не следует задавать `process-max` настолько большим, чтобы это ухудшало производительность базы данных.

```text
default: 1
allowed: [1, 999]
example: process-max=4
```

### Параметр тайм-аута протокола (`--protocol-timeout`) {#protocol-timeout-option---protocol-timeout}

Тайм-аут протокола.

Задаёт тайм-аут, в секундах, на который локальный или удалённый процесс будет ждать получения нового сообщения на уровне протокола. Это предотвращает бесконечное ожидание сообщения процессами.

ПРИМЕЧАНИЕ:

Параметр `protocol-timeout` должен быть больше `db-timeout`.

```text
default: 31m
allowed: [100ms, 7d]
example: protocol-timeout=630
```

### Параметр поддержания соединения (`--sck-keep-alive`) {#keep-alive-option---sck-keep-alive}

Включение поддержания соединения.

Включает сообщения keep-alive для сокетных соединений.

```text
default: y
example: sck-keep-alive=n
```

### Параметр каталога очереди (`--spool-path`) {#spool-path-option---spool-path}

Путь для хранения промежуточных данных.

Этот каталог используется для хранения данных асинхронных команд `archive-push` и `archive-get`.

Асинхронная команда `archive-push` записывает подтверждения в каталог очереди после успешного сохранения WAL в архиве (а при сбое — сообщения об ошибках), чтобы процесс переднего плана мог быстро уведомить PostgreSQL. Файлы подтверждений очень малы: нулевого размера при успехе и несколько сотен байтов при ошибке.

Асинхронная команда `archive-get` помещает WAL в очередь в каталоге очереди, чтобы быстро передавать его по запросу PostgreSQL. Перемещение файлов в PostgreSQL наиболее эффективно, когда каталог очереди находится в той же файловой системе, что и `pg_xlog`/`pg_wal`. Однако не рекомендуется размещать каталог очереди *внутри* `pg_xlog`/`pg_wal`, поскольку это может вызвать проблемы у утилит PostgreSQL, таких как `pg_rewind`.

Данные в каталоге очереди нельзя считать строго временными: они могут сохраняться после перезагрузки, и их следует сохранять. Однако их потеря не представляет проблемы. pgBackRest просто повторно проверит каждый сегмент WAL, чтобы убедиться в его надёжном архивировании для `archive-push`, и заново построит очередь для `archive-get`.

Каталог очереди предназначен для размещения в локальной файловой системе, совместимой с Posix, а не в удалённой файловой системе, такой как NFS или CIFS.

```text
default: /var/spool/pgbackrest
example: spool-path=/backup/db/spool
```

### Параметр числа сообщений keep-alive (`--tcp-keep-alive-count`) {#keep-alive-count-option---tcp-keep-alive-count}

Число сообщений keep-alive.

Задаёт число сообщений TCP keep-alive, которые могут быть потеряны, прежде чем соединение будет считаться неработающим.

Этот параметр доступен на системах, которые поддерживают опцию сокета `TCP_KEEPCNT`.

### Параметр времени простоя keep-alive (`--tcp-keep-alive-idle`) {#keep-alive-idle-option---tcp-keep-alive-idle}

Время простоя перед отправкой keep-alive.

Задаёт время отсутствия сетевой активности в секундах, по истечении которого операционной системе следует отправить сообщение TCP keep-alive.

Этот параметр доступен на системах, которые поддерживают опцию сокета `TCP_KEEPIDLE`.

```text

```

### Параметр интервала keep-alive (`--tcp-keep-alive-interval`) {#keep-alive-interval-option---tcp-keep-alive-interval}

Интервал сообщений keep-alive.

Задаёт время в секундах, после которого следует повторно отправить сообщение TCP keep-alive, не получившее подтверждения.

Этот параметр доступен на системах, которые поддерживают опцию сокета `TCP_KEEPINTVL`.

```text

example: tcp-keep-alive-interval=30
```

### Параметр наборов шифров TLSv1.2 (`--tls-cipher-12`) {#tlsv12-cipher-suites-option---tls-cipher-12}

Допустимые наборы шифров TLSv1.2.

Все соединения TLS между клиентом pgBackRest и сервером зашифрованы. По умолчанию также зашифрованы соединения с объектными хранилищами (например, S3).

При необходимости допустимые наборы шифров можно изменить. Приведённый пример подходит, если нет особых требований к безопасности. Если параметр не задан (по умолчанию), применяется значение по умолчанию используемой библиотеки OpenSSL.

```text
example: tls-cipher-12=HIGH:MEDIUM:+3DES:!aNULL
```

### Параметр наборов шифров TLSv1.3 (`--tls-cipher-13`) {#tlsv13-cipher-suites-option---tls-cipher-13}

Допустимые наборы шифров TLSv1.3.

## Параметры для сопровождающих {#maintainer-options}

Параметры для сопровождающих предназначены для поддержки форков PostgreSQL. Сопровождающему форка следует определить подходящие значения и затем сообщить их пользователям форка.

ПРЕДУПРЕЖДЕНИЕ:

Неправильное использование этих параметров может привести к неожиданному поведению или повреждению данных.

Сопровождающий форка отвечает за тестирование pgBackRest с требуемыми параметрами. pgBackRest не гарантирует совместимость ни с одним форком.

### Параметр проверки заголовков WAL (`--archive-header-check`) {#check-wal-headers-option---archive-header-check}

Проверка версии и идентификатора PostgreSQL в заголовках WAL.

Этот параметр включён по умолчанию и проверяет соответствие заголовка WAL версии PostgreSQL и системному идентификатору, чтобы убедиться, что WAL копируется в правильную stanza. Эта проверка дополняет проверку соответствия `pg_control` stanza и проверку того, что WAL копируется из того же каталога данных PostgreSQL, где находится `pg_control`.

Поэтому отключение этой проверки достаточно безопасно, но делать это следует только при необходимости, например если WAL зашифрован.

```text
default: y
example: archive-header-check=n
```

### Параметр проверки заголовков страниц (`--page-header-check`) {#page-header-check-option---page-header-check}

Проверка заголовков страниц PostgreSQL.

Этот параметр включён по умолчанию и добавляет проверки заголовков страниц.

Следует избегать отключения этого параметра, кроме случаев, когда оно необходимо, например если страницы зашифрованы.

```text
default: y
example: page-header-check=n
```

### Параметр принудительного задания версии PostgreSQL (`--pg-version-force`) {#force-postgresql-version-option---pg-version-force}

Принудительное задание версии PostgreSQL.

Указанная версия PostgreSQL будет использоваться вместо версии, автоматически определённой по `pg_control` или заголовкам WAL. Это полезно главным образом для форков PostgreSQL или версий в разработке, в которых эти значения отличаются от версии выпуска. Версия, которую PostgreSQL сообщает через `server_version_num`, должна совпадать с принудительно заданной.

ПРЕДУПРЕЖДЕНИЕ:

Используйте этот параметр осторожно: `pg_control` и заголовки WAL всё равно будут читаться в формате, ожидаемом для указанной версии, то есть в формате официальной версии PostgreSQL с открытым исходным кодом. Если форк или версия в разработке меняет формат полей, от которых зависит pgBackRest, это приведёт к неожиданному поведению. В общем случае параметр будет работать как ожидается только тогда, когда форк добавляет все собственные поля структур *после* стандартных полей PostgreSQL.

```text
example: pg-version-force=15
```

## Параметры репозитория {#repository-options}

Секция `repository` определяет параметры настройки репозитория.

**Индексация**: все параметры `repo-` имеют индексы, что позволяет настраивать несколько репозиториев. Например, один репозиторий настраивается параметрами `repo1-path`, `repo1-host` и т. п. Если настроено несколько репозиториев и для команды не указан параметр `--repo`, действия с репозиториями выполняются в порядке убывания приоритета (например, сначала repo1, затем repo2).

Параметры `repo-retention-*` определяют срок хранения резервных копий. Удаление происходит только тогда, когда число завершённых резервных копий превышает заданное число хранимых копий. Иными словами, если `repo1-retention-full-type` равен `count` (по умолчанию), а `repo1-retention-full` равен 2, то для удаления самой старой копии должны существовать 3 завершённые копии. Если `repo1-retention-full-type` равен `time`, значение `repo1-retention-full` задаётся в днях, поэтому до удаления должны накопиться полные резервные копии хотя бы за указанное число дней. Убедитесь, что места всегда хватает для числа копий, заданного сроком хранения, + 1 резервной копии.

### Параметр поблочного инкрементного резервного копирования (`--repo-block`) {#block-incremental-backup-option---repo-block}

Включение поблочного инкрементного резервного копирования.

Поблочное инкрементное копирование позволяет создавать более детальные резервные копии, разбивая файлы на блоки, которые можно копировать независимо. Это экономит место в репозитории и может ускорить дельта-восстановление, поскольку отдельные блоки можно получать без чтения всего файла из репозитория.

ПРИМЕЧАНИЕ:

Прежде чем включить `repo-block`, необходимо включить параметр `repo-bundle`.

Размер блока определяется размером и возрастом файла. Как правило, для более старых или крупных файлов выбираются более крупные блоки. Если файл достаточно старый, поблочное инкрементное копирование для него не используется.

Поблочное инкрементное копирование наиболее эффективно, когда включено для всех типов резервных копий, в том числе полных. Полная копия при этом становится немного больше, зато последующие дифференциальные и инкрементные копии могут использовать созданные ею карты блоков для экономии места.

```text
default: n
example: repo1-block=y
```

### Параметр пакетирования файлов в репозитории (`--repo-bundle`) {#repository-bundles-option---repo-bundle}

Пакетирование файлов в репозитории.

Объединяет небольшие файлы в пакеты, уменьшая общее число файлов, записываемых в репозиторий. Записывать меньше файлов обычно эффективнее, особенно в объектные хранилища, такие как S3. Кроме того, файлы нулевого размера не сохраняются (кроме записей в манифесте), что экономит время и место.

```text
default: n
example: repo1-bundle=y
```

### Параметр предельного размера файла в пакете репозитория (`--repo-bundle-limit`) {#repository-bundle-limit-option---repo-bundle-limit}

Предельный размер файлов для пакетирования.

Максимальный размер файлов, включаемых в пакеты. Файлы большего размера хранятся отдельно.

Файлы в пакетах нельзя использовать повторно при возобновлении резервного копирования, поэтому этот параметр определяет, какие файлы можно использовать при возобновлении: чем больше значение, тем меньше таких файлов.

```text
default: 2MiB
allowed: [8KiB, 1PiB]
example: repo1-bundle-limit=10MiB
```

### Параметр размера пакета репозитория (`--repo-bundle-size`) {#repository-bundle-size-option---repo-bundle-size}

Целевой размер пакета файлов.

Определяет целевой суммарный размер файлов, добавляемых в один пакет. Несжатый пакет может достигать размера `repo-bundle-size` + `repo-bundle-limit`, поэтому не следует задавать этому параметру максимальный размер, допустимый файловой системой.

Как правило, слишком большое значение нежелательно: при повторной попытке потребуется заново обработать весь пакет.

```text
default: 20MiB
allowed: [1MiB, 1PiB]
example: repo1-bundle-size=10MiB
```

### Параметр хранения архива (`--repo-retention-archive`) {#archive-retention-option---repo-retention-archive}

Число резервных копий, для которых сохраняется непрерывный WAL.

ПРИМЕЧАНИЕ:

Сегменты WAL, необходимые для согласованности резервной копии, всегда сохраняются до удаления этой копии независимо от настройки данного параметра.

Если значение не задано, а `repo-retention-full-type` равен `count` (по умолчанию), то для удаления архива по умолчанию используется значение `repo-retention-full` (или `repo-retention-diff`), соответствующее `repo-retention-archive-type`, заданному как `full` (или `diff`). Это гарантирует, что WAL удаляется только для уже удалённых резервных копий. Если `repo-retention-full-type` равен `time`, по умолчанию удаляются архивы, предшествующие самой старой полной копии, оставшейся после применения настройки `repo-retention-full`.

Этот параметр должен быть задан, если `repo-retention-archive-type` равен `incr`. При острой нехватке дискового пространства он вместе с `repo-retention-archive-type` позволяет агрессивнее удалять сегменты WAL. Однако это исключает возможность PITR из копий с удалённым WAL и потому **не** рекомендуется.

```text
allowed: [1, 9999999]
example: repo1-retention-archive=2
```

Устаревшее имя: retention-archive

### Параметр типа хранения архива (`--repo-retention-archive-type`) {#archive-retention-type-option---repo-retention-archive-type}

Тип резервных копий для хранения WAL.

Поддерживаются следующие типы резервных копий:

- `full` - pgBackRest сохраняет архивные журналы для числа полных резервных копий, заданного `repo-retention-archive`.
- `diff` - (дифференциальные) pgBackRest сохраняет архивные журналы для числа полных и дифференциальных копий, заданного `repo-retention-archive`: если последняя копия полная, для целей хранения в репозитории она учитывается как дифференциальная.
- `incr` - (инкрементные) pgBackRest сохраняет архивные журналы для числа полных, дифференциальных и инкрементных копий, заданного `repo-retention-archive`.

Рекомендуется оставить значение по умолчанию, при котором WAL удаляется только вместе с полными резервными копиями.

```text
default: full
example: repo1-retention-archive-type=diff
```

Устаревшее имя: retention-archive-type

### Параметр хранения дифференциальных копий (`--repo-retention-diff`) {#differential-retention-option---repo-retention-diff}

Число сохраняемых дифференциальных резервных копий.

При удалении дифференциальной копии также удаляются все связанные с ней инкрементные копии. Если параметр не задан, все дифференциальные копии сохраняются до удаления полных копий, от которых они зависят.

При определении копий для удаления полные копии учитываются в числе дифференциальных. В большинстве случаев это немного уменьшает число дифференциальных копий, которые необходимо хранить.

```text
allowed: [1, 9999999]
example: repo1-retention-diff=3
```

Устаревшее имя: retention-diff

### Параметр хранения полных копий (`--repo-retention-full`) {#full-retention-option---repo-retention-full}

Число или срок хранения полных резервных копий.

При удалении полной копии также удаляются все связанные с ней дифференциальные и инкрементные копии. Если параметр не задан, выводится предупреждение. Для бессрочного хранения задайте максимальное значение.

```text
allowed: [1, 9999999]
example: repo1-retention-full=2
```

Устаревшее имя: retention-full

### Параметр типа хранения полных копий (`--repo-retention-full-type`) {#full-retention-type-option---repo-retention-full-type}

Тип срока хранения полных резервных копий.

Определяет, означает ли настройка `repo-retention-full` период времени (в днях) или число полных копий, которые нужно сохранять.

Поддерживаются следующие типы хранения:

- `time` - полные копии старше `repo-retention-full` удаляются из репозитория, если существует хотя бы ещё одна копия, возраст которой не меньше значения `repo-retention-full`. Например, если `repo-retention-full` равен 30 (дней) и есть 2 полные копии возрастом 25 и 35 дней, ни одна не будет удалена: после удаления копии возрастом 35 дней останется только копия возрастом 25 дней, что нарушит политику хранения за 30 дней. Эта политика требует наличия хотя бы одной копии возрастом 30 дней перед удалением более старой. Архивный WAL, предшествующий самой старой оставшейся полной копии, удаляется автоматически, если `repo-retention-archive-type` и `repo-retention-archive` не заданы явно.
- `count` - полные копии сверх числа `repo-retention-full` удаляются. Например, если `repo-retention-full` равен `4` и завершается пятая полная копия, самая старая полная копия будет удалена, чтобы их число осталось равным 4.

Резервная копия учитывается при применении политики хранения только после успешного завершения. Например, если `repo-retention-full-type` равен `count`, а `repo-retention-full` равен `2`, для удаления самой старой копии должны существовать 3 завершённые полные копии.

```text
default: count
example: repo1-retention-full-type=time
```

### Параметр хранения истории резервных копий (`--repo-retention-history`) {#backup-history-retention-option---repo-retention-history}

Число дней хранения манифестов истории резервных копий.

После завершения резервного копирования копия манифеста сохраняется в каталоге `backup.history`. По умолчанию эти файлы никогда не удаляются, поскольку полезны для анализа данных, например для измерения роста резервных копий и WAL со временем.

Параметр `repo-retention-history` задаёт число дней хранения манифестов истории резервных копий. Неудалённые резервные копии всегда сохраняются в истории. Укажите `repo-retention-history=0`, чтобы хранить историю только для неудалённых резервных копий.

При удалении манифеста истории полной резервной копии также удаляются манифесты истории всех связанных с ней дифференциальных и инкрементных копий.

```text

example: repo1-retention-history=365
```

### Параметр типа проверки ключа сервера SFTP (`--repo-sftp-host-key-check-type`) {#sftp-host-key-check-type-option---repo-sftp-host-key-check-type}

### Параметр чтения с пропуском ненужных данных в хранилище репозитория (`--repo-storage-read-over`) {#repository-storage-read-over-option---repo-storage-read-over}

Чтение с пропуском ненужных данных в хранилище репозитория.

Пакеты файлов могут содержать данные, не нужные при восстановлении, например уже существующие файлы. Этот параметр позволяет пропускать ненужные данные, продолжая чтение без нового запроса к объектному хранилищу. Обычно это быстрее, поскольку задержка нового запроса чтения больше, чем при продолжении уже выполняющегося чтения. Для большинства классов хранения это также дешевле.

```text
default: 64KiB
allowed: [0B, 1MiB]
example: repo1-storage-read-over=128KiB
```

### Параметр тегов хранилища репозитория (`--repo-storage-tag`) {#repository-storage-tag-option---repo-storage-tag}

Теги хранилища репозитория.

Задаёт теги, добавляемые к объектам, если репозиторий расположен в объектном хранилище (например, S3). Параметр можно повторять для добавления нескольких тегов.

В pgBackRest нет возможности изменять эти теги, поэтому их следует правильно задать до запуска `stanza-create`, чтобы теги были одинаковыми во всём репозитории.

```text
example: repo1-storage-tag=key1=value1
```

### Параметр размера части загрузки в хранилище репозитория (`--repo-storage-upload-chunk-size`) {#repository-storage-upload-chunk-size-option---repo-storage-upload-chunk-size}

Размер части загрузки в хранилище репозитория.

Объектные хранилища, такие как S3, позволяют загружать файлы частями, если файл слишком велик для размещения в памяти. Даже если он помещается в память, ограничение объёма памяти для загрузок позволяет использовать её экономнее.

Больший размер части обычно повышает производительность, поскольку уменьшает число запросов загрузки и позволяет загружать больше файлов одним запросом, а не частями. Недостаток — повышенное потребление памяти. Поскольку буфер части выделяется каждому процессу, большие значения `process-max` увеличивают общий расход памяти.

Допустимые размеры частей зависят от типа хранилища и платформы. Например, минимальный размер части в AWS S3 — 5MiB. Терминология также различается: при поиске минимальных и максимальных значений используйте «part size» для AWS S3, «chunk size» для GCS и «block size» для Azure.

Если файл больше 1GiB (максимального размера, который PostgreSQL создаёт по умолчанию), размер части постепенно увеличивается вплоть до максимально допустимого, чтобы завершить загрузку файла.

```text
default (depending on repo-type):
    azure - 4MiB
    gcs - 4MiB
    s3 - 5MiB

allow range (depending on repo-type):
    azure - [4MiB, 1GiB]
    gcs - [4MiB, 1GiB]
    s3 - [5MiB, 1GiB]

example: repo1-storage-upload-chunk-size=16MiB
```

### Параметр проверки сертификата хранилища репозитория (`--repo-storage-verify-tls`) {#repository-storage-certificate-verify-option---repo-storage-verify-tls}

Проверка сертификата хранилища репозитория.

Позволяет включать и отключать проверку TLS-сертификата сервера хранилища (например, S3 или Azure). Отключать проверку следует только при тестировании или в других случаях использования самоподписанного сертификата.

```text
default: y
example: repo1-storage-verify-tls=n
```

Устаревшие имена: repo-azure-verify-tls, repo-s3-verify-ssl, repo-s3-verify-tls

### Параметр символических ссылок в репозитории (`--repo-symlink`) {#repository-symlink-option---repo-symlink}

Создание символических ссылок внутри репозитория.

Включает создание символических ссылок `latest` и ссылок табличных пространств. Эти ссылки наиболее полезны при использовании снимков для восстановления непосредственно в репозитории, что встречается редко.

Хотя подавляющему большинству пользователей эта возможность, вероятно, не нужна, она остаётся включённой по умолчанию ради совместимости. Однако для Posix-подобных хранилищ, не поддерживающих символические ссылки, может быть полезно отключить их.

```text
default: y
example: repo1-symlink=n
```

### Параметр целевого времени репозитория (`--repo-target-time`) {#target-time-for-repository-option---repo-target-time}

Целевое время репозитория.

Целевое время определяет момент, на который команды читают репозиторий в хранилище с версионированием. Это позволяет прочитать состояние репозитория на определённый момент времени и восстановить данные, удалённые или повреждённые по ошибке пользователя либо вредоносным ПО.

S3, GCS и Azure поддерживают версионирование, но обычно оно отключено по умолчанию. Помимо включения версионирования, может быть полезно включить блокировку объектов в S3 и обратимое удаление в GCS или Azure.

Если указан параметр `repo-target-time`, необходимо также указать `repo`. Версионирование, вероятно, поддерживается не всеми типами репозиториев, и в целом при восстановлении разумно обращаться к одному конкретному репозиторию.

Временные метки хранилища сравниваются с указанной по условию <=; миллисекунды, если они указаны, отбрасываются.

```text
example: repo-target-time=2024-08-08 12:12:12+00
```

### Параметр типа репозитория (`--repo-type`) {#repository-type-option---repo-type}

Тип хранилища репозитория.

Поддерживаются следующие типы репозиториев:

- `azure` - Azure Blob Storage Service
- `cifs` - Аналогичен `posix`, но отключает ссылки и fsync каталогов
- `gcs` - Google Cloud Storage
- `posix` - Файловые системы, совместимые с Posix
- `s3` - AWS Simple Storage Service
- `sftp` - Secure File Transfer Protocol

При использовании смонтированной NFS в качестве репозитория `posix` к pgBackRest применяются те же правила, что описаны в документации PostgreSQL: [Создание кластера баз данных — файловые системы](https://www.postgresql.org/docs/current/creating-cluster.html#CREATING-CLUSTER-FILESYSTEM).

```text
default: posix
example: repo1-type=cifs
```

## Параметры восстановления {#restore-options}

Секция `restore` определяет параметры восстановления резервных копий.

### Параметр режима архивирования (`--archive-mode`) {#archive-mode-option---archive-mode}

Сохранение или отключение архивирования на восстановленном кластере.

Позволяет сохранить или отключить архивирование на восстановленном кластере. Это полезно, когда для выполнения определённой работы кластер необходимо повысить до первичного, но использовать его как новый первичный сервер не планируется. В таком случае отправлять WAL этого кластера в репозиторий нежелательно.

Поддерживаются следующие режимы:

- `off` - Отключает архивирование, задавая `archive_mode=off`.
- `preserve` - Сохраняет текущее значение `archive_mode`.

**ПРИМЕЧАНИЕ**: этот параметр недоступен в PostgreSQL < 12.

```text
default: preserve
example: archive-mode=off
```

### Параметр исключения баз данных (`--db-exclude`) {#exclude-database-option---db-exclude}

Восстановление с исключением указанных баз данных.

Исключённые базы данных восстанавливаются в виде разреженных файлов, заполненных нулями: это экономит место, сохраняя возможность восстановления PostgreSQL. После восстановления эти базы будут недоступны, но их можно удалить командой `drop database`. Параметр `--db-exclude` можно передать несколько раз, чтобы исключить несколько баз данных.

В сочетании с параметром `--db-include` параметр `--db-exclude` применяется только к стандартным системным базам данных (`template0`, `template1` и `postgres`).

```text
example: db-exclude=db_main
```

### Параметр включения баз данных (`--db-include`) {#include-database-option---db-include}

Восстановление только указанных баз данных.

Эта возможность позволяет восстановить только выбранные базы данных. Базы, не включённые явно, восстанавливаются в виде разреженных файлов, заполненных нулями: это экономит место, сохраняя возможность восстановления PostgreSQL. После восстановления базы, которые не были включены, будут недоступны, но их можно удалить командой `drop database`.

ПРИМЕЧАНИЕ:

Встроенные базы данных (`template0`, `template1` и `postgres`) всегда восстанавливаются, если они не исключены явно.

Параметр `--db-include` можно передать несколько раз, чтобы включить несколько баз данных.

Дополнительные сведения и ограничения приведены в разделе [Восстановление выбранных баз данных](/ru/pgbackrest/user-guide/#restore-selected-databases).

```text
example: db-include=db_main
```

### Параметр восстановления всех ссылок (`--link-all`) {#link-all-option---link-all}

Восстановление всех символических ссылок.

По умолчанию каталоги и файлы, на которые указывают символические ссылки, восстанавливаются как обычные каталоги и файлы в $PGDATA. Причина в том, что восстанавливать ссылки на исходные цели в другой системе, отличной от той, где выполнялось резервное копирование, может быть небезопасно. Этот параметр восстанавливает все символические ссылки в том виде, в каком они были в исходной системе при резервном копировании.

```text
default: n
example: link-all=y
```

### Параметр переназначения ссылок (`--link-map`) {#link-map-option---link-map}

Изменение цели символической ссылки.

Позволяет при восстановлении изменить целевой файл или путь символической ссылки. Это полезно при восстановлении в системах, где организация хранилища отличается от исходной системы, в которой была создана резервная копия.

```text
example: link-map=pg_xlog=/data/xlog
```

### Параметр настройки восстановления (`--recovery-option`) {#recovery-option---recovery-option}

Установка параметра в `postgresql.auto.conf` или `recovery.conf`.

Сведения о параметрах `postgresql.auto.conf` и `recovery.conf` приведены в разделе [Конфигурация сервера](https://www.postgresql.org/docs/current/runtime-config.html) (обязательно выберите свою версию PostgreSQL). Этот параметр можно указывать несколько раз.

Для PostgreSQL >= 12 параметры записываются в `postgresql.auto.conf`. Для всех остальных версий — в `recovery.conf`.

ПРИМЕЧАНИЕ:

Параметр `restore_command` создаётся автоматически, но его можно переопределить этим параметром. Собственный `restore_command` следует задавать осторожно, поскольку pgBackRest рассчитан на автоматическое управление им. Параметры цели восстановления (recovery_target_name, recovery_target_time и т. п.) pgBackRest формирует автоматически, и их не следует задавать таким способом.

Поскольку после записи файла `postgresql.auto.conf` или `recovery.conf` pgBackRest не запускает PostgreSQL, перед ручным перезапуском всегда можно проверить или отредактировать `postgresql.auto.conf` или `recovery.conf`.

```text
example: recovery-option=primary_conninfo=db.mydomain.com
```

### Параметр переназначения табличного пространства (`--tablespace-map`) {#tablespace-map-option---tablespace-map}

Восстановление табличного пространства в указанный каталог.

Перемещает табличное пространство в новое расположение при восстановлении. Это полезно, когда расположения табличных пространств на реплике отличаются или после обновления системы изменились точки монтирования.

Расположения табличных пространств не хранятся в pg_tablespace, поэтому их можно свободно перемещать. Однако переносить табличное пространство в `data_directory` не рекомендуется: это может вызвать проблемы. Дополнительные сведения о перемещении табличных пространств приведены на http://www.databasesoup.com/2013/11/moving-tablespaces.html.

```text
example: tablespace-map=ts_01=/db/ts_01
```

### Параметр переназначения всех табличных пространств (`--tablespace-map-all`) {#map-all-tablespaces-option---tablespace-map-all}

Восстановление всех табличных пространств в указанный каталог.

По умолчанию табличные пространства восстанавливаются в исходные расположения. Для каждого пространства это можно изменить параметром `tablespace-map`, но иногда удобнее сразу переназначить все пространства в новый каталог. Это особенно полезно в системах разработки или предварительного тестирования, где организация хранилища может отличаться от исходной системы, в которой была создана резервная копия.

Указанный путь будет родительским каталогом, в котором создаются все табличные пространства из резервной копии.

ОСТОРОЖНО:

Табличные пространства, созданные после начала резервного копирования, не переназначаются. Если требуется переназначение, после создания табличного пространства следует сделать новую резервную копию.

```text
example: tablespace-map-all=/data/tablespace
```

## Параметры сервера {#server-options}

Секция `server` определяет параметры настройки TLS-сервера.

### Параметр адреса TLS-сервера (`--tls-server-address`) {#tls-server-address-option---tls-server-address}

Адрес TLS-сервера.

IP-адрес, на котором сервер будет слушать запросы клиентов.

```text
default: localhost
example: tls-server-address=*
```

### Параметр авторизованных клиентов TLS-сервера (`--tls-server-auth`) {#tls-server-authorized-clients-option---tls-server-auth}

Авторизованные клиенты TLS-сервера.

Сервер авторизует клиентов, проверяя их сертификаты и сверяя CN (общее имя) сертификата со списком, заданным на сервере параметром `tls-server-auth`.

Клиентский CN можно авторизовать для любого количества stanza, передав в параметре `tls-server-auth` список через запятую, либо для всех stanza, указав `tls-server-auth=client-cn=*`. Для клиентского CN нельзя указывать подстановочные символы.

```text
example: tls-server-auth=client-cn=stanza1,stanza2
```

### Параметр центров сертификации TLS-сервера (`--tls-server-ca-file`) {#tls-server-certificate-authorities-option---tls-server-ca-file}

Центры сертификации TLS-сервера.

Проверяет, что сертификаты клиентов подписаны доверенным центром сертификации.

```text
example: tls-server-ca-file=/path/to/server.ca
```

### Параметр сертификата TLS-сервера (`--tls-server-cert-file`) {#tls-server-certificate-option---tls-server-cert-file}

Файл сертификата TLS-сервера.

Отправляется клиенту для подтверждения личности сервера.

```text
example: tls-server-cert-file=/path/to/server.crt
```

### Параметр ключа TLS-сервера (`--tls-server-key-file`) {#tls-server-key-option---tls-server-key-file}

Файл ключа TLS-сервера.

Подтверждает, что сертификат сервера отправлен его владельцем.

```text
example: tls-server-key-file=/path/to/server.key
```

### Параметр порта TLS-сервера (`--tls-server-port`) {#tls-server-port-option---tls-server-port}

Порт сервера TLS.

Порт, на котором сервер будет слушать запросы клиентов.

```text
default: 8432
allowed: [1, 65535]
example: tls-server-port=8000
```

## Параметры stanza {#stanza-options}

Stanza определяет конфигурацию резервного копирования конкретного кластера баз данных PostgreSQL. В секции stanza должен быть задан путь к кластеру, а для удалённого кластера — также сервер и пользователь. Кроме того, любые глобальные секции конфигурации можно переопределить, задав настройки для конкретной stanza.

**Индексация**: все параметры `pg-` имеют индексы, что позволяет настраивать несколько серверов PostgreSQL. Например, один первичный сервер настраивается параметрами `pg1-path`, `pg1-port` и т. п. Если настроен резервный сервер, укажите на сервере репозитория его параметры `pg-` с индексом `pg2-` (например, pg2-host, pg2-path и т. п.).

### Параметр базы данных PostgreSQL (`--pg-database`) {#postgresql-database-option---pg-database}

База данных PostgreSQL.

Имя базы данных для соединения с PostgreSQL. Обычно лучше оставить значение по умолчанию, но в некоторых установках такой базы может не быть.

По историческим причинам значение переменной окружения `PGDATABASE` игнорируется.

```text
default: postgres
example: pg1-database=backupdb
```

### Параметр сервера PostgreSQL (`--pg-host`) {#postgresql-host-option---pg-host}

Сервер PostgreSQL для удалённой работы.

Используется при резервном копировании, когда сервер PostgreSQL отличается от сервера репозитория.

```text
example: pg1-host=db.domain.com
```

Устаревшее имя: db-host

### Параметр файла центра сертификации сервера PostgreSQL (`--pg-host-ca-file`) {#postgresql-host-certificate-authority-file-option---pg-host-ca-file}

Файл центра сертификации сервера PostgreSQL.

Позволяет использовать для соединения с сервером PostgreSQL файл CA, отличный от системного файла по умолчанию.

```text
example: pg1-host-ca-file=/etc/pki/tls/certs/ca-bundle.crt
```

### Параметр каталога центра сертификации сервера PostgreSQL (`--pg-host-ca-path`) {#postgresql-host-certificate-authority-path-option---pg-host-ca-path}

Каталог центра сертификации сервера PostgreSQL.

Позволяет использовать для соединения с сервером PostgreSQL каталог CA, отличный от системного каталога по умолчанию.

```text
example: pg1-host-ca-path=/etc/pki/tls/certs
```

### Параметр файла сертификата сервера PostgreSQL (`--pg-host-cert-file`) {#postgresql-host-certificate-file-option---pg-host-cert-file}

Файл сертификата для сервера PostgreSQL.

Отправляется серверу PostgreSQL для подтверждения личности клиента.

```text
example: pg1-host-cert-file=/path/to/client.crt
```

### Параметр команды на сервере PostgreSQL (`--pg-host-cmd`) {#postgresql-host-command-option---pg-host-cmd}

Команда pgBackRest на сервере PostgreSQL.

Требуется только тогда, когда путь к команде pgBackRest на локальном сервере и сервере PostgreSQL различается. Если параметр не задан, команда на сервере PostgreSQL будет той же, что и локальная команда.

```text
default: [path of executed pgbackrest binary]
example: pg1-host-cmd=/usr/lib/backrest/bin/pgbackrest
```

Устаревшее имя: db-cmd

### Параметр файла конфигурации сервера PostgreSQL (`--pg-host-config`) {#postgresql-host-configuration-option---pg-host-config}

Файл конфигурации pgBackRest на сервере базы данных.

Задаёт расположение файла конфигурации на сервере PostgreSQL. Требуется только тогда, когда оно отличается от расположения локального файла конфигурации.

```text
default: CFGOPTDEF_CONFIG_PATH "/" PROJECT_CONFIG_FILE
example: pg1-host-config=/conf/pgbackrest/pgbackrest.conf
```

Устаревшее имя: db-config

### Параметр каталога включаемых конфигураций сервера PostgreSQL (`--pg-host-config-include-path`) {#postgresql-host-configuration-include-path-option---pg-host-config-include-path}

Каталог включаемых конфигураций pgBackRest на сервере базы данных.

Задаёт расположение каталога включаемых конфигураций на сервере PostgreSQL. Требуется только тогда, когда оно отличается от расположения локального каталога включаемых конфигураций.

```text
default: CFGOPTDEF_CONFIG_PATH "/" PROJECT_CONFIG_INCLUDE_PATH
example: pg1-host-config-include-path=/conf/pgbackrest/conf.d
```

```text
default: CFGOPTDEF_CONFIG_PATH
```

### Параметр порта сервера PostgreSQL (`--pg-host-port`) {#postgresql-host-port-option---pg-host-port}

Порт сервера PostgreSQL при заданном `pg-host`.

Позволяет указать нестандартный порт для протокола сервера PostgreSQL.

ПРИМЕЧАНИЕ:

При `pg-host-type=ssh` для `pg-host-port` нет значения по умолчанию. В этом случае используется порт, настроенный для команды, указанной в `cmd-ssh`.

```text
default (depending on pg-host-type):
    tls - 8432

allowed: [0, 65535]
example: pg1-host-port=25
```

Устаревшее имя: db-ssh-port

### Параметр типа протокола сервера PostgreSQL (`--pg-host-type`) {#postgresql-host-protocol-type-option---pg-host-type}

Тип протокола сервера PostgreSQL.

Поддерживаются следующие типы протоколов:

- `ssh` - Secure Shell.
- `tls` - TLS-сервер pgBackRest.

```text
default: ssh
example: pg1-host-type=tls
```

### Параметр пользователя сервера PostgreSQL (`--pg-host-user`) {#postgresql-host-user-option---pg-host-user}

Пользователь для входа на сервер PostgreSQL при заданном `pg-host`.

Этот пользователь также будет владельцем удалённого процесса pgBackRest и будет устанавливать соединения с PostgreSQL. Для правильной работы следует использовать владельца кластера базы данных PostgreSQL, обычно это пользователь `postgres`, выбранный по умолчанию.

```text
default: postgres
example: pg1-host-user=db_owner
```

Устаревшее имя: db-user

### Параметр пути PostgreSQL (`--pg-path`) {#postgresql-path-option---pg-path}

Каталог данных PostgreSQL.

Следует указать значение `data_directory`, сообщаемое PostgreSQL. Хотя его можно получить из разных источников, разумно задать его явно на случай, если эти источники будут недоступны при восстановлении или резервном копировании остановленного кластера.

При каждом резервном копировании работающего кластера параметр `pg-path` сверяется со значением, сообщаемым PostgreSQL, поэтому его следует всегда поддерживать актуальным.

```text
example: pg1-path=/data/db
```

Устаревшее имя: db-path

### Параметр порта PostgreSQL (`--pg-port`) {#postgresql-port-option---pg-port}

Порт PostgreSQL.

Порт, на котором работает PostgreSQL. Обычно его не требуется указывать, поскольку большинство кластеров PostgreSQL работают на порту по умолчанию.

```text
default: 5432
allowed: [0, 65535]
example: pg1-port=6543
```

Устаревшее имя: db-port

### Параметр каталога сокета PostgreSQL (`--pg-socket-path`) {#postgresql-socket-path-option---pg-socket-path}

Каталог Unix-сокета PostgreSQL.

Каталог Unix-сокета, указанный при запуске PostgreSQL. pgBackRest автоматически проверяет стандартное расположение для используемой ОС, поэтому обычно этот параметр не требуется, если каталог сокета не был явно изменён настройкой `unix_socket_directories` в `postgresql.conf`.

```text
example: pg1-socket-path=/var/run/postgresql
```

Устаревшее имя: db-socket-path

### Параметр пользователя базы данных PostgreSQL (`--pg-user`) {#postgresql-database-user-option---pg-user}

Пользователь базы данных PostgreSQL.

Имя пользователя базы данных для соединения с PostgreSQL. Если оно не указано, pgBackRest использует локального пользователя ОС или `PGUSER`.

```text
example: pg1-user=backupuser
```
