## 脆弱な暗号化サブキーとソルト {#weak-encryption}

**2026年10月4日**

2.59.3より前のpgBackRestは、暗号化用のランダムデータを生成する際にエラーを確認していませんでした。OpenSSLがオペレーティングシステムからランダムデータを取得できない場合、メモリ内に既に存在するデータから暗号化サブキーとソルトが生成され、エラーは報告されませんでした。暗号化されていないリポジトリは影響を受けません。

このエラーが発生することはまれと考えられます。原因として、`getrandom()`システムコールをブロックするサンドボックスやseccompポリシー、無効なOpenSSL設定などが考えられます。

主に問題となるのは、`archive.info`と`backup.info`内のサブキーです。これらは`stanza-create`で一度だけ生成され、スタンザの存続期間を通して使用されるため、アップグレードしても脆弱なサブキーは置き換わりません。バックアップ用の脆弱なサブキーとソルトは、バックアップとWALの有効期限が切れるにつれて削除されます。

### 影響 {#weak-encryption-impact}

WALのサブキーは`archive.info`に、マニフェストのサブキーは`backup.info`に保存されます。脆弱なサブキーはランダムなサブキーより推測しやすく、推測に成功すると、`repo-cipher-pass`なしで、そのサブキーで暗号化されたファイルを復号できます。推測の容易さはメモリ内のデータに依存し、プラットフォームやビルドによって異なります。`archive.info`のサブキーが脆弱だと、リポジトリ内のすべてのWALが漏えいの危険にさらされます。`backup.info`のサブキーが脆弱だと、すべてのバックアップが漏えいの危険にさらされます。マニフェストはそのサブキーで暗号化され、各マニフェストには対応するバックアップのファイル用サブキーが保存されているためです。これにはアップグレード後に追加されたWALとバックアップも含まれます。

バックアップ内のファイル用サブキーは、完全バックアップごとに生成され、その完全バックアップに基づく差分バックアップと増分バックアップでも使用されます。バックアップ用サブキーが脆弱だと、これらのバックアップ内のファイルが漏えいの危険にさらされます。

脆弱なソルト自体がサブキーを露出させることはありません。同じサブキーとソルトで暗号化されたファイルは同じキーとIVを使用するため、それらのファイル内の同一データからは同一の暗号文が生成されます。ソルトは各ファイルの先頭に平文で保存され、脆弱なソルトには、それまでメモリに存在していたデータが最大8バイト含まれる可能性があります。

### サブキーの確認 {#weak-encryption-check-subkey}

リポジトリにアクセスできるホストで、`STANZA`にスタンザ名を設定して以下を実行してください。最初のリポジトリ以外を確認するには、`pgbackrest`コマンドに`--repo`を追加してください。

```bash
STANZA=demo

for file in archive/$STANZA/archive.info backup/$STANZA/backup.info; do
    for key in $(pgbackrest --stanza=$STANZA repo-get $file | grep '^cipher-pass=' | grep -oE '[A-Za-z0-9+/]{64}'); do
        echo "$(printf '%s' $key | base64 -d | od -An -v -tx1 | tr -s ' ' '\n' | grep -c '^00$') $file"
    done
done
```

最初の列はサブキー内のゼロバイトの数です。ランダムなサブキーに6個以上のゼロバイトが含まれる確率は25,000,000分の1未満ですが、テストで見つかった脆弱なサブキーには13個以上含まれていました。ゼロバイトが6個以上含まれるサブキーは脆弱とみなすべきです。

### OpenSSL 1.0 {#weak-encryption-openssl-1-0}

2.53より前のpgBackRestはOpenSSL 1.0でビルドできました。このバージョンでは、オペレーティングシステムからランダムデータを取得できないと、ランダムデータでシードを設定していない状態からランダムデータを生成します。この方法で生成された脆弱なサブキーは、上記の確認方法では検出できません。

### 対処方法 {#weak-encryption-remediation}

- pgBackRest 2.59.3以降にアップグレードしてください。これらのバージョンは、ランダムデータを生成できない場合にエラーを報告します。
- `archive.info`または`backup.info`内のサブキーが脆弱な場合は、新しいリポジトリにスタンザを作成し、古いリポジトリはそのバックアップが必要な間だけ保持してください。
- 差分バックアップと増分バックアップは、その基となる完全バックアップのサブキーを使用するため、アップグレード後に新しい完全バックアップを作成することを検討してください。
- バックアップ用の脆弱なサブキーとソルトは、アップグレード前のバックアップとWALの有効期限が切れるにつれて削除されます。保持期間が長いバックアップでは、有効期限が切れるまで残ります。

## 新しい配布用tarアーカイブ {#distribution-tarball}

**2026年7月20日**

pgBackRest 2.59.0以降、各リリースにはソースからのビルドを簡単にする配布用tarアーカイブが含まれます。gitリポジトリのチェックアウトとは異なり、このtarアーカイブには生成済みのソースコードとレンダリング済みのドキュメントが同梱されています。このため、リポジトリのチェックアウトで必要になるコード生成やドキュメント用のツールなしで、pgBackRestをビルドしてインストールできます。

tarアーカイブには、生成済みコードを含むpgBackRestのソース、コマンドリファレンスのmanページ、HTMLドキュメント、ビルドを検証するスモークテストが含まれています。通常のpgBackRestライブラリだけを使用し、mesonとninjaでビルドできます。

tarアーカイブは`pgbackrest-{version}.tar.gz`という名前のアセットとして、対応する`.sha256sum`チェックサムとともに各リリースに添付されます。GitHubの[リリース](https://github.com/pgbackrest/pgbackrest/releases)ページからダウンロードし、ビルドとテストの手順についてはtarアーカイブ内の`README.md`を参照してください。

パッケージ作成者には、配布用tarアーカイブからビルドすることを推奨します。これにより、今後のリリースでコードとドキュメントの生成に必要になる追加のビルドツールを導入せずに済みます。

## pgBackRestの保守終了について {#no-longer-maintained}

**2026年4月27日**

要点：pgBackRestの保守を終了します。pgBackRestをフォークする場合は、プロジェクトに新しい名前を付けてください。

熟考の末、pgBackRestの開発をやめることにしました。軽い気持ちで決めたわけではありません。pgBackRestは過去13年間、情熱を注いできたプロジェクトです。幸い、その多くの期間に企業からのスポンサー支援を受けられましたが、多くの貢献者に助けられながら現在のpgBackRestを築くために、深夜や週末を費やすことも少なくありませんでした。オープンソース開発者なら誰もが、私の言う意味や、特別なプロジェクトに人生のどれほど多くを捧げることになるかをよくご存じでしょう。

Crunchy Dataの売却以降、pgBackRestを保守しながら、この仕事を続けられる職を探してきましたが、これまでのところ見つかっていません。同様に、スポンサー獲得の取り組みも、プロジェクトを継続するために必要な水準には大きく届いていません。

他の人と同じように、私も生計を立てる必要がありますが、pgBackRest関連の仕事は非常に限られています。今後はより幅広い仕事を検討できますが、それらに就くとpgBackRestに取り組む時間はなくなります。保守、不具合修正、PRレビュー、issueへの回答などだけでも相当の時間が必要です。そこには、私が最も好きな新機能の開発時間すら含まれていません。不十分な、あるいは散発的な作業を続けるより、明確に区切りを付けるほうがよいと考えています。

いずれpgBackRestはフォークされると思います。ただ、それは新しいメンテナーによる新しいプロジェクトとなり、私たちと同じように信頼を築いていく必要があります。

最後に、長年にわたりpgBackRestに貢献してくださった皆様に、改めて感謝します。皆様と一緒に取り組めたことは喜びでした！
