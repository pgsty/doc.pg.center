ينبغي أن تعمل الإعدادات الافتراضية في etcd بشكل جيد للتثبيتات على شبكة محلية يكون متوسط زمن استجابة الشبكة فيها منخفضًا. ومع ذلك، عند استخدام etcd عبر مراكز بيانات متعددة أو عبر شبكات ذات زمن استجابة مرتفع، قد يحتاج إعدادا فاصل نبض القلب ومهلة الانتخاب إلى ضبط.

الشبكة ليست المصدر الوحيد لزمن الاستجابة. فكلٌّ من الطلب والاستجابة قد يتأثر بأقراص بطيئة على القائد والتابع على حد سواء. وتمثل كلٌّ من هاتين المهلتين إجمالي الوقت من الطلب حتى الاستجابة الناجحة من الجهاز الآخر.

## معلمات الوقت {#time-parameters}

يعتمد بروتوكول التوافق الموزع الكامن على معلمتي زمن منفصلتين لضمان قدرة العقد على تسليم القيادة إذا تعثّرت إحداها أو انقطع اتصالها. تُسمى المعلمة الأولى *فاصل نبض القلب* (Heartbeat Interval)، وهي التكرار الذي يخطر به القائد التابعين بأنه لا يزال القائد.
وفقًا لأفضل الممارسات، ينبغي ضبط هذه المعلمة حول وقت الذهاب والإياب بين الأعضاء. افتراضيًا، يستخدم etcd فاصل نبض قلب مقداره `100ms`.

المعلمة الثانية هي *مهلة الانتخاب* (Election Timeout). تُحدد هذه المهلة المدة التي تمضيها عقدة تابع دون سماع نبضة قلب قبل أن تحاول أن تصبح قائدًا بنفسها. افتراضيًا، يستخدم etcd مهلة انتخاب مقدارها `1000ms`.

إن ضبط هذه القيم ينطوي على مقايضة. يوصى بأن تكون قيمة فاصل نبض القلب حول الحد الأقصى لمتوسط وقت الذهاب والإياب (RTT) بين الأعضاء، وعادةً عند حوالي 0.5-1.5x من وقت الذهاب والإياب. إذا كان فاصل نبض القلب منخفضًا جدًا، فسيرسل etcd رسائل غير ضرورية تزيد من استخدام موارد المعالج والشبكة. ومن الجهة الأخرى، يؤدي فاصل نبض القلب المرتفع جدًا إلى مهلة انتخاب مرتفعة. وتستغرق مهلة الانتخاب الأعلى وقتًا أطول لاكتشاف فشل القائد. وأسهل طريقة لقياس وقت الذهاب والإياب (RTT) هي استخدام [أداة PING][ping].

ينبغي ضبط مهلة الانتخاب استنادًا إلى فاصل نبض القلب ومتوسط وقت الذهاب والإياب بين الأعضاء. يجب أن تكون مهل الانتخاب 10 أضعاف وقت الذهاب والإياب على الأقل حتى تراعي التباين في الشبكة. فعلى سبيل المثال، إذا كان وقت الذهاب والإياب بين الأعضاء 10ms فيجب أن تكون مهلة الانتخاب 100ms على الأقل.

الحد الأعلى لمهلة الانتخاب هو 50000ms (50s)، ولا ينبغي استخدامه إلا عند نشر عنقود etcd موزع عالميًا. وقت الذهاب والإياب المعقول داخل الولايات المتحدة القارية هو 130ms، والوقت بين الولايات المتحدة واليابان حوالي 350-400ms. إذا كانت الشبكة ذات أداء غير متكافئ أو بها تأخيرات/فقدان منتظم للحزم، فمن الممكن أن تكون هناك حاجة إلى بضع محاولات إعادة لإرسال حزمة بنجاح. لذا فإن 5s حد أعلى آمن لوقت الذهاب والإياب العالمي. وبما أن مهلة الانتخاب ينبغي أن تكون أكبر من وقت البث بمقدار رتبة حجمية، ففي حالة ~5s لعنقود موزع عالميًا، يصبح 50 ثانية حدًا أقصى معقولًا.

ينبغي أن تكون قيمتا فاصل نبض القلب ومهلة الانتخاب متماثلتين لجميع الأعضاء في العنقود الواحد. قد يؤدي تعيين قيم مختلفة لأعضاء etcd إلى الإخلال باستقرار العنقود.

يمكن تجاوز القيم الافتراضية من سطر الأوامر:

```sh
# Command line arguments:
$ etcd --heartbeat-interval=100 --election-timeout=500

# Environment variables:
$ ETCD_HEARTBEAT_INTERVAL=100 ETCD_ELECTION_TIMEOUT=500 etcd
```

تُحدَّد القيم بالمللي ثانية.

## اللقطات {#snapshots}

يُلحق etcd جميع تغييرات المفاتيح بملف سجل. ينمو هذا السجل بلا نهاية ويشكل تاريخًا خطيًا كاملًا لكل تغيير أُجري على المفاتيح. يعمل التاريخ الكامل جيدًا للعناقيد قليلة الاستخدام، لكن العناقيد كثيفة الاستخدام ستحمل معها سجلًا ضخمًا.

لتجنب وجود سجل ضخم، ينشئ etcd لقطات دورية. توفر هذه اللقطات لـ etcd طريقة لضغط السجل عبر حفظ الحالة الحالية للنظام وإزالة السجلات القديمة.

### ضبط اللقطات {#snapshot-tuning}

تُنشأ لقطات Raft بعد عدد مُهيَّأ من الإدخالات المطبَّقة؛ ولم يعد etcd 3.7 يستخدم الواجهة الخلفية V2. افتراضيًا، ستُنشأ اللقطات بعد كل 10,000 تغيير. إذا كان استخدام etcd للذاكرة والقرص مرتفعًا جدًا، فجرّب خفض عتبة اللقطات بتعيين ما يلي في سطر الأوامر:

```sh
# Command line arguments:
$ etcd --snapshot-count=5000

# Environment variables:
$ ETCD_SNAPSHOT_COUNT=5000 etcd
```

## القرص {#disk}

عنقود etcd حساس جدًا لأزمنة استجابة الأقراص. وبما أن على etcd حفظ المقترحات في سجله بصفة دائمة، فقد يتسبب نشاط القرص الناتج عن عمليات أخرى في أزمنة استجابة `fsync` طويلة. والنتيجة أن etcd قد يفوّت نبضات القلب، مما يسبب انتهاء مهل الطلبات وفقدان القائد مؤقتًا. يمكن لخادم etcd أحيانًا أن يعمل بثبات إلى جانب هذه العمليات عند منحه أولوية قرص عالية.

على Linux، يمكن تهيئة أولوية قرص etcd باستخدام `ionice`:

```sh
# best effort, highest priority
$ sudo ionice -c2 -n0 -p `pgrep etcd`
```

## الشبكة {#network}

إذا كان قائد etcd يخدم عددًا كبيرًا من طلبات العملاء المتزامنة، فقد يؤخر معالجة طلبات أقران التابعين بسبب ازدحام الشبكة. ويظهر ذلك في صورة رسائل خطأ مخزن الإرسال المؤقت على العقد التابعة:

```
dropped MsgProp to 247ae21ff9436b2d since streamMsg's sending buffer is full
dropped MsgAppResp to 247ae21ff9436b2d since streamMsg's sending buffer is full
```

يمكن حل هذه الأخطاء بمنح حركة مرور الأقران الخاصة بـ etcd أولوية على حركة مرور العملاء. على Linux، يمكن منح حركة مرور الأقران أولوية باستخدام آلية التحكم في حركة المرور:

```
tc qdisc add dev eth0 root handle 1: prio bands 3
tc filter add dev eth0 parent 1: protocol ip prio 1 u32 match ip sport 2380 0xffff flowid 1:1
tc filter add dev eth0 parent 1: protocol ip prio 1 u32 match ip dport 2380 0xffff flowid 1:1
tc filter add dev eth0 parent 1: protocol ip prio 2 u32 match ip sport 2379 0xffff flowid 1:1
tc filter add dev eth0 parent 1: protocol ip prio 2 u32 match ip dport 2379 0xffff flowid 1:1
```

[ping]: https://en.wikipedia.org/wiki/Ping_(networking_utility)


لإلغاء `tc`، نفِّذ:

```
tc qdisc del dev eth0 root
```

## CPU {#cpu}

بما أن etcd حساس جدًا لزمن الاستجابة، يمكن تحسين الأداء بشكل أكبر على أنظمة Linux بضبط حاكم المعالج (CPU governor) على وضع performance أو conservative.

على Linux، يمكن تهيئة حاكم المعالج (CPU governor) على وضع performance:
```
echo performance | tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
```
