يهدف هذا المستند إلى تقديم نظرة عامة على التصميم الأساسي لواجهات برمجة تطبيقات etcd الإصدار v3.
ينبغي عدم الخلط بينه وبين واجهة etcd v2 API، التي أُهملت في etcd v3.5.
لا يدّعي هذا المستند الشمول بأي حال، بل يهدف إلى التركيز على الأفكار الأساسية اللازمة لفهم etcd دون التشتت بنداءات API الأقل شيوعًا.
جميع واجهات API في etcd معرَّفة في [خدمات gRPC][grpc-service]، التي تصنف نداءات الإجراءات البعيدة (RPCs) التي يفهمها خادم etcd.
القائمة الكاملة بجميع نداءات RPC في etcd موثقة بصيغة markdown في [قائمة واجهة gRPC API][grpc-api].

## خدمات gRPC {#grpc-services}

كل طلب API يُرسَل إلى خادم etcd هو نداء إجراء بعيد gRPC. تُصنَّف نداءات RPC في etcd بناءً على الوظيفة إلى خدمات.

تشمل الخدمات المهمة للتعامل مع فضاء مفاتيح etcd ما يلي:
* KV - ينشئ أزواج المفتاح-القيمة ويحدّثها ويجلبها ويحذفها.
* Watch - يراقب التغييرات على المفاتيح.
* Lease - بدائيات لاستهلاك رسائل keep-alive من العميل.

تشمل الخدمات التي تدير العنقود نفسه ما يلي:
* Auth - آلية مصادقة قائمة على الأدوار لمصادقة المستخدمين.
* Cluster - يوفر معلومات العضوية ومرافق التهيئة.
* Maintenance - يأخذ لقطات الاستعادة، ويزيل تجزئة المخزن، ويعيد معلومات الحالة لكل عضو.

### الطلبات والاستجابات {#requests-and-responses}

تتبع جميع نداءات RPC في etcd التنسيق نفسه. لكل نداء RPC دالة `Name` تأخذ `NameRequest` كوسيطة وتعيد `NameResponse` كاستجابة. على سبيل المثال، إليك وصف نداء RPC الخاص بـ `Range`:

```protobuf
service KV {
  Range(RangeRequest) returns (RangeResponse)
  ...
}
```

### ترويسة الاستجابة {#response-header}

تحمل جميع الاستجابات من واجهة etcd API ترويسة استجابة مرفقة تتضمن البيانات الوصفية للعنقود الخاصة بالاستجابة:

```proto
message ResponseHeader {
  uint64 cluster_id = 1;
  uint64 member_id = 2;
  int64 revision = 3;
  uint64 raft_term = 4;
}
```

* Cluster_ID - معرّف العنقود الذي يولّد الاستجابة.
* Member_ID - معرّف العضو الذي يولّد الاستجابة.
* Revision - مراجعة مخزن المفتاح-القيمة عند توليد الاستجابة.
* Raft_Term - دورة Raft (term) الخاصة بالعضو عند توليد الاستجابة.

يمكن لتطبيق ما قراءة الحقل `Cluster_ID` أو `Member_ID` للتأكد من أنه يتواصل مع العنقود (العضو) المقصود.

يمكن للتطبيقات استخدام الحقل `Revision` لمعرفة أحدث مراجعة لمخزن المفتاح-القيمة. وهذا مفيد بشكل خاص عندما تحدد التطبيقات مراجعة تاريخية لإجراء `time travel query` وترغب في معرفة أحدث مراجعة وقت تقديم الطلب.

يمكن للتطبيقات استخدام `Raft_Term` لاكتشاف متى يكمل العنقود انتخاب قائد جديد.

## واجهة API للمفتاح-القيمة {#key-value-api}

تعالج واجهة API للمفتاح-القيمة أزواج المفتاح-القيمة المخزنة داخل etcd. معظم الطلبات المرسلة إلى etcd هي عادةً طلبات مفتاح-قيمة.

### بدائيات النظام {#system-primitives}

### زوج المفتاح-القيمة {#key-value-pair}

زوج المفتاح-القيمة هو أصغر وحدة يمكن لواجهة API للمفتاح-القيمة معالجتها. لكل زوج مفتاح-قيمة عدد من الحقول، معرَّفة بصيغة [protobuf][kv-proto]:

```protobuf
message KeyValue {
  bytes key = 1;
  int64 create_revision = 2;
  int64 mod_revision = 3;
  int64 version = 4;
  bytes value = 5;
  int64 lease = 6;
}
```

* Key - المفتاح بصيغة بايتات. لا يُسمح بمفتاح فارغ.
* Value - القيمة بصيغة بايتات.
* Version - الإصدار هو إصدار المفتاح. الحذف يعيد ضبط الإصدار إلى الصفر، وأي تعديل على المفتاح يزيد من إصداره.
* Create_Revision - مراجعة آخر إنشاء للمفتاح.
* Mod_Revision - مراجعة آخر تعديل على المفتاح.
* Lease - معرّف عقد الإيجار (lease) المرفق بالمفتاح. إذا كان عقد الإيجار 0، فلا يوجد عقد إيجار مرفق بالمفتاح.


بالإضافة إلى المفتاح والقيمة فقط، يرفق etcd بيانات وصفية إضافية للمراجعة كجزء من رسالة المفتاح. ترتب معلومات المراجعة هذه المفاتيح حسب وقت الإنشاء والتعديل، وهو أمر مفيد لإدارة التزامن في المزامنة الموزعة. تستخدم [الأقفال المشتركة الموزعة][locks] في عميل etcd مراجعة الإنشاء لانتظار ملكية القفل. وبالمثل، تُستخدم مراجعة التعديل لاكتشاف تعارضات مجموعة القراءة في [الذاكرة المعاملاتية البرمجية][STM] وانتظار تحديثات [انتخاب القائد][elections].

#### المراجعات {#revisions}

يحافظ etcd على عداد 64 بت يشمل العنقود بأكمله، يسمى مراجعة المخزن، يزداد في كل مرة يُعدَّل فيها فضاء المفاتيح. تعمل المراجعة كساعة منطقية عامة، ترتب جميع التحديثات على المخزن ترتيبًا متسلسلًا. التغيير الذي تمثله المراجعة الجديدة تزايدي؛ فالبيانات المرتبطة بمراجعة ما هي البيانات التي غيّرت المخزن. داخليًا، تعني المراجعة الجديدة كتابة التغييرات في شجرة B+ الخاصة بالواجهة الخلفية، مفهرسةً بالمراجعة المتزايدة.

تصبح المراجعات أكثر قيمة عند النظر في الواجهة الخلفية [التحكم في التزامن متعدد الإصدارات][mvcc] في etcd. يعني نموذج MVCC إمكانية عرض مخزن المفتاح-القيمة من مراجعات سابقة، إذ يُحتفظ بالمراجعات التاريخية للمفاتيح. يمكن لمسؤولي العنقود تهيئة سياسة الاحتفاظ بهذا التاريخ لإدارة تخزين دقيقة التفاصيل؛ وعادةً يتخلص etcd من المراجعات القديمة للمفاتيح وفق مؤقت زمني. يحتفظ عنقود etcd النموذجي ببيانات المفاتيح المتجاوزة لساعات. يوفر ذلك أيضًا معالجة موثوقة لانقطاعات العميل الطويلة، وليس فقط الاضطرابات الشبكية العابرة: فالمراقبون يستأنفون ببساطة من آخر مراجعة تاريخية لوحظت. وبالمثل، للقراءة من المخزن في نقطة زمنية معينة، يمكن وسم طلبات القراءة بمراجعة لإرجاع المفاتيح من عرض لفضاء المفاتيح في النقطة الزمنية التي اعتُمدت فيها تلك المراجعة.

#### نطاقات المفاتيح {#key-ranges}

يفهرس نموذج بيانات etcd جميع المفاتيح في فضاء مفاتيح ثنائي مسطح. ويختلف ذلك عن أنظمة مخازن المفتاح-القيمة الأخرى التي تستخدم نظامًا هرميًا لتنظيم المفاتيح في أدلة. وبدلًا من سرد المفاتيح حسب الدليل، تُسرَد المفاتيح حسب فواصل مفاتيح `[a, b)`.

كثيرًا ما تُسمى هذه الفواصل «النطاقات» في etcd. العمليات على النطاقات أقوى من العمليات على الأدلة. مثل المخازن الهرمية، تدعم الفواصل البحث عن مفتاح واحد عبر `[a, a+1)` (مثلًا، تبحث ['a', 'a\x00') عن 'a') والبحث في الدلائل بترميز المفاتيح حسب عمق الدليل. بالإضافة إلى تلك العمليات، يمكن للفواصل ترميز البادئات أيضًا؛ فمثلًا تبحث الفاصلة `['a', 'b')` عن جميع المفاتيح ذات البادئة بالسلسلة 'a'.

بحسب الاصطلاح، تُحدَّد نطاقات الطلب بالحقلين `key` و `range_end`. حقل `key` هو أول مفتاح في النطاق وينبغي ألا يكون فارغًا. أما `range_end` فهو المفتاح التالي لآخر مفتاح في النطاق. إذا لم يُعطَ `range_end` أو كان فارغًا، فسيُعرَّف النطاق ليحتوي على وسيطة المفتاح فقط. إذا كان `range_end` يساوي `key` زائد واحد (مثلًا، "aa"+1 == "ab" و "a\xff"+1 == "b")، فإن النطاق يمثل جميع المفاتيح التي يكون المفتاح بادئة لها. إذا كان كل من `key` و `range_end` يساوي '\0'، فإن النطاق يمثل جميع المفاتيح. إذا كان `range_end` يساوي '\0'، فالنطاق هو جميع المفاتيح الأكبر من وسيطة المفتاح أو المساوية لها.

### Range {#range}

تُجلَب المفاتيح من مخزن المفتاح-القيمة باستخدام نداء API الخاص بـ `Range`، الذي يأخذ `RangeRequest`:

```protobuf
message RangeRequest {
  enum SortOrder {
	NONE = 0; // default, no sorting
	ASCEND = 1; // lowest target value first
	DESCEND = 2; // highest target value first
  }
  enum SortTarget {
	KEY = 0;
	VERSION = 1;
	CREATE = 2;
	MOD = 3;
	VALUE = 4;
  }

  bytes key = 1;
  bytes range_end = 2;
  int64 limit = 3;
  int64 revision = 4;
  SortOrder sort_order = 5;
  SortTarget sort_target = 6;
  bool serializable = 7;
  bool keys_only = 8;
  bool count_only = 9;
  int64 min_mod_revision = 10;
  int64 max_mod_revision = 11;
  int64 min_create_revision = 12;
  int64 max_create_revision = 13;
}
```

* Key, Range_End - نطاق المفاتيح المطلوب جلبه.
* Limit - الحد الأقصى لعدد المفاتيح المعادة للطلب. عندما يُضبط limit على 0، يعامَل كعدم وجود حد.
* Revision - النقطة الزمنية لمخزن المفتاح-القيمة المطلوب استخدامها لطلب النطاق. إذا كانت المراجعة أقل من الصفر أو تساويه، فالنطاق يجري على أحدث حالة لمخزن المفتاح-القيمة. إذا كانت المراجعة مضغوطة، تُعاد ErrCompacted كاستجابة.
* Sort_Order - الترتيب المستخدم للطلبات المرتبة.
* Sort_Target - حقل المفتاح-القيمة المطلوب ترتيبه.
* Serializable - يضبط طلب النطاق لاستخدام قراءات محلية للعضو قابلة للتسلسل (serializable). افتراضيًا، Range خطّي (linearizable)؛ إذ يعكس الإجماع الحالي للعنقود. للحصول على أداء وتوافرية أفضل، مقابل قراءات قديمة محتملة، يُخدَم طلب النطاق القابل للتسلسل محليًا دون حاجة للوصول إلى إجماع مع العقد الأخرى في العنقود.
* Keys_Only - يعيد المفاتيح فقط دون القيم.
* Count_Only - يعيد عدد المفاتيح في النطاق فقط.
* Min_Mod_Revision - الحد الأدنى لمراجعات تعديل المفاتيح؛ يستبعد المراجعات الأدنى.
* Max_Mod_Revision - الحد الأقصى لمراجعات تعديل المفاتيح؛ يستبعد المراجعات الأعلى.
* Min_Create_Revision - الحد الأدنى لمراجعات إنشاء المفاتيح؛ يستبعد المراجعات الأدنى.
* Max_Create_Revision - الحد الأقصى لمراجعات إنشاء المفاتيح؛ يستبعد المراجعات الأعلى.

يتلقى العميل رسالة `RangeResponse` من نداء `Range`:

```protobuf
message RangeResponse {
  ResponseHeader header = 1;
  repeated mvccpb.KeyValue kvs = 2;
  bool more = 3;
  int64 count = 4;
}
```

* Kvs - قائمة أزواج المفتاح-القيمة المطابقة لطلب النطاق. عندما يكون `Count_Only` مضبوطًا، تكون `Kvs` فارغة.
* More - يشير إلى ما إذا كانت هناك مفاتيح أخرى يجب إعادتها في النطاق المطلوب إذا كان `limit` مضبوطًا.
* Count - العدد الإجمالي للمفاتيح التي تحقق طلب النطاق.

للنطاقات الكبيرة من المفاتيح حيث يكون تخزين الاستجابة الكاملة مؤقتًا غير مرغوب فيه، راجع [RangeStream](#rangestream).

### RangeStream {#rangestream}

يعيد `RangeStream` مجموعة النتائج نفسها التي يعيدها `Range`، لكن الخادم يقسم الاستجابة إلى سلسلة من الأجزاء ويبثها إلى العميل. يتجنب ذلك تخزين النطاقات الكبيرة بالكامل في الذاكرة على أي من الطرفين. يقبل `RangeStream` نفس `RangeRequest` الذي يقبله `Range`.

يتلقى العميل تدفقًا من رسائل `RangeStreamResponse` من نداء `RangeStream`:

```protobuf
message RangeStreamResponse {
  RangeResponse range_response = 1;
}
```

تعبئة الحقول عبر الأجزاء:

* Kvs - يحمل كل جزء شريحة منفصلة من النتيجة. يؤدي تسلسل `kvs` من كل جزء بالترتيب الذي تصل به إلى الحصول على مجموعة المفاتيح نفسها التي يعيدها نداء `Range` واحد.
* Header, More, Count - تُملأ في الجزء الأخير فقط، وفقط عندما يكتمل التدفق دون خطأ. تترك الأجزاء السابقة هذه الحقول بقيمة صفرية. يؤدي تطبيق `proto.Merge` على `range_response` لكل جزء إلى الحصول على `RangeResponse` مكافئ لما كان سيعيده `Range`.

إذا انتهى التدفق بخطأ، لا يحمل أي جزء قيمة صالحة لـ `header` أو `more` أو `count`.

يُخدَم كل جزء في التدفق وفق المراجعة نفسها. إذا لم يضبط الطلب `Revision`، يلتقط الخادم آخر مراجعة معتمدة عند بدء التدفق ويعيد استخدامها لبقية التدفق.

لا يدعم `RangeStream` ترتيبات الفرز المخصصة ولا مرشحات المراجعة (`min_mod_revision` و `max_mod_revision` و `min_create_revision` و `max_create_revision`). الطلبات التي تستخدم أيًّا منهما تعيد `Unimplemented`. كما أن `RangeStream` غير مدعوم من قبل وكيل gRPC الخاص بـ etcd.

توجد طريقتان شائعتان لاستهلاك `RangeStream`:

1. **معالجة كل جزء بشكل مستقل.** تناسب سيناريوهات الأداء العالي حيث يريد العميل فك ترميز المفاتيح والتصرف بناءً عليها فور وصولها بدلًا من جمع النتيجة كاملة أولًا. يمر العميل على الأجزاء ويعالج `kvs` من كل جزء، ثم يقرأ `header` أو `more` أو `count` من الجزء الأخير بعد انتهاء التدفق بشكل سليم.
2. **تجميع استجابة واحدة.** تناسب عندما يريد العميل نتيجة مكافئة لنداء `Range` أحادي. يدمج العميل `range_response` لكل جزء في `RangeResponse` واحد (مثلًا عبر `proto.Merge`). تحتوي النتيجة المدمجة على `kvs` الكامل، إضافة إلى `header` و `more` و `count` من الجزء الأخير. يوفر عميل Go الدالة `clientv3.GetStreamToGetResponse` كمساعد لهذا النمط.

### Put {#put}

تُحفَظ المفاتيح في مخزن المفتاح-القيمة بإصدار نداء `Put`، الذي يأخذ `PutRequest`:

```protobuf
message PutRequest {
  bytes key = 1;
  bytes value = 2;
  int64 lease = 3;
  bool prev_kv = 4;
  bool ignore_value = 5;
  bool ignore_lease = 6;
}
```

* Key - اسم المفتاح المطلوب وضعه في مخزن المفتاح-القيمة.
* Value - القيمة، بصيغة بايتات، المطلوب ربطها بالمفتاح في مخزن المفتاح-القيمة.
* Lease - معرّف عقد الإيجار المطلوب ربطه بالمفتاح في مخزن المفتاح-القيمة. قيمة عقد الإيجار 0 تعني عدم وجود عقد إيجار.
* Prev_Kv - عند ضبطه، يستجيب ببيانات زوج المفتاح-القيمة قبل التحديث الناتج عن طلب `Put` هذا.
* Ignore_Value - عند ضبطه، يحدّث المفتاح دون تغيير قيمته الحالية. يعيد خطأ إذا كان المفتاح غير موجود.
* Ignore_Lease - عند ضبطه، يحدّث المفتاح دون تغيير عقد الإيجار الحالي له. يعيد خطأ إذا كان المفتاح غير موجود.

يتلقى العميل رسالة `PutResponse` من نداء `Put`:

```protobuf
message PutResponse {
  ResponseHeader header = 1;
  mvccpb.KeyValue prev_kv = 2;
}
```

* Prev_Kv - زوج المفتاح-القيمة الذي استبدله `Put`، إذا كان `Prev_Kv` مضبوطًا في `PutRequest`.

### حذف النطاق {#delete-range}

تُحذَف نطاقات المفاتيح باستخدام نداء `DeleteRange`، الذي يأخذ `DeleteRangeRequest`:

```protobuf
message DeleteRangeRequest {
  bytes key = 1;
  bytes range_end = 2;
  bool prev_kv = 3;
}
```

* Key, Range_End - نطاق المفاتيح المطلوب حذفه.
* Prev_Kv - عند ضبطه، يعيد محتوى أزواج المفتاح-القيمة المحذوفة.

يتلقى العميل رسالة `DeleteRangeResponse` من نداء `DeleteRange`:

```protobuf
message DeleteRangeResponse {
  ResponseHeader header = 1;
  int64 deleted = 2;
  repeated mvccpb.KeyValue prev_kvs = 3;
}
```

* Deleted - عدد المفاتيح المحذوفة.
* Prev_Kv - قائمة بجميع أزواج المفتاح-القيمة التي حذفتها عملية `DeleteRange`.

### المعاملة {#transaction}

المعاملة بنية ذرية من نوع If/Then/Else فوق مخزن المفتاح-القيمة. فهي توفر بدائية لتجميع الطلبات معًا في كتل ذرية (أي then/else) يكون تنفيذها محميًا (أي if) استنادًا إلى محتوى مخزن المفتاح-القيمة. يمكن استخدام المعاملات لحماية المفاتيح من التحديثات المتزامنة غير المقصودة، وبناء عمليات المقارنة والاستبدال (compare-and-swap)، وتطوير تحكم تزامني أعلى مستوى.

يمكن للمعاملة معالجة طلبات متعددة معالجة ذرية في طلب واحد. بالنسبة لتعديلات مخزن المفتاح-القيمة، يعني ذلك أن مراجعة المخزن تزداد مرة واحدة فقط للمعاملة، وأن جميع الأحداث التي تولدها المعاملة ستكون لها المراجعة نفسها. ومع ذلك، يُحظر تعديل المفتاح نفسه عدة مرات داخل معاملة واحدة.

تُحمى جميع المعاملات باقتران من المقارنات، بشكل مشابه لعبارة `If`. تتحقق كل مقارنة من مفتاح واحد في المخزن. وقد تتحقق من غياب قيمة أو وجودها، أو تقارنها بقيمة معينة، أو تفحص مراجعة المفتاح أو إصداره. وقد تنطبق مقارنتان مختلفتان على المفاتيح نفسها أو على مفاتيح مختلفة. تُطبَّق جميع المقارنات بشكل ذري؛ فإذا كانت جميع المقارنات صحيحة، قيل إن المعاملة نجحت وطبّق etcd كتلة الطلب then / `success` الخاصة بالمعاملة، وإلا قيل إنها فشلت وطبّق كتلة الطلب else / `failure`.

تُرمَّز كل مقارنة كرسالة `Compare`:

```protobuf
message Compare {
  enum CompareResult {
    EQUAL = 0;
    GREATER = 1;
    LESS = 2;
    NOT_EQUAL = 3;
  }
  enum CompareTarget {
    VERSION = 0;
    CREATE = 1;
    MOD = 2;
    VALUE= 3;
  }
  CompareResult result = 1;
  // target is the key-value field to inspect for the comparison.
  CompareTarget target = 2;
  // key is the subject key for the comparison operation.
  bytes key = 3;
  oneof target_union {
    int64 version = 4;
    int64 create_revision = 5;
    int64 mod_revision = 6;
    bytes value = 7;
  }
}
```

* Result - نوع عملية المقارنة المنطقية (مثل يساوي، أقل من، إلخ).
* Target - حقل المفتاح-القيمة المطلوب مقارنته. إما إصدار المفتاح، أو مراجعة الإنشاء، أو مراجعة التعديل، أو القيمة.
* Key - المفتاح المستخدم في المقارنة.
* Target_Union - البيانات التي حددها المستخدم للمقارنة.

بعد معالجة كتلة المقارنة، تطبق المعاملة كتلة من الطلبات. الكتلة قائمة من رسائل `RequestOp`:

```protobuf
message RequestOp {
  // request is a union of request types accepted by a transaction.
  oneof request {
    RangeRequest request_range = 1;
    PutRequest request_put = 2;
    DeleteRangeRequest request_delete_range = 3;
  }
}
```

* Request_Range - رسالة `RangeRequest`.
* Request_Put - رسالة `PutRequest`. يجب أن تكون المفاتيح فريدة. ولا يجوز أن تتشارك المفاتيح مع أي عمليات Put أو Deletes أخرى.
* Request_Delete_Range - رسالة `DeleteRangeRequest`. ولا يجوز أن تتشارك المفاتيح مع أي طلبات Put أو Deletes.

بأخذها جميعًا معًا، تُصدَر المعاملة بنداء API باسم `Txn`، الذي يأخذ `TxnRequest`:

```protobuf
message TxnRequest {
  repeated Compare compare = 1;
  repeated RequestOp success = 2;
  repeated RequestOp failure = 3;
}
```

* Compare - قائمة من المسندات تمثل اقترانًا من العبارات لحماية المعاملة.
* Success - قائمة الطلبات المطلوب معالجتها إذا قُيِّمت جميع اختبارات المقارنة إلى true.
* Failure - قائمة الطلبات المطلوب معالجتها إذا قُيِّم أي اختبار مقارنة إلى false.

يتلقى العميل رسالة `TxnResponse` من نداء `Txn`:

```protobuf
message TxnResponse {
  ResponseHeader header = 1;
  bool succeeded = 2;
  repeated ResponseOp responses = 3;
}
```

* Succeeded - ما إذا كانت `Compare` قُيِّمت إلى true أو false.
* Responses - قائمة من الاستجابات تقابل نتائج تطبيق كتلة `Success` إذا كانت succeeded تساوي true، أو كتلة `Failure` إذا كانت تساوي false.

تقابل قائمة `Responses` نتائج قائمة `RequestOp` المطبقة، مع ترميز كل استجابة كـ `ResponseOp`:

```protobuf
message ResponseOp {
  oneof response {
    RangeResponse response_range = 1;
    PutResponse response_put = 2;
    DeleteRangeResponse response_delete_range = 3;
  }
}
```

ينبغي عدم تفسير `ResponseHeader` المضمّن في كل استجابة داخلية بأي شكل من الأشكال.
إذا احتاج العملاء إلى الحصول على أحدث مراجعة، فعليهم دائمًا فحص `ResponseHeader` في المستوى الأعلى داخل `TxnResponse`.


## واجهة API للمراقبة {#watch-api}

توفر واجهة API الخاصة بـ `Watch` واجهة قائمة على الأحداث لمراقبة التغييرات على المفاتيح بشكل غير متزامن. تنتظر مراقبة etcd تغييرات المفاتيح عبر المراقبة المستمرة بدءًا من مراجعة معينة، حالية أو تاريخية، وتبث تحديثات المفاتيح مرة أخرى إلى العميل.

### الأحداث {#events}

يُمثَّل كل تغيير يطرأ على كل مفتاح برسائل `Event`. توفر رسالة `Event` بيانات التحديث ونوع التحديث معًا:

```protobuf
message Event {
  enum EventType {
    PUT = 0;
    DELETE = 1;
  }
  EventType type = 1;
  KeyValue kv = 2;
  KeyValue prev_kv = 3;
}
```

* Type - نوع الحدث. يشير النوع PUT إلى تخزين بيانات جديدة في المفتاح. ويشير DELETE إلى حذف المفتاح.
* KV - زوج KeyValue المرتبط بالحدث. يحتوي حدث PUT على زوج kv الحالي. يدل حدث PUT مع kv.Version=1 على إنشاء مفتاح. ويحتوي حدث DELETE على المفتاح المحذوف مع ضبط مراجعة تعديله على مراجعة الحذف.
* Prev_KV - زوج المفتاح-القيمة للمفتاح من المراجعة السابقة مباشرة للحدث. توفيرًا لعرض النطاق الترددي، لا يُملأ إلا إذا كانت المراقبة قد مكّنته صراحةً.

### تدفقات المراقبة {#watch-streams}

المراقبات طلبات طويلة الأمد تستخدم تدفقات gRPC لبث بيانات الأحداث. تدفق المراقبة ثنائي الاتجاه؛ يكتب العميل في التدفق لإنشاء المراقبات ويقرأ منه لتلقي أحداث المراقبة. يمكن لتدفق مراقبة واحد إجراء تعدد الإرسال لـ العديد من المراقبات المتميزة عن طريق وسم الأحداث بمعرّفات خاصة بكل مراقبة. يساعد تعدد الإرسال هذا في تقليل استخدام الذاكرة وتكلفة الاتصال على عنقود etcd الأساسي.

للاطلاع على الضمانات المتعلقة بأحداث المراقبة، يرجى قراءة [ضمانات واجهة etcd API][watch-api-guarantees].

ينشئ العميل مراقبة بإرسال `WatchCreateRequest` عبر تدفق يعيده `Watch`:

```protobuf
message WatchCreateRequest {
  bytes key = 1;
  bytes range_end = 2;
  int64 start_revision = 3;
  bool progress_notify = 4;

  enum FilterType {
    NOPUT = 0;
    NODELETE = 1;
  }
  repeated FilterType filters = 5;
  bool prev_kv = 6;
}
```

* Key, Range_End - نطاق المفاتيح المطلوب مراقبته.
* Start_Revision - مراجعة اختيارية لبدء المراقبة منها بشكل شامل. إذا لم تُعطَ، سيبث الأحداث بعد مراجعة ترويسة استجابة إنشاء المراقبة. يمكن مراقبة سجل الأحداث المتاح بالكامل بدءًا من مراجعة الضغط الأخيرة.
* Progress_Notify - عند ضبطه، ستتلقى المراقبة دوريًا WatchResponse بلا أحداث إذا لم تكن هناك أحداث حديثة. وهو مفيد عندما يرغب العملاء في استعادة مراقب انقطع اتصاله بدءًا من مراجعة حديثة معروفة. يحدد خادم etcd مدى تكرار إرسال الإشعارات بناءً على الحمل الحالي للخادم.
* Filters - قائمة بأنواع الأحداث المطلوب استبعادها على جانب الخادم.
* Prev_Kv - عند ضبطه، تتلقى المراقبة بيانات المفتاح-القيمة من قبل وقوع الحدث. وهذا مفيد لمعرفة البيانات التي تمت الكتابة فوقها.

استجابةً لـ `WatchCreateRequest` أو إذا كان هناك حدث جديد لمراقبة قائمة، يتلقى العميل `WatchResponse`:

```protobuf
message WatchResponse {
  ResponseHeader header = 1;
  int64 watch_id = 2;
  bool created = 3;
  bool canceled = 4;
  int64 compact_revision = 5;

  repeated mvccpb.Event events = 11;
}
```

* Watch_ID - معرّف المراقبة الذي تقابله الاستجابة.
* Created - يُضبط على true إذا كانت الاستجابة لطلب إنشاء مراقبة. ينبغي للعميل تخزين المعرّف وتوقع تلقي أحداث للمراقبة على التدفق. جميع الأحداث المرسلة إلى المراقب المنشأ ستكون لها watch_id نفسه.
* Canceled - يُضبط على true إذا كانت الاستجابة لطلب إلغاء مراقبة. لن تُرسل أي أحداث إضافية إلى المراقب الملغى.
* Compact_Revision - يُضبط على الحد الأدنى للمراجعة التاريخية المتاحة لـ etcd إذا حاول مراقب المراقبة عند مراجعة مضغوطة. يحدث ذلك عند إنشاء مراقب عند مراجعة مضغوطة أو عندما يعجز المراقب عن مواكبة تقدم مخزن المفتاح-القيمة. سيُلغى المراقب؛ وسيفشل إنشاء مراقبات جديدة بنفس start_revision.
* Events - قائمة بالأحداث الجديدة بالتسلسل تقابل معرّف المراقبة المعطى.

إذا رغب العميل في التوقف عن تلقي أحداث مراقبة ما، فإنه يصدر `WatchCancelRequest`:

```protobuf
message WatchCancelRequest {
   int64 watch_id = 1;
}
```

* Watch_ID - معرّف المراقبة المطلوب إلغاؤها بحيث لا تُنقل أحداث أخرى.

## واجهة API لعقود الإيجار {#lease-api}

عقود الإيجار (leases) آلية لاكتشاف حيوية العميل. يمنح العنقود عقود الإيجار مع مدة بقاء (TTL). ينتهي عقد الإيجار إذا لم يتلقَ عنقود etcd رسالة keepAlive خلال فترة TTL معينة.

لربط عقود الإيجار بمخزن المفتاح-القيمة، يمكن إرفاق كل مفتاح بعقد إيجار واحد على الأكثر. عندما ينتهي عقد إيجار أو يُلغى، ستُحذف جميع المفاتيح المرفقة بذلك العقد. يولّد كل مفتاح منتهٍ حدث حذف في سجل الأحداث.

### الحصول على عقود الإيجار {#obtaining-leases}

تُحصَّل عقود الإيجار من خلال نداء API باسم `LeaseGrant`، الذي يأخذ `LeaseGrantRequest`:

```protobuf
message LeaseGrantRequest {
  int64 TTL = 1;
  int64 ID = 2;
}
```

* TTL - مدة البقاء الاستشارية، بالثواني.
* ID - المعرّف المطلوب لعقد الإيجار. إذا ضُبط ID على 0، فسيختار etcd معرّفًا.

يتلقى العميل `LeaseGrantResponse` من نداء `LeaseGrant`:

```protobuf
message LeaseGrantResponse {
  ResponseHeader header = 1;
  int64 ID = 2;
  int64 TTL = 3;
}
```

* ID - معرّف عقد الإيجار للعقد الممنوح.
* TTL - هي مدة البقاء التي اختارها الخادم، بالثواني، لعقد الإيجار.

```protobuf
message LeaseRevokeRequest {
  int64 ID = 1;
}
```

* ID - معرّف عقد الإيجار المطلوب إلغاؤه. عندما يُلغى عقد الإيجار، تُحذف جميع المفاتيح المرفقة به.

### إبقاء عقود الإيجار حيّة {#keep-alives}

تُجدَّد عقود الإيجار باستخدام تدفق ثنائي الاتجاه يُنشأ بنداء API باسم `LeaseKeepAlive`. عندما يرغب العميل في تجديد عقد إيجار، يرسل `LeaseKeepAliveRequest` عبر التدفق:

```protobuf
message LeaseKeepAliveRequest {
  int64 ID = 1;
}
```

* ID - معرّف عقد الإيجار المطلوب إبقاؤه حيًا.

يستجيب تدفق الإبقاء الحي بـ `LeaseKeepAliveResponse`:

```protobuf
message LeaseKeepAliveResponse {
  ResponseHeader header = 1;
  int64 ID = 2;
  int64 TTL = 3;
}
```

* ID - عقد الإيجار الذي جُدّد بمدة TTL جديدة.
* TTL - مدة البقاء الجديدة، بالثواني، المتبقية لعقد الإيجار.
