## 物理マシン {#physical-machines}

GCEのn1-highcpu-2マシンタイプ

- etcdのデータディレクトリとしてマウントした専用ローカルSSD：1台
- OS用の専用低速ディスク：1台
- メモリー：1.8 GB
- CPU：2基

## etcdクラスター {#etcd-cluster}

etcd 2.2.0メンバー3つを、それぞれ別のマシンで実行します。

バージョンの詳細：

```
etcd Version: 2.2.0
Git SHA: e4561dd
Go Version: go1.5
Go OS/Arch: linux/amd64
```

## テスト {#testing}

etcdクラスターの外部に別のマシンを起動し、接続再利用のパッチを適用した[`hey` HTTPベンチマークツール](https://github.com/rakyll/hey)を実行して、各etcdクラスターメンバーにリクエストを送信します。パッチと測定手順の再現方法は、[ベンチマークの手順](https://github.com/etcd-io/etcd/tree/v2.3.8/hack/benchmark)を参照してください。

性能は100回のベンチマーク結果から算出します。

## 性能の変化 {#performance-changes}

- etcdがAPI呼び出しごとにメトリクスを記録するようになったため、ほとんどのシナリオで読み取りQPSがわずかに低下しているようです。得られる監視・デバッグ情報の広がりを考慮し、この小さな性能への影響は妥当なものと判断しました。

- クラスターのリーダーに対する書き込みQPSは、わずかに増加しているようです。これは、etcdのraft処理でメインループとエントリー適用ループを分離し、両者の間で発生していたいくつかのブロックを解消したためです。

- 全メンバーに対する書き込みQPSは、大幅に増加しているようです。フォロワーが最新のコミットインデックスをより早く受信し、提案をより速くコミットできるようになったためです。
