本文介绍横向扩展的方式，并通过实际客户的集群规模说明：Citus 既适用于 2～3 个节点的小型集群，也适用于大型多节点部署。

可以从单节点开始使用 Citus，并从一开始就采用分布式数据模型，为日后横向扩容做好准备。当 PostgreSQL 负载需要更大容量时，可向 Citus 集群添加工作节点，也可提升协调节点和工作节点的单机配置。Citus 可从 2～3 个节点扩展到处理 PB 级数据、每天数十亿行数据的大型部署。实际生产集群可超过 100 个节点，每天处理数十亿个事件，并提供亚秒级查询响应。

## 何时使用 Citus {#when-to-use-citus}

以下场景指南可帮助你判断 Citus 是否适合多租户 SaaS、实时分析或微服务负载，并在采用前了解相关取舍与限制。

### 多租户 SaaS 数据库 {#multitenant-saas-database}

大多数 B2B 应用的数据模型中已经有租户、客户或账户的概念。在这种模型中，一个数据库服务多个租户，各租户的数据彼此独立。

Citus 为这类负载提供完整的 SQL 支持，可将关系数据库横向扩展到超过 100,000 个租户。它还提供专门面向多租户的能力，例如通过租户隔离为大租户提供性能保障，以及通过参考表减少租户之间的重复数据。

利用这些能力，可将租户数据分散到多台机器，并方便地增加 CPU、内存与磁盘资源。多个租户共享同一数据库模式，既能高效利用硬件，也能简化数据库管理。

Citus 对多租户应用的优势包括：

- 为所有租户提供快速查询
- 在数据库中实现分片逻辑，无须在应用中实现
- 容纳超过单节点 PostgreSQL 容量的数据
- 横向扩展的同时保留 SQL
- 在高并发下保持性能
- 快速分析整个客户群的指标
- 随新客户注册而方便地扩容
- 隔离大客户与小客户的资源使用

### 实时分析 {#real-time-analytics}

Citus 支持对大规模数据集执行实时查询。这类查询常见于快速增长的事件系统或时序数据系统，例如：

- 具有亚秒级响应的分析仪表盘
- 对正在发生的事件执行探索性查询
- 大型数据集的归档与报表
- 用漏斗、细分和同期群查询分析会话

Citus 通过并行执行查询发挥作用，并随集群中工作节点数据库数量的增加而线性扩展。它对实时应用的优势包括：

- 数据量增长时仍保持亚秒级响应
- 实时分析新产生的事件与数据
- 并行执行 SQL 查询
- 横向扩展的同时保留 SQL
- 在高并发下保持性能
- 快速响应仪表盘查询
- 使用一个数据库，无须拼凑多种系统
- 使用 PostgreSQL 丰富的数据类型与扩展

### 微服务 {#microservices}

Citus 支持基于模式的分片，可将普通数据库模式分布到多台机器。这很适合典型的微服务架构：每项服务完全拥有自己的存储，无法与其他租户共用同一模式定义。

基于模式的分片更容易采用。创建新模式，并在服务中设置 `search_path`，即可开始使用。

Citus 对微服务的优势包括：

- 将各服务的状态分布存储并横向扩展，解决微服务的一个[主要难题](https://stackoverflow.blog/2020/11/23/the-macro-problem-with-microservices/)。
- 将微服务中的重要业务数据汇集到共享的分布式表，供分析使用。
- 在多台机器间均衡分配服务，提高硬件利用率。
- 将资源占用过多的服务隔离到专用节点。
- 分片模型容易理解。
- 能够快速接入。

### 注意事项与限制 {#considerations-and-limitations}

Citus 为 PostgreSQL 增加分布式能力，但并非能让所有负载横向扩展的通用替代品。要获得良好的集群性能，需要考虑数据模型、工具以及所用的 SQL 功能。

如果负载符合本文介绍的场景，但遇到了不支持的工具或查询，通常可以找到合适的变通方案。

### 不适合使用 Citus 的场景 {#when-citus-isnt-the-right-fit}

有些负载不需要强大的分布式数据库，另一些则需要在工作节点之间传输大量数据。前者使用 Citus 没有必要，后者则难以获得良好性能。例如：

- 始终不会超出单节点 PostgreSQL 容量的负载。
- 不需要实时写入或实时查询的离线分析。
- 不需要支持大量并发用户的分析应用。
- 返回大量 ETL 数据，而非汇总结果的查询。
