HAProxy позволяет запрашивать сведения о своём состоянии. Чаще всего для этого используется страница статистики HTTP. Она также предоставляет альтернативный формат вывода CSV для средств мониторинга. Тот же формат доступен через сокет Unix.

Статистика сгруппирована по категориям, называемым доменами, которые соответствуют различным компонентам HAProxy. Доступны два домена: proxy и resolvers. Если домен не указан, выбирается proxy. На странице HTTP выводится только статистика домена proxy.

## 9.1. Формат CSV {#section-9-1}

Статистику можно получать через сокет Unix или страницу HTTP. Оба способа поддерживают формат CSV с перечисленными ниже полями. Первая строка начинается с решётки ('#') и содержит по одному слову в каждом поле, отделённом запятой: это название столбца. Все строки начиная со второй используют обычный формат CSV с запятой в качестве разделителя и двойной кавычкой ('"') в качестве необязательного ограничителя текста, но только если текст неоднозначен (содержит кавычку или запятую). Двойная кавычка ('"') внутри текста удваивается ('""'); этот формат распознаётся большинством инструментов. Не вставляйте столбцы перед перечисленными, чтобы не нарушить работу инструментов с жёстко заданными позициями столбцов.

Для статистики прокси после имени каждого поля в скобках указаны типы объектов, у которых это поле может иметь значение: L (слушатели), F (фронтенды), B (бэкенды) и S (серверы). Существует фиксированный набор статических полей, всегда доступных в одном и том же порядке. Столбец с символом '-' обозначает конец статических полей; наличие и порядок следующих за ним полей не гарантируются.

Ниже перечислены статические поля домена статистики proxy:

```text
 0. pxname [LFBS]: имя прокси
 1. svname [LFBS]: имя службы (FRONTEND для фронтенда, BACKEND для бэкенда,
    произвольное имя для сервера/слушателя)
 2. qcur [..BS]: текущее число запросов в очереди. Для бэкенда — число
    запросов в очереди, которым ещё не назначен сервер.
 3. qmax [..BS]: максимальное значение qcur
 4. scur [LFBS]: текущее число сеансов
 5. smax [LFBS]: максимальное число сеансов
 6. slim [LFBS]: настроенный предел числа сеансов
 7. stot [LFBS]: суммарное число сеансов
 8. bin [LFBS]: полученные байты
 9. bout [LFBS]: отправленные байты
10. dreq [LFB.]: запросы, отклонённые по соображениям безопасности.
    - Для tcp — из-за совпадения с правилом tcp-request content.
    - Для http — из-за совпадения с правилом http-request или tarpit.
11. dresp [LFBS]: ответы, отклонённые по соображениям безопасности.
    - Для http — из-за совпадения с правилом http-request или
      "option checkcache".
12. ereq [LF..]: ошибки запросов. Некоторые возможные причины:
    - клиент преждевременно завершил соединение до отправки запроса.
    - ошибка чтения данных от клиента
    - тайм-аут клиента
    - клиент закрыл соединение
    - различные некорректные запросы от клиента.
    - запрос попал в ловушку соединений (tarpit).
13. econ [..BS]: число запросов, при попытке соединения которых с сервером
    бэкенда возникла ошибка. Для бэкенда показатель равен сумме показателей
    всех его серверов и ошибок соединения, не связанных с конкретным
    сервером (например, когда в бэкенде нет активных серверов).
14. eresp [..BS]: ошибки ответов. Здесь также учитывается srv_abrt.
    Некоторые другие ошибки:
    - ошибка записи в сокет клиента (не учитывается в статистике сервера)
    - ошибка применения фильтров к ответу.
15. wretr [..BS]: число повторных попыток соединения с сервером.
16. wredis [..BS]: число повторных направлений запроса на другой сервер.
    Значение для сервера показывает, сколько раз запрос был перенаправлен
    с этого сервера на другой.
17. status [LFBS]: состояние (UP/DOWN/NOLB/MAINT/MAINT(via)/MAINT(resolution)...)
18. weight [..BS]: суммарный эффективный вес (бэкенд), эффективный вес (сервер)
19. act [..BS]: число активных серверов (бэкенд), признак активности (сервер)
20. bck [..BS]: число резервных серверов (бэкенд), признак резервного сервера (сервер)
21. chkfail [...S]: число неудачных проверок. (Учитываются только проверки,
    завершившиеся неудачно, когда сервер доступен.)
22. chkdown [..BS]: число переходов UP->DOWN. Счётчик бэкенда учитывает
    переходы всего бэкенда в недоступное состояние, а не сумму счётчиков
    отдельных серверов.
23. lastchg [..BS]: число секунд с последнего перехода UP<->DOWN
24. downtime [..BS]: суммарное время простоя (в секундах). Для бэкенда это
    простой всего бэкенда, а не сумма времени простоя серверов.
25. qlimit [...S]: настроенное значение maxqueue для сервера; пустое поле,
    если значение равно 0 (по умолчанию, означает отсутствие ограничения)
26. pid [LFBS]: идентификатор процесса (0 для первого экземпляра, 1 для второго, ...)
27. iid [LFBS]: уникальный идентификатор прокси
28. sid [L..S]: идентификатор сервера (уникальный в пределах прокси)
29. throttle [...S]: текущий предел нагрузки сервера в процентах, если
    действует slowstart; пустое поле, если slowstart не действует.
30. lbtot [..BS]: общее число выборов сервера для новых сеансов или при
    повторном распределении. Счётчик сервера показывает, сколько раз
    был выбран этот сервер.
31. tracked [...S]: идентификатор прокси/сервера, если включено отслеживание.
32. type [LFBS]: (0=фронтенд, 1=бэкенд, 2=сервер, 3=сокет/слушатель)
33. rate [.FBS]: число сеансов в секунду за последнюю истёкшую секунду
34. rate_lim [.F..]: настроенный предел числа новых сеансов в секунду
35. rate_max [.FBS]: максимальное число новых сеансов в секунду
36. check_status [...S]: состояние последней проверки работоспособности, одно из:
       UNK     -> неизвестно
       INI     -> инициализация
       SOCKERR -> ошибка сокета
       L4OK    -> проверка уровня 4 пройдена, проверки верхних уровней отключены
       L4TOUT  -> тайм-аут уровня 1-4
       L4CON   -> проблема соединения на уровне 1-4, например
                  "Connection refused" (tcp rst) или "No route to host" (icmp)
       L6OK    -> проверка уровня 6 пройдена
       L6TOUT  -> тайм-аут уровня 6 (SSL)
       L6RSP   -> некорректный ответ уровня 6 — ошибка протокола
       L7OK    -> проверка уровня 7 пройдена
       L7OKC   -> проверка уровня 7 пройдена условно, например 404 при
                  disable-on-404
       L7TOUT  -> тайм-аут уровня 7 (HTTP/SMTP)
       L7RSP   -> некорректный ответ уровня 7 — ошибка протокола
       L7STS   -> ошибка ответа уровня 7, например HTTP 5xx
    Примечание: если проверка сейчас выполняется, выводится последнее
    известное состояние с префиксом "* ", например "* L7OK".
37. check_code [...S]: код уровня 5-7, если доступен
38. check_duration [...S]: длительность последней проверки работоспособности в ms
39. hrsp_1xx [.FBS]: ответы http с кодом 1xx
40. hrsp_2xx [.FBS]: ответы http с кодом 2xx
41. hrsp_3xx [.FBS]: ответы http с кодом 3xx
42. hrsp_4xx [.FBS]: ответы http с кодом 4xx
43. hrsp_5xx [.FBS]: ответы http с кодом 5xx
44. hrsp_other [.FBS]: ответы http с другими кодами (ошибка протокола)
45. hanafail [...S]: сведения о неудачных проверках работоспособности
46. req_rate [.F..]: число запросов HTTP в секунду за последнюю истёкшую секунду
47. req_rate_max [.F..]: максимальное наблюдавшееся число запросов HTTP в секунду
48. req_tot [.FB.]: общее число полученных запросов HTTP
49. cli_abrt [..BS]: число передач данных, прерванных клиентом
50. srv_abrt [..BS]: число передач данных, прерванных сервером
    (учитывается в eresp)
51. comp_in [.FB.]: число байтов ответов HTTP, переданных механизму сжатия
52. comp_out [.FB.]: число байтов ответов HTTP на выходе механизма сжатия
53. comp_byp [.FB.]: число байтов, прошедших в обход механизма сжатия HTTP
    (ограничение CPU/BW)
54. comp_rsp [.FB.]: число сжатых ответов HTTP
55. lastsess [..BS]: число секунд с момента назначения последнего сеанса
    серверу/бэкенду
56. last_chk [...S]: содержимое последней проверки работоспособности или текст ошибки
57. last_agt [...S]: содержимое последней проверки агента или текст ошибки
58. qtime [..BS]: среднее время в очереди в ms за последние 1024 запроса
59. ctime [..BS]: среднее время соединения в ms за последние 1024 запроса
60. rtime [..BS]: среднее время ответа в ms за последние 1024 запроса
    (0 для TCP)
61. ttime [..BS]: средняя общая длительность сеанса в ms за последние 1024
    запроса
62. agent_status [...S]: состояние последней проверки агента, одно из:
       UNK     -> неизвестно
       INI     -> инициализация
       SOCKERR -> ошибка сокета
       L4OK    -> проверка уровня 4 пройдена, проверки верхних уровней отключены
       L4TOUT  -> тайм-аут уровня 1-4
       L4CON   -> проблема соединения на уровне 1-4, например
                  "Connection refused" (tcp rst) или "No route to host" (icmp)
       L7OK    -> агент сообщил "up"
       L7STS   -> агент сообщил "fail", "stop" или "down"
63. agent_code [...S]: числовой код от агента, если есть (пока не используется)
64. agent_duration [...S]: длительность последней проверки в ms
65. check_desc [...S]: краткое понятное человеку описание check_status
66. agent_desc [...S]: краткое понятное человеку описание agent_status
67. check_rise [...S]: параметр сервера "rise", используемый проверками
68. check_fall [...S]: параметр сервера "fall", используемый проверками
69. check_health [...S]: значение проверки работоспособности сервера от 0 до rise+fall-1
70. agent_rise [...S]: параметр агента "rise", обычно 1
71. agent_fall [...S]: параметр агента "fall", обычно 1
72. agent_health [...S]: параметр работоспособности агента от 0 до rise+fall-1
73. addr [L..S]: address:port или "unix". Адрес IPv6 заключён в скобки.
74: cookie [..BS]: значение cookie сервера или имя cookie бэкенда
75: mode [LFBS]: режим прокси (tcp, http, health, unknown)
76: algo [..B.]: алгоритм балансировки нагрузки
77: conn_rate [.F..]: число соединений за последнюю истёкшую секунду
78: conn_rate_max [.F..]: наибольшее известное значение conn_rate
79: conn_tot [.F..]: суммарное число соединений
80: intercepted [.FB.]: суммарное число перехваченных запросов (monitor, stats)
81: dcon [LF..]: запросы, отклонённые правилами "tcp-request connection"
82: dses [LF..]: запросы, отклонённые правилами "tcp-request session"
83: wrew [LFBS]: суммарное число предупреждений о неудачной перезаписи заголовков
84: connect [..BS]: суммарное число попыток установления соединения

104. sess_other [.F..]: общее число сеансов, отличных от HTTP, с запуска процесса

107. h3_sess [.F..]: общее число сеансов HTTP/3 с запуска процесса
108. req_other [.F..]: общее число сеансов, отличных от HTTP, обработанных
```

## 9.2. Типизированный формат вывода {#section-9-2}

Команды "show info" и "show stat" поддерживают режим, в котором каждое выводимое значение сопровождается типом и сведениями, достаточными для определения способа его агрегации по процессам и характера изменения.

Во всех случаях каждое значение выводится в отдельной строке, а все сведения разделены на поля двоеточиями (':').

Первый столбец обозначает выводимый объект или метрику. Его формат зависит от команды, формирующей вывод, и в этом разделе не рассматривается. Обычно это последовательность идентификаторов и имён полей.

Второй столбец содержит 4 символа, обозначающих соответственно источник, характер, область действия и сохранность выводимого значения. Первый символ (источник) указывает, откуда извлечено значение. Возможны следующие символы:

```text
M   Значение является метрикой. Оно действительно в определённый момент
    времени и может меняться в зависимости от своего характера.

S   Значение обозначает состояние. Это дискретное значение, которое по
    определению нельзя агрегировать. Это может быть состояние сервера
    ("UP" или "DOWN"), PID процесса и т. д.

K   Значение является ключом сортировки. Это идентификатор, позволяющий
    группировать значения, поскольку он уникален в своём классе. Все
    внутренние идентификаторы являются ключами. Некоторые имена могут
    считаться ключами, если они уникальны (например, имя фронтенда уникально).
    Обычно ключи берутся из конфигурации, хотя некоторые назначаются
    автоматически. В большинстве случаев ключи можно считать эквивалентом
    конфигурации.

C   Значение взято из конфигурации. Некоторые значения конфигурации полезны
    в выводе, например предел числа одновременных соединений или имя cookie.
    По определению эти значения одинаковы во всех процессах, запущенных
    с одним и тем же файлом конфигурации.

P   Значение задано самим продуктом. Таких значений очень мало; чаще всего
    они сообщают название продукта, версию и дату выпуска. Эти элементы
    также одинаковы во всех процессах.
```

Второй символ (характер) обозначает характер информации в поле, чтобы агрегатор мог выбрать операцию для объединения нескольких значений. Возможны следующие символы:

```text
A   Значение обозначает время с момента последнего события. Оно несколько
    отличается от длительности: прошедшее время вычисляется автоматически
    на основе текущей даты. Типичный пример — время с последнего сеанса
    на сервере. Такие значения обычно агрегируют, выбирая минимум, и их
    не требуется хранить.

a   Значение уже усреднено. К этому типу относятся среднее время ответа
    и веса серверов. Средние значения обычно можно усреднять по процессам.

C   Значение является накопительным счётчиком. Такие показатели постоянно
    растут до переполнения. Некоторым протоколам мониторинга требуется
    различать счётчик и показатель текущего значения, чтобы сообщать разные
    типы. Обычно счётчики можно просто суммировать, поскольку они отражают
    события или объёмы. Примеры метрик такого типа — число соединений
    или число байтов.

D   Значение обозначает длительность состояния. Применений немного;
    чаще всего это длительность последней проверки работоспособности
    и время недоступности сервера. Длительности обычно не суммируют;
    чаще всего для расчёта SLA сохраняют максимальное значение.

G   Значение является показателем текущего значения (gauge): измерением
    в определённый момент времени. К этому типу относятся потребление памяти
    и текущее число активных соединений. При агрегации метрики этого типа
    обычно суммируют.

L   Значение обозначает ограничение (обычно заданное в конфигурации).
    Ограничения по своей природе труднее агрегировать, поскольку они
    относятся к конкретному месту измерения. В некоторых ситуациях их
    можно суммировать или учитывать отдельно.

M   Значение обозначает максимум. Обычно оно относится к показателю
    текущего значения и сохраняет наибольшее известное значение. Пример —
    максимальное число одновременных соединений за время работы продукта.
    Для правильной агрегации максимумов следует выводить диапазон от
    наибольшего из всех максимумов до их суммы: невозможно узнать,
    были ли эти максимумы достигнуты одновременно.

m   Значение обозначает минимум. Обычно оно относится к показателю
    текущего значения и сохраняет наименьшее известное значение. Пример —
    минимальное количество свободных пулов памяти за время работы продукта.
    Для правильной агрегации минимумов следует выводить диапазон от
    наименьшего из всех минимумов до их суммы: невозможно узнать,
    были ли эти минимумы достигнуты одновременно.

N   Значение обозначает имя и потому является строкой. Оно служит для
    вывода имён прокси, серверов и cookie. Имена берутся из конфигурации
    или ключей; предполагается, что они одинаковы во всех процессах.

O   Значение является произвольным текстом. К этому типу относятся вывод
    различных команд, результаты проверок работоспособности и описания узлов.

R   Значение обозначает интенсивность событий. Это измерение в определённый
    момент времени. Оно очень похоже на показатель текущего значения,
    но получатель знает, что оно меняется медленно, и может решить не хранить
    все значения. Пример такой метрики — измеренное число соединений
    в секунду. При агрегации метрики этого типа обычно суммируют.

T   Значение обозначает дату или время. К этому типу относилось бы поле
    с текущей датой. Способ агрегации таких данных зависит от реализации.
    Пока ни одно поле не использует этот тип.
```

Третий символ (область действия) указывает, к какой области относится значение. Одни элементы относятся к процессу, другие — к конфигурации или системе. Это различие важно для определения того, следует ли при агрегации оставить единственное значение или объединить несколько значений. В настоящее время поддерживаются следующие символы:

```text
C   Значение действительно для всего кластера узлов — совокупности узлов,
    взаимодействующих по протоколу peers. Пример — число записей в таблице
    привязок, реплицируемой на другие узлы peers. В настоящее время ни одна
    метрика не использует эту область действия.

P   Значение действительно только для процесса, который его сообщает.
    Большинство метрик используют эту область действия.

S   Значение действительно для всей службы — совокупности процессов,
    запущенных вместе с одним и тем же файлом конфигурации. Все метрики,
    полученные из конфигурации, используют эту область действия.
    Некоторые другие метрики общих ресурсов также могут её использовать
    (например, статистика общего кэша SSL).

s   Значение действительно для всей системы, например имя узла системы,
    текущая дата или использование ресурсов. В настоящее время ни одна
    метрика не использует эту область действия.
```

Четвёртый символ (сохранность) указывает, теряется или сохраняется значение метрики при перезагрузках конфигурации. Ожидаются следующие символы:

```text
V   Метрика непостоянная, поскольку она локальна для текущего процесса,
    и её значение теряется при перезагрузке конфигурации.

P   Метрика постоянная, поскольку может совместно использоваться другими
    процессами, благодаря чему значение сохраняется при перезагрузках.
```

Потребителям этих данных обычно достаточно указанных 4 символов, чтобы определить, как правильно представлять агрегированную информацию по нескольким процессам.

Следующий, третий столбец указывает тип поля: "s32" (знаковое 32-разрядное целое), "s64" (знаковое 64-разрядное целое), "u32" (беззнаковое 32-разрядное целое), "u64" (беззнаковое 64-разрядное целое) или "str" (строка). Для правильного чтения значения необходимо знать его тип до разбора. Например, строка, содержащая только цифры, остаётся строкой, а не целым числом (например, код ошибки, извлечённый при проверке).

Четвёртый столбец содержит само значение, закодированное в соответствии с его типом. Строки выводятся без изменений сразу после двоеточия, без начального пробела. Если строка содержит двоеточие, оно выводится как обычно. Поэтому нельзя просто разбивать весь вывод по двоеточиям: некоторые результаты проверок или адреса серверов могут оказаться усечёнными.

## 9.3. Команды сокета Unix {#section-9-3}

По умолчанию сокет статистики отключён. Для его включения необходимо добавить строку в секцию global конфигурации HAProxy. Рекомендуется добавить и вторую строку, задающую больший тайм-аут: это удобно при вводе команд вручную:

```text
global
    stats socket /var/run/haproxy.sock mode 600 level admin
    stats timeout 2m
```

Повторив строку, можно добавить несколько сокетов статистики и настроить их на прослушивание порта TCP вместо сокета UNIX. По умолчанию это никогда не делается, поскольку это опасно, но в некоторых ситуациях может быть полезно:

```text
global
    stats socket /var/run/haproxy.sock mode 600 level admin
    stats socket ipv4@192.168.0.1:9999 level admin
    stats timeout 2m
```

Для доступа к сокету требуется внешняя утилита, например "socat". Socat — универсальное средство соединения разных источников и приёмников. Здесь она используется для подключения терминалов к сокету либо для подключения к нему пары каналов stdin/stdout из скриптов. Основные два варианта синтаксиса:

```shell
# socat /var/run/haproxy.sock stdio
# socat /var/run/haproxy.sock readline
```

Первый вариант используется в скриптах. Вывод скрипта можно направить в HAProxy, а вывод HAProxy — в другой скрипт. Это удобно, например, для получения счётчиков или следов атак.

Второй вариант полезен только для ввода команд вручную. Его преимущество — обработка терминала библиотекой readline, поддерживающей редактирование строк и историю. Это очень удобно при повторном вводе команд (например, для наблюдения за счётчиком).

Сокет поддерживает три режима работы:

- неинтерактивный, без приглашения
- интерактивный, без приглашения
- интерактивный с приглашением

При подключении socat к сокету по умолчанию используется неинтерактивный режим. В нём можно отправить одну строку: она обрабатывается целиком, ответы отправляются обратно, а после завершения ответа соединение закрывается. Этот режим используют скрипты и средства мониторинга. В нём можно отправить несколько команд, разделив их точкой с запятой (';'). Например:

```shell
# echo "show info;show stat;show table" | socat /var/run/haproxy stdio
```

Если в команде требуется точка с запятой или обратная косая черта (например, в значении), перед ней обязательно ставится обратная косая черта ('&#92;').

Интерактивный режим позволяет отправлять новые команды после завершения команд из предыдущих строк. Есть два варианта: без приглашения, работающий как неинтерактивный режим, но ожидающий новую команду вместо закрытия сокета, и с приглашением ('\>') в начале строки. Для более сложных инструментов предпочтителен интерактивный режим, а для ручной работы — режим с приглашением.

Режим меняется командой "prompt". По умолчанию она переключает интерактивный режим и режим с приглашением. Ввод "prompt" в интерактивном режиме включает приглашение. Команда также может принимать обозначение конкретного режима:

- "n": неинтерактивный режим (одна команда и выход)
- "i": интерактивный режим (несколько команд, без приглашения)
- "p": режим с приглашением (несколько команд с приглашением)

Поскольку по умолчанию действует неинтерактивный режим, для его переключения "prompt" должна быть первой командой; иначе предыдущая команда приведёт к закрытию соединения. При переключении в неинтерактивный режим соединение закрывается после выполнения всех команд той же строки.

Поэтому при отладке вручную работу часто начинают с команды "prompt":

```haproxy
# socat /var/run/haproxy readline
prompt
```

> show info ...

Интерактивным инструментам может быть удобнее начинать с "prompt i", чтобы включить интерактивный режим без приглашения.

В приглашении также можно показывать время работы процесса. Команда "prompt timed" включает приглашение и переключает отображение времени. Время работы выводится в формате "d:hh:mm:ss", где "d" — число дней, а "hh", "mm" и "ss" — число часов, минут и секунд соответственно, по две цифры каждое:

```haproxy
# socat /var/run/haproxy readline
prompt timed
```

[23:03:34:39]\> show version 2.8-dev9-e5e622-18

[23:03:34:41]\> quit

Если приглашение со временем включено в CLI главного процесса, оно показывает время работы выбранного процесса. Это работает для главного процесса, текущего рабочего процесса и старого рабочего процесса:

```shell
master> prompt timed
[0:00:00:50] master> show proc
(...)
[0:00:00:58] master> @!11955     <-- master, switch to current worker
[0:00:01:03] 11955> @!11942      <-- current worker, switch to older worker
[0:00:02:17] 11942> @            <-- older worker, switch back to master
[0:00:01:10] master>
```

Поскольку за один раз можно передать несколько команд, HAProxy отмечает конец вывода каждой команды пустой строкой и гарантирует, что сами команды не выводят пустых строк. Поэтому скрипт легко разбирает вывод, даже если несколько команд переданы подряд в одной строке.

Некоторые команды принимают необязательную полезную нагрузку. Чтобы добавить её, первая строка команды должна заканчиваться последовательностью "\<\<&#92;n". Следующие строки считаются полезной нагрузкой; их может быть столько, сколько требуется. Для подтверждения команды с полезной нагрузкой ввод должен завершаться пустой строкой.

Маркер полезной нагрузки можно настроить, изменив способ определения её конца. Чтобы завершать полезную нагрузку чем-либо, кроме пустой строки, между '\<\<' и '&#92;n' можно задать собственный маркер. В дополнение к '\<\<' допускается не более 64 символов, иначе последовательность не будет распознана как начало полезной нагрузки. Этого должно хватать для случайных маркеров. Например, для передачи файла PEM с пустыми строками и комментариями:

```haproxy
# echo -e "set ssl cert common.pem <<%EOF%\n$(cat common.pem)\n%EOF%\n" | \
socat /var/run/haproxy.stat -
```

Есть ограничения: последовательность "\<\<" не должна примыкать к последнему слову строки. Длина командной строки не должна превышать tune.bufsize, включая маркер начала полезной нагрузки, но исключая саму полезную нагрузку. Её размер по умолчанию ограничен 128KB. Это можно изменить глобальным параметром "tune.cli.max-payload-size", соблюдая осторожность. Маркер конца полезной нагрузки также входит в это ограничение.

При вводе полезной нагрузки в интерактивном режиме приглашение меняется с "\> " на "+ ".

Важно понимать: если на одних и тех же сокетах запущено несколько процессов HAProxy, запрос может принять любой из них, и он выведет собственную статистику.

Ниже перечислены команды, которые сейчас поддерживает сокет статистики. В ответ на неизвестную команду HAProxy выводит справку со всеми поддерживаемыми командами. Некоторые команды имеют более сложный синтаксис; при ошибке обычно поясняется, какая часть команды некорректна.

Некоторым командам нужен более высокий уровень привилегий. При недостаточных привилегиях возвращается ошибка "Permission denied". Подробнее см. описание опции "level" в строках ключевого слова "bind" в руководстве по конфигурации.

<a id="entry-9-3-acme-renew"></a>

**`acme renew <certificate>`**

```haproxy
acme renew <certificate>
```

Запускает задачу выпуска сертификата ACME с указанным именем сертификата. Сертификат должен быть связан с секцией acme; см. раздел [12.8](/ru/haproxy/other-sections/#section-12-8) "ACME" руководства по конфигурации. См. также "acme status".

<a id="entry-9-3-acme-status"></a>

**`acme status`**

```haproxy
acme status
```

Показывает состояние всех сертификатов, настроенных с использованием ACME.

Команда выводит следующие поля, разделённые табуляцией:

- Имя сертификата, заданное в HAProxy
- Секция acme, используемая в конфигурации
- Состояние задачи acme: "Running", "Scheduled" или "Stopped"
- Дата окончания срока действия сертификата в UTC в формате ISO8601
- Время до окончания срока действия (0d, если срок истёк)
- Запланированная дата для сертификата в UTC в формате ISO8601
- Время до запланированного запуска (0d в состоянии Running)

Пример:

```shell
$ echo "@1; acme status" | socat /tmp/master.sock - | column -t -s $'\t'
# certificate   section  state      expiration date (UTC)  expires in        scheduled date (UTC)  scheduled in
ecdsa.pem       LE       Running    2020-01-18T09:31:12Z   0d 0h00m00s       2020-01-15T21:31:12Z  0d 0h00m00s
foobar.pem.rsa  LE       Scheduled  2025-08-04T11:50:54Z   89d 23h01m13s     2025-07-27T23:50:55Z  82d 11h01m14s
```

<a id="entry-9-3-add-acl"></a>

**`add acl [@<ver>] <acl> <pattern>`**

```haproxy
add acl [@<ver>] <acl> <pattern>
```

Добавляет запись в acl `<acl>`. `<acl>` — это \#`<id>` или `<name>`, возвращённые командой "show acl". Команда не проверяет, существует ли запись. Записи добавляются в текущую версию ACL, если конкретная версия не указана через "@`<ver>`". Номер версии должен быть заранее выделен командой "prepare acl" и находиться в диапазоне от "curr_ver" до "next_ver" в выводе "show acl". Записи с явно заданным номером версии не будут участвовать в сопоставлении до выполнения операции "commit acl". Однако их можно просматривать командой "show acl @`<ver>`" и очищать командой "clear acl @`<ver>`". Эту команду нельзя использовать, если ссылка `<acl>` является именем, которое также используется для карты. В этом случае необходимо использовать команду "add map".

<a id="entry-9-3-add-backend"></a>

**`add backend <name> from <defproxy> [mode <mode>] [guid <guid>]`**

```haproxy
add backend <name> from <defproxy> [mode <mode>] [guid <guid>]
```

Создаёт новый бэкенд-прокси с именем `<name>`.

Можно создавать только прокси TCP или HTTP. Все настройки наследуются от экземпляра прокси defaults `<defproxy>`. По умолчанию режим бэкенда обязательно задаётся одноимённым аргументом, если только он уже не указан явно в `<defproxy>`. При необходимости также можно передать необязательный аргумент GUID.

Серверы можно добавлять командой "add server". Бэкенд создаётся в неопубликованном состоянии. Когда он будет готов принимать трафик, команда "publish backend" делает новый экземпляр доступным.

Можно использовать любые именованные прокси defaults, если они удовлетворяют тем же правилам наследования, которые действуют при разборе конфигурации. Однако есть исключения, например режим, отличный от TCP и HTTP.

Команда имеет ограниченный доступ и может выполняться только через сокеты, настроенные с уровнем "admin".

<a id="entry-9-3-add-map"></a>

**`add map [@<ver>] <map> <key> <value>`**

```haproxy
add map [@<ver>] <map> <key> <value>
add map [@<ver>] <map> <payload>
```

Добавляет запись в карту `<map>`, связывая значение `<value>` с ключом `<key>`. Команда не проверяет, существует ли запись. В основном она используется для заполнения карты после операции "clear" или "prepare". Записи добавляются в текущую версию ACL, если конкретная версия не указана через "@`<ver>`". Номер версии должен быть заранее выделен командой "prepare acl" и находиться в диапазоне от "curr_ver" до "next_ver" в выводе "show acl". Записи с явно заданным номером версии не будут участвовать в сопоставлении до выполнения операции "commit map". Однако их можно просматривать командой "show map @`<ver>`" и очищать командой "clear acl @`<ver>`". Если указанная карта также используется как ACL, ACL сопоставляет только часть `<key>` и игнорирует часть `<value>`. Синтаксис с полезной нагрузкой позволяет добавлять несколько пар ключ/значение, вводя их в отдельных строках. В каждой новой строке первое слово является ключом, а остаток строки считается значением, которое может содержать пробелы.

Пример:

```shell
# socat /tmp/sock1 -
prompt

> add map #-1 <<
+ key1 value1
+ key2 value2 with spaces
+ key3 value3 also with spaces
+ key4 value4

>
```

<a id="entry-9-3-add-server"></a>

**`add server <backend>/<server> [args]*`**

```haproxy
add server <backend>/<server> [args]*
```

Создаёт новый сервер, связанный с бэкендом `<backend>`.

Имя `<server>` не должно уже использоваться в бэкенде. Для бэкенда действует особое ограничение: он должен использовать динамический алгоритм балансировки нагрузки. Поведение сервера можно настроить частью ключевых слов директивы server файла конфигурации (их список выводит "add server help"). Настройки возможной директивы 'default-server' в том же бэкенде не наследуются.

В настоящее время динамический сервер статически инициализируется методом init-addr "none". Это означает, что при указании FQDN в качестве адреса разрешение имени не выполняется, хотя запрос на создание сервера будет признан корректным.

Для поддержки перезагрузки конфигурации сервер, созданный через CLI, следует также вручную добавить в соответствующий файл конфигурации HAProxy. Динамический сервер, отсутствующий в конфигурации, после её перезагрузки не восстанавливается.

Динамический сервер может использовать ключевое слово "track" для отслеживания состояния проверок другого сервера из конфигурации. Однако отслеживать другой динамический сервер нельзя. Это обеспечивает согласованность цепочки отслеживания даже при удалении динамических серверов.

Ключевое слово "check" включает поддержку проверок работоспособности. По умолчанию сама проверка отключена, и её необходимо включить отдельно от сервера командой "enable health". Для проверок агента используются ключевое слово "agent-check" и команда "enable agent". В этом случае агент может активировать сервер в зависимости от сообщённого состояния без явной команды "enable server". Поэтому удаление динамического сервера с проверкой агента требует особой осторожности. Сначала следует отключить агент командой "disable agent", чтобы перед удалением можно было перевести сервер в обязательный режим обслуживания.

При большом числе динамических серверов можно достичь предела числа файловых дескрипторов (fd). В этом случае см. документацию глобального ключевого слова "u-limit".

Выводит ключевые слова, поддерживаемые для динамических серверов текущей версией HAProxy. Их синтаксис аналогичен строке server в файле конфигурации; подробности приведены в документации каждого ключевого слова.

<a id="entry-9-3-add-ssl-ca-file"></a>

**`add ssl ca-file <cafile> <payload>`**

```haproxy
add ssl ca-file <cafile> <payload>
```

Добавляет новый сертификат в ca-file. Команда полезна, когда достигнут предел размера буфера CLI и требуется добавить несколько сертификатов. Вместо "set" со всеми сертификатами можно добавлять их по одному. Команда "set ssl ca-file" сбрасывает содержимое ca-file.

Пример:

```text
echo -e "set ssl ca-file cafile.pem <<\n$(cat rootCA.crt)\n" | \

echo -e "add ssl ca-file cafile.pem <<\n$(cat intermediate1.crt)\n" | \
socat /var/run/haproxy.stat -
echo -e "add ssl ca-file cafile.pem <<\n$(cat intermediate2.crt)\n" | \
socat /var/run/haproxy.stat -
echo "commit ssl ca-file cafile.pem" | socat /var/run/haproxy.stat -
```

<a id="entry-9-3-add-ssl-crt-list"></a>

**`add ssl crt-list <crtlist> <certificate>`**

```haproxy
add ssl crt-list <crtlist> <certificate>
add ssl crt-list <crtlist> <payload>
```

Добавляет сертификат в crt-list. Команду также можно использовать для каталогов, поскольку теперь они загружаются так же, как crt-list. Имя сертификата можно передать параметром; чтобы использовать опции SSL или фильтры, вместо этого необходимо передать строку crt-list как полезную нагрузку. В полезной нагрузке поддерживается только одна строка crt-list. Команда загружает сертификат для всех строк bind, использующих этот crt-list. Для передачи нового сертификата в HAProxy необходимо использовать команды "new ssl cert" и "set ssl cert".

Пример:

```shell
$ echo "new ssl cert foobar.pem" | socat /tmp/sock1 -
$ echo -e "set ssl cert foobar.pem <<\n$(cat foobar.pem)\n" | socat
/tmp/sock1 -
$ echo "commit ssl cert foobar.pem" | socat /tmp/sock1 -
$ echo "add ssl crt-list certlist1 foobar.pem" | socat /tmp/sock1 -

$ echo -e 'add ssl crt-list certlist1 <<\nfoobar.pem [allow-0rtt] foo.bar.com
!test1.com\n' | socat /tmp/sock1 -
```

<a id="entry-9-3-add-ssl-ech"></a>

**`add ssl ech <bind> <payload>`**

```haproxy
add ssl ech <bind> <payload>
```

Добавляет ключ ECH в строку `<bind>`. Полезная нагрузка должна быть в формате PEM для ECH.
(<https://datatracker.ietf.org/doc/html/draft-farrell-tls-pemesni>)

Формат строки bind: `<frontend>`/@`<filename>`:`<linenum>` (пример: frontend1/@haproxy.conf:19) или `<frontend>`/`<name>`, если строке bind назначено имя ключевым словом "name".

Требуется версия OpenSSL с поддержкой ECH, а HAProxy должен быть собран с USE_ECH=1. Команда поддерживается только в соединении CLI, работающем в экспериментальном режиме (см. "experimental-mode on").

См. также "show ssl ech" и "ech" в [разделе 5.1](/ru/haproxy/bind-and-server-options/#section-5-1) руководства по конфигурации.

Пример:

```shell
$ openssl ech -public_name foobar.com -out foobar3.com.ech
$ echo -e "experimental-mode on; add ssl ech frontend1/@haproxy.conf:19 <<%EOF%\n$(cat foobar3.com.ech)\n%EOF%\n" | \
  socat /tmp/haproxy.sock -
added a new ECH config to frontend1
```

<a id="entry-9-3-clear-counters"></a>

Также сбрасываются внутренние счётчики активности, выводимые командой "show activity". Это позволяет получить чистые счётчики после инцидента без перезапуска и без сброса счётчиков трафика. По умолчанию очищается только текущая версия ACL (используемая для сопоставления). Однако можно указать другую версию, поставив её номер после '@'.

Удаляет все записи из карты `<map>`. `<map>` — это \#`<id>` или `<name>`, возвращённые командой "show map". Если ссылка `<map>` является именем, общим с acl, этот acl также очищается. По умолчанию очищается только текущая версия карты (используемая для сопоставления). Однако можно указать другую версию, поставив её номер после '@'.

<a id="entry-9-3-clear-table"></a>

**`clear table <table> [ data.<type> <operator> <value> ] | [ key <key> ] |`**

```haproxy
clear table <table> [ data.<type> <operator> <value> ] | [ key <key> ] |
                    [ ptr <ptr> ]
```

Удаляет записи из таблицы привязок `<table>`.

Обычно команда используется для разблокировки пользователей, сообщающих о необоснованном отказе в доступе к службе. Ею также можно удалить записи привязки к серверу, который предстоит заменить (подробности см. ниже в описании "show table"). Иногда удаление записи отклоняется, поскольку она в данный момент отслеживается сеансом. Обычно достаточно повторить попытку через несколько секунд, когда сеанс завершится.

Если аргументы опций не заданы, удаляются все записи.

При использовании формы "data." удаляются записи, соответствующие фильтру по сохранённым данным (см. "stick-table" в разделе 4.2). В `<type>` необходимо указать тип сохраняемых данных; этот тип должен храниться в таблице, иначе возвращается ошибка. Оператор `<operator>` определяет сравнение данных с 64-разрядным целым `<value>`. Операторы те же, что в ACL:

    - eq: записи, данные которых равны этому значению
    - ne: записи, данные которых не равны этому значению
    - le: записи, данные которых меньше или равны этому значению
    - ge: записи, данные которых больше или равны этому значению
    - lt: записи, данные которых меньше этого значения
    - gt: записи, данные которых больше этого значения

При использовании формы key удаляется запись `<key>`. Ключ должен иметь тот же тип, что и таблица; в настоящее время поддерживаются только IPv4, IPv6, целое число и строка.

При использовании формы ptr удаляется запись `<ptr>`. `<ptr>` задаётся в виде 0xffff и должен соответствовать адресу, возвращённому предыдущей командой "show table". Поиск записи по указателю полезен, если найти её по ключу невозможно из-за пустого ключа или символов, несовместимых с CLI.

Если data.`<type>` имеет тип массива, для доступа к определённому индексу можно использовать "[]", например: data.gpt[1]

Пример:

```shell
    $ echo "show table http_proxy" | socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:2
>>> 0x80e6a4c: key=127.0.0.1 use=0 exp=3594729 gpc0=0 conn_rate(30000)=1 \
      bytes_out_rate(60000)=187
>>> 0x80e6a80: key=127.0.0.2 use=0 exp=3594740 gpc0=1 conn_rate(30000)=10 \
      bytes_out_rate(60000)=191
>>> 0x80e6b40: key=127.0.0.3 use=0 exp=3594743 gpc0=2 conn_rate(30000)=10 \
      bytes_out_rate(60000)=200

    $ echo "clear table http_proxy key 127.0.0.1" | socat stdio /tmp/sock1

    $ echo "show table http_proxy" | socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:1
>>> 0x80e6a80: key=127.0.0.2 use=0 exp=3594740 gpc0=1 conn_rate(30000)=10 \
>>> 0x80e6b40: key=127.0.0.3 use=0 exp=3594743 gpc0=2 conn_rate(30000)=10 \
      bytes_out_rate(60000)=200
      bytes_out_rate(60000)=191
    $ echo "clear table http_proxy data.gpc0 eq 1" | socat stdio /tmp/sock1
    $ echo "show table http_proxy" | socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:1
>>> 0x80e6b40: key=127.0.0.3 use=0 exp=3594743 gpc0=2 conn_rate(30000)=10 \
      bytes_out_rate(60000)=200

    $ echo "clear table http_proxy ptr 0x80e6b40" | socat stdio /tmp/sock1
    $ echo "show table http_proxy" | socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:0
```

<a id="entry-9-3-commit-acl"></a>

**`commit acl @<ver> <acl>`**

```haproxy
commit acl @<ver> <acl>
```

Фиксирует все изменения версии `<ver>` ACL `<acl>` и удаляет все предыдущие версии. `<acl>` — это \#`<id>` или `<name>`, возвращённые командой "show acl". Номер версии должен находиться в диапазоне от "curr_ver"+1 до "next_ver" из вывода "show acl". При необходимости содержимое, которое будет записано в ACL, можно просмотреть командой "show acl @`<ver>` `<acl>`". Обычно указанный номер версии создаётся командой "prepare acl". Замена атомарна: текущая версия атомарно меняется на указанную, вследствие чего все записи других версий сразу становятся невидимыми, а все записи новой версии — видимыми. Команду также можно использовать для атомарного удаления всех видимых записей ACL: сначала вызвать "prepare acl", затем выполнить фиксацию без добавления записей. Эту команду нельзя использовать, если ссылка `<acl>` является именем, которое также используется для карты. В этом случае необходимо использовать команду "commit map".

<a id="entry-9-3-commit-map"></a>

**`commit map @<ver> <map>`**

```haproxy
commit map @<ver> <map>
```

Фиксирует все изменения версии `<ver>` карты `<map>` и удаляет все предыдущие версии. `<map>` — это \#`<id>` или `<name>`, возвращённые командой "show map". Номер версии должен находиться в диапазоне от "curr_ver"+1 до "next_ver" из вывода "show map". При необходимости содержимое, которое будет записано в карту, можно просмотреть командой "show map @`<ver>` `<map>`". Обычно указанный номер версии создаётся командой "prepare map". Замена атомарна: текущая версия атомарно меняется на указанную, вследствие чего все записи других версий сразу становятся невидимыми, а все записи новой версии — видимыми. Команду также можно использовать для атомарного удаления всех видимых записей карты: сначала вызвать "prepare map", затем выполнить фиксацию без добавления записей.

<a id="entry-9-3-commit-ssl-ca-file"></a>

**`commit ssl ca-file <cafile>`**

```haproxy
commit ssl ca-file <cafile>
```

Фиксирует временную транзакцию обновления файла CA для SSL.

Если файл CA уже существует (имеет состояние "Used" в выводе "show ssl ca-file"), новая запись файла CA вставляется в дерево файлов CA, а каждый экземпляр, использовавший прежнюю запись, перестраивается вместе со всеми необходимыми ему контекстами SSL. Все контексты, ранее использовавшиеся перестроенными экземплярами, удаляются. При успехе прежняя запись файла CA удаляется из дерева. При сбое ничего не удаляется, а все исходные контексты SSL сохраняются и продолжают использоваться. После фиксации временная транзакция уничтожается.

Если файл CA новый (создан командой "new ssl ca-file" и имеет состояние "Unused" в выводе "show ssl ca-file"), он вставляется в дерево файлов CA, но нигде в HAProxy не используется. Чтобы использовать его и создать использующие его контексты SSL, необходимо добавить его в crt-list командой "add ssl crt-list".

См. также "new ssl ca-file", "set ssl ca-file", "add ssl ca-file", "abort ssl ca-file" и "add ssl crt-list".

Заменяет в памяти прежние сертификаты SSL везде, где в конфигурации использовался `<filename>`. При сбое ничего не удаляет и не вставляет. После фиксации временная транзакция уничтожается.

<a id="entry-9-3-debug-counters"></a>

**`debug counters [reset|show|on|off|all|bug|chk|cnt|glt|?]*`**

```haproxy
debug counters [reset|show|on|off|all|bug|chk|cnt|glt|?]*
```

Выводит внутренние счётчики, размещённые в коде; их набор может зависеть от опций сборки. Одни зависят от DEBUG_STRICT, другие — от DEBUG_COUNTERS. Команда принимает сочетание нескольких аргументов: одни задают действия, другие — фильтры: - bug включает вывод счётчиков для операторов BUG_ON() - cnt включает вывод счётчиков для операторов COUNT_IF() - chk включает вывод счётчиков для операторов CHECK_IF() - glt включает вывод счётчиков для операторов COUNT_GLITCH() - all включает вывод счётчиков, которые ни разу не срабатывали (значение 0) - действие off: отключает обновление счётчиков COUNT_IF() - действие on: включает обновление счётчиков COUNT_IF() - действие reset: сбрасывает все указанные счётчики - действие show: выводит все указанные счётчики

По умолчанию используется действие "show", выводящее счётчики, и показываются счётчики всех типов с ненулевым значением. Команда "show" подразумевается, если не указано другое действие; она предусмотрена лишь для упрощения формирования команд в скриптах.

Вывод начинается с целочисленного значения счётчика, за которым следуют его тип в верхнем регистре, местоположение в коде (file:line), имя функции и, при наличии описания, ": " с этим описанием. Обратите внимание: формат вывода может меняться между основными версиями, а новые типы и записи могут переноситься в стабильные версии для улучшения возможностей отладки. Если эти счётчики всё же используются для мониторинга, такой мониторинг должен быть очень терпимым к изменениям и отклонениям; предпочтительно вообще от него отказаться.

Обычно конечные пользователи не используют эту команду, но разработчик, выясняющий причину проблемы, может попросить выполнить её для поиска записей CNT или GLT. При этом ненулевые записи "CHK" не должны появляться; о них следует сообщать разработчикам, поскольку они могут указывать на неверные предположения в коде.

<a id="entry-9-3-del-backend"></a>

**`del backend <name>`**

```haproxy
del backend <name>
```

Удаляет прокси бэкенда с именем `<name>`.

Операция возможна только для прокси TCP или HTTP. Для её успешного выполнения экземпляр бэкенда предварительно должен быть снят с публикации. Кроме того, сначала необходимо удалить все его серверы (командой CLI "del server"). Наконец, к экземпляру бэкенда не должно оставаться привязанных потоков.

Есть и другие ограничения, препятствующие удалению бэкенда. Во-первых, бэкенд нельзя удалить, если на него явно ссылаются элементы конфигурации, например правило use_backend или выражения извлечения образцов. Некоторые опции прокси также несовместимы с удалением во время выполнения. В настоящее время это касается устаревших dispatch и option transparent. Кроме того, бэкенд нельзя удалить, если в нём объявлена таблица привязок. Наконец, пока невозможно удалить бэкенд, в котором присутствовали серверы QUIC.

Перед этой командой может быть полезно выполнить "wait be-removable", чтобы проверить перечисленные условия. Это также позволяет дождаться окончательного закрытия потоков, привязанных к целевому бэкенду.

Команда имеет ограниченный доступ и может выполняться только через сокеты с уровнем "admin".

<a id="entry-9-3-del-server"></a>

**`del server <backend>/<server>`**

```haproxy
del server <backend>/<server>
```

Удаляет доступный для удаления сервер, привязанный к бэкенду `<backend>`. Для возможности удаления сервер должен удовлетворять всем следующим условиям:

- на него не ссылаются другие элементы конфигурации
- он уже должен находиться в режиме обслуживания (см. "disable server")
- у него не должно быть активных или простаивающих соединений

Если хотя бы одно из этих условий не выполнено, команда завершается с ошибкой.

Активными считаются соединения, в которых выполняется хотя бы один запрос. Их завершение можно ускорить командой "shutdown sessions server". Настоятельно рекомендуется перед "del server" выполнить "wait srv-removable", чтобы убедиться, что все активные и простаивающие соединения закрыты и команда завершится успешно.

<a id="entry-9-3-disable-agent"></a>

**`disable agent <backend>/<server>`**

```haproxy
disable agent <backend>/<server>
```

Помечает вспомогательную агентскую проверку как временно остановленную.

Если агентская проверка выполняется как вспомогательная благодаря параметру agent-check директивы server, новые проверки запускаются только при включённом агенте. Таким образом, disable agent предотвращает запуск новых агентских проверок до повторного включения агента командой enable agent.

При отключении агента вспомогательная агентская проверка, запущенная при включённом агенте, обрабатывается следующим образом: все результаты, которые изменили бы вес, в частности "drain" или вес, возвращённый агентом, игнорируются. В остальном обработка агентской проверки не меняется.

Эта возможность позволяет приостановить изменение веса по результатам агентских проверок, чтобы вес сервера можно было настроить командой set weight без последующего переопределения агентом.

Команда имеет ограниченный доступ и может выполняться только через сокеты с уровнем "admin".

<a id="entry-9-3-experimental-mode"></a>

**`experimental-mode [on|off]`**

```haproxy

```

Без опций показывает, включён ли экспериментальный режим в текущем соединении. При передаче "on" включает экспериментальный режим только для текущего соединения CLI. При передаче "off" отключает его.

Экспериментальный режим предоставляет доступ к дополнительным возможностям, которые ещё разрабатываются. В настоящее время эти возможности нестабильны, поэтому их следует использовать с осторожностью. При переходе между версиями в них возможны несовместимые изменения.

При использовании из CLI главного процесса команду следует вводить без префикса, поскольку она задаёт режим для любого рабочего процесса при подключении к его CLI.

Пример:

```text
echo "@1; experimental-mode on; <experimental_cmd>..." | socat /var/run/haproxy.master -
echo "experimental-mode on; @1 <experimental_cmd>..." | socat /var/run/haproxy.master -
```

**`expert-mode [on|off]`**


Эта команда аналогична experimental-mode, но переключает экспертный режим.

Экспертный режим включает отображение команд для специалистов, которые могут быть крайне опасны для процесса и иногда помогают разработчикам собирать важную информацию о сложных ошибках. Любое неправильное использование этих возможностей с большой вероятностью приведёт к аварийному завершению процесса. Не используйте эту опцию без соответствующего указания. Обратите внимание: команда намеренно не включена в справочное сообщение. Она доступна только на уровне admin. Переход на другой уровень автоматически сбрасывает экспертный режим.

При использовании из CLI главного процесса команду следует вводить без префикса, поскольку она задаёт режим для любого рабочего процесса при подключении к его CLI.


<a id="entry-9-3-prompt"></a>

**`prompt [help | n | i | p | timed]*`**

```haproxy

```

Меняет поведение интерактивного режима и приглашение, отображаемое в начале строки в интерактивном режиме: - "help" : выводит справку по команде - "n" : переключает в неинтерактивный режим - "i" : переключает в интерактивный режим - "p" : переключает в интерактивный режим с приглашением - "timed" : переключает отображение времени в приглашении

Без опций циклически переключает режим с приглашением и неинтерактивный режим. В неинтерактивном режиме соединение закрывается после выполнения последней команды текущей строки. В интерактивном режиме соединение не закрывается после выполнения команды, чтобы можно было ввести следующую. В режиме с приглашением по-прежнему используется интерактивный режим, а в начале строки появляется приглашение, сообщающее пользователю, что интерпретатор ожидает новую команду. Приглашение состоит из правой угловой скобки и пробела "\> ".

Режим с приглашением лучше подходит для ручной работы, интерактивный режим — для сложных скриптов, а неинтерактивный режим (по умолчанию) — для простых скриптов. Обратите внимание: неинтерактивный режим недоступен для сокета главного процесса.

<a id="entry-9-3-set-anon"></a>

**`set anon [on|off] [<key>]`**

```haproxy
set anon [on|off] [<key>]
```

Эта команда включает или отключает «режим анонимизации» для текущего сеанса CLI. В нём некоторые поля вывода команд, считающиеся чувствительными или конфиденциальными, заменяются хешами. Эти хеши сохраняют достаточно согласованности между элементами, чтобы разработчики могли выявлять связи при поиске ошибок, но имеют достаточно малую разрядность (24), чтобы восстановление исходных значений было невозможно из-за большого числа потенциальных совпадений. При включении режима без указания ключа используется глобальный ключ (заданный в файле конфигурации через "anonkey" или командой CLI "set anon global-key"). Если такой ключ не задан, создаётся случайный. Вместо этого можно указать 32-разрядный ключ для текущего сеанса, например повторно использовать ключ предыдущего дампа для упрощения сравнения вывода. Разработчикам этот ключ никогда не понадобится; рекомендуется никому его не передавать, поскольку он может позволить подтвердить или опровергнуть догадки о том, что скрывается за определёнными хешами.

<a id="entry-9-3-set-ssl-cert"></a>

**`set ssl cert <filename> <payload>`**

```haproxy
set ssl cert <filename> <payload>
```

Эта команда входит в систему транзакций; могут потребоваться команды "commit ssl cert" и "abort ssl cert". Вся система транзакций работает с любым сертификатом, который выводит команда "show ssl cert", то есть с любым сертификатом фронтенда или бэкенда. Если текущей транзакции нет, сертификат `<filename>` дублируется в памяти во временную транзакцию, после чего эта транзакция обновляется файлом PEM из полезной нагрузки. Если транзакция с тем же именем файла существует, она обновляется. Также можно обновлять файлы, связанные с сертификатом (.issuer, .sctl, .ocsp и т. д.). После внесения изменений необходимо зафиксировать транзакцию командой "commit ssl cert".

Передавать файлы через CLI необходимо с осторожностью, поскольку пустая строка обозначает конец полезной нагрузки. Рекомендуется передавать предварительно очищенный файл PEM. Простой способ — удалить все пустые строки и оставить только содержимое секций PEM. Это можно сделать командой sed.

Пример:

```haproxy
# With some simple sanitizing
 echo -e "set ssl cert localhost.pem <<\n$(sed -n '/^$/d;/-BEGIN/,/-END/p' 127.0.0.1.pem)\n" | \
 socat /var/run/haproxy.stat -

 # Complete example with commit
 echo -e "set ssl cert localhost.pem <<\n$(cat 127.0.0.1.pem)\n" | \
 socat /var/run/haproxy.stat -
 echo -e \
 "set ssl cert localhost.pem.issuer <<\n $(cat 127.0.0.1.pem.issuer)\n" | \
 socat /var/run/haproxy.stat -
 echo -e \
 "set ssl cert localhost.pem.ocsp <<\n$(base64 -w 1000 127.0.0.1.pem.ocsp)\n" | \
 socat /var/run/haproxy.stat -
 echo "commit ssl cert localhost.pem" | socat /var/run/haproxy.stat -
```

**`set weight <backend>/<server> <weight>[%]`**

<a id="entry-9-3-show-activity"></a>

**`show activity [-1 | 0 | thread_num]`**

```haproxy

```

Выводит некоторые счётчики внутренних событий, помогающие разработчикам и другим людям, достаточно хорошо знающим haproxy, сузить круг возможных причин аномального поведения. В многопоточных развёртываниях первый столбец содержит сумму (или среднее — в зависимости от природы метрики) по всем потокам, а значения отдельных потоков перечисляются в квадратных скобках в порядке потоков. <a id="entry-9-3-show-errors"></a>

**`show errors [<iid>|<proxy>] [request|response]`**

```haproxy
show errors [<iid>|<proxy>] [request|response]
```

Выгружает последние известные ошибки запросов и ответов HTTP/1.x, собранные фронтендами и бэкендами. Если задан `<iid>`, вывод ограничивается ошибками фронтенда или бэкенда с ID `<iid>`. ID прокси "-1" приводит к выводу всех экземпляров. Если вместо этого задано имя прокси, в качестве фильтра используется его ID. Если после имени или ID прокси добавлено "request" или "response", выводятся только ошибки запросов или ответов соответственно. Команда имеет ограниченный доступ и может выполняться только через сокеты с уровнем "operator" или "admin".

Собираются последние ошибки запросов и ответов, вызванные нарушением протокола, часто из-за недопустимых символов в именах заголовков. Отчёт точно указывает символ, нарушивший протокол. Выводятся и другие важные сведения: точная дата обнаружения ошибки, имена фронтенда и бэкенда, имя сервера (если известно), внутренний ID транзакции и адрес источника, инициировавшего сеанс.

Возвращаются все символы, при этом непечатаемые символы кодируются. Наиболее распространённые
(&#92;t = 9, &#92;n = 10, &#92;r =
13 и &#92;e = 27) кодируются одной буквой после обратной косой черты.
Сама обратная косая черта кодируется как '&#92;&#92;', чтобы избежать
неоднозначности. Другие непечатаемые символы кодируются как '&#92;xNN', где NN —
двухзначное шестнадцатеричное представление кода ASCII символа.

Перед строками указывается позиция их первого символа, начиная с 0 для начала буфера. В каждой строке вывода печатается не более одной входной строки, а длинные строки разбиваются на несколько последовательных строк вывода, чтобы ширина никогда не превышала 79 символов. Перенос легко распознать: строка не заканчивается на '&#92;n', а после смещения следующей строки стоит знак '+', указывающий на продолжение предыдущей строки.

Пример:

```shell

      src 127.0.0.1, session #54, frontend fe-eth0 (#1), server s2 (#1)
      response length 213 bytes, error at position 23:

      00000  HTTP/1.0 200 OK\r\n
      00017  header/bizarre:blah\r\n
      00038  Location: blah\r\n
      00054  Long-line: this is a very long line which should b
      00104+ e broken into multiple lines on the output buffer,
      00154+  otherwise it would be too large to print in a ter
      00204+ minal\r\n
      00211  \r\n

В примере выше бэкенд "http-in" с внутренним ID 2 заблокировал неверный
ответ своего сервера s2 с внутренним ID 1. Запрос относился к транзакции
54 (здесь названной "session"), начатой источником 127.0.0.1 и принятой
фронтендом fe-eth0 с ID 1. При обнаружении ошибки общая длина ответа
составляла 213 байт, а ошибка находилась в байте 23: это косая черта ('/')
в имени заголовка "header/bizarre", недопустимая в имени заголовка HTTP.
```

<a id="entry-9-3-show-events"></a>

**`show events [<sink>] [-w] [-n] [-0] [-s]`**

```haproxy
show events [<sink>] [-w] [-n] [-0] [-s]
```

Без опций выводит все известные приёмники событий и их типы. С опцией выгружает все доступные события из указанного приёмника, если он имеет тип buffer. Если после имени приёмника передана опция "-w", по достижении конца буфера команда ожидает новые события и выводит их. Операцию можно остановить любым вводом (который будет отброшен) или закрытием сеанса. Опция "-n" сразу переходит к концу буфера; это часто удобно в сочетании с "-w", чтобы выводить только новые события. Для удобства можно использовать "-wn" или "-nw", включающие обе опции сразу. По умолчанию события разделяются символом перевода строки ('&#92;n', 10 или 0x0A). Передав аргумент "-0", разделитель можно заменить символом NUL ('&#92;0' или 0). Опция "-s" очищает вывод, чтобы двоичное содержимое захваченных или декодированных данных не меняло отображение в терминале. Пробельные символы (пробел и табуляция) заменяются пробелом, чтобы каждая запись оставалась на одной строке. Остальные управляющие символы (от 0x00 до 0x1F и 0x7F), а также символы вне ASCII (0x80 и выше) заменяются на '?'. Длина вывода сохраняется. Поэтому выгрузка кольцевого буфера не может внедрить ANSI escape-последовательности или коды направления письма в терминал оператора. Это полезно при выводе в терминал либо в программу, ввод которой не должен интерпретироваться как специальные символы, например в скрипты мониторинга, чья выдача без изменений копируется в отчёты.

<a id="entry-9-3-show-fd"></a>

**`show fd [-!plcfbsd]* [[<tgid>]/[<fd>] | <fd>]`**

```haproxy
show fd [-!plcfbsd]* [[<tgid>]/[<fd>] | <fd>]
```

Выгружает список всех открытых файловых дескрипторов либо только дескриптор с номером `<fd>`, если он указан. Также принимается форма "`<tgid>`/`<fd>`", в которой любую сторону можно оставить пустой для выбора всех соответствующих значений ("/`<fd>`" для fd `<fd>` во всех группах потоков, "`<tgid>`/" для всех fd группы `<tgid>`). Сейчас `<tgid>` разбирается, но игнорируется до появления поддержки отдельных таблиц fd для групп потоков. При необходимости можно передать набор флагов, чтобы выводить только определённые типы FD или исключать их. При встрече '-' или '!' выбор инвертируется для следующих символов того же аргумента. Перед каждым новым словом аргумента, отделённым пробельными символами, инверсия сбрасывается. Выбираемые типы FD: 'p' — каналы, 'l' — слушатели, 'c' — соединения любого типа, 'f' — соединения фронтенда, 'b' — соединения бэкенда любого типа, 's' — соединения с серверами, 'd' — соединения с адресом "dispatch" или прозрачным адресом бэкенда. Таким образом, 'b' — сокращение для 'sd', а 'c' — для 'fb' или 'fsd'. 'c!f' эквивалентно 'b' («все соединения, кроме соединений фронтенда» действительно являются соединениями бэкенда). Команда предназначена только для разработчиков, которым нужно наблюдать внутренние состояния при отладке сложных проблем, например аномального потребления CPU. Каждый fd выводится отдельной строкой. Для него указывается состояние в механизме опроса: включённые флаги обозначаются прописными буквами, отключённые — строчными; "P" означает опрос, "R" — готовность, "A" — активность. Состояние событий обозначается как "H" — разрыв соединения, "E" — ошибка, "O" — вывод, "P" — приоритет и "I" — ввод. Есть и другие флаги: "N" — новый (только что добавлен в кеш fd), "U" — обновлённый (получил обновление в кеше fd), "L" — "linger_risk", "C" — клонированный. Далее идут позиция записи в кеше, указатель на внутреннего владельца, указатель на функцию обратного вызова I/O и её имя, если оно известно. Если владелец — соединение, выводятся флаги соединения и его цель (фронтенд, прокси или сервер). Если владелец — слушатель, выводятся его состояние и фронтенд. Без хорошего знания внутреннего устройства пользоваться этой командой бессмысленно. Формат вывода со временем может меняться, поэтому этот вывод нельзя разбирать инструментами, рассчитанными на длительное использование. Некоторые состояния внутренних структур могут показаться подозрительными функции, которая их выводит; в этом случае в конце строки ставится восклицательный знак ('!'). Это может дать отправную точку при диагностике инцидента.

<a id="entry-9-3-show-info"></a>

**`show info [typed|json] [desc] [float]`**

```haproxy
show info [typed|json] [desc] [float]
```

Выгружает сведения о состоянии haproxy в текущем процессе. Если передан необязательный аргумент "typed", также выводятся номера, имена и типы полей, чтобы внешние средства мониторинга могли легко получать, при необходимости агрегировать, а затем представлять сведения из неизвестных им полей. Каждое поле выводится отдельной строкой. Если передан необязательный аргумент "json", сведения из вывода "typed" представляются в формате JSON как список объектов JSON. По умолчанию формат содержит лишь два столбца, разделённых двоеточием (':'): слева имя поля, справа значение. Очень важно учитывать, что в типизированном формате вывод одного объекта идёт непрерывно, поэтому получателю не требуется хранить всё сразу. Если передан необязательный аргумент "float", некоторые поля, обычно выводимые как целые числа, могут выводиться как числа с плавающей точкой для повышения точности. Намеренно не уточняется, какие именно поля затрагиваются, поскольку со временем это может измениться. Использование этой опции предполагает, что получатель умеет обрабатывать числа с плавающей точкой. Используемый формат вывода — sprintf("%f").

В типизированном формате каждая строка состоит из 4 столбцов, разделённых двоеточиями (':'). Первый столбец — последовательность из 3 элементов, разделённых точками. Первый элемент — числовая позиция поля в списке (начиная с нуля). Эта позиция не должна меняться со временем, но возможны пропуски в зависимости от опций сборки или удаления некоторых полей в будущем. Второй элемент — имя поля, как в обычном выводе "show info". Третий элемент — относительный номер процесса, начинающийся с 1.

Остаток строки после первого двоеточия соответствует «типизированному формату вывода», описанному выше. Второй столбец (после первого ':') указывает происхождение, характер и область действия переменной. Третий столбец задаёт тип поля: "s32", "s64", "u32", "u64" или "str". Четвёртый столбец содержит само значение; благодаря столбцу 3 получатель знает, как его разобрать, а благодаря столбцу 2 — как его обработать.

По умолчанию показывается текущая версия карты (версия, с которой сейчас выполняется сопоставление и которая указана как 'curr_ver' в списке карт). Можно выгрузить другие версии, поставив '@`<ver>`' перед идентификатором карты. Версия действует как фильтр: для несуществующей версии просто не будет результата. Возвращаемые данные представляют собой не непосредственно список доступных карт, а список всех шаблонов, составляющих какую-либо карту. Многие из этих шаблонов могут быть общими с ACL.

<a id="entry-9-3-show-profiling"></a>

**`show profiling [{all | status | tasks | memory}] [byaddr|bytime|byctx|aggr|<max_lines>]*`**

```haproxy

```

Выгружает текущие настройки профилирования, по одной в строке, а также команды для их изменения. При включённом профилировании задач также выводится собранная планировщиком статистика по функциям: число вызовов, общее/среднее время CPU и общая/средняя задержка. <a id="entry-9-3-show-quic"></a>

**`show quic [<format>] [<filter>]`**

```haproxy
show quic [<format>] [<filter>]
```

Выгружает сведения обо всех активных соединениях QUIC фронтенда. Команда имеет ограниченный доступ и может выполняться только через сокеты с уровнем "operator" или "admin".

Необязательный аргумент позволяет управлять подробностью вывода. Его значение можно интерпретировать разными способами. Первый вариант — предопределённые значения: "oneline" для формата по умолчанию, "stream" для перечисления всех активных потоков и "full" для вывода всех сведений. Вместо этого можно задать разделённый запятыми список полей, ограничив вывод. Сейчас поддерживаются "tp", "sock", "pktns", "cc" и "mux". Наконец, значение формата "help" выводит более подробную справку.

Последний аргумент ограничивает или расширяет список соединений. По умолчанию показываются только активные соединения фронтенда. Дополнительный аргумент "clo" позволяет вместо них вывести закрывающиеся соединения фронтенда, "be" — соединения бэкенда, "all" — все категории. Также можно ограничиться одним соединением, указав его шестнадцатеричный адрес.

<a id="entry-9-3-show-servers-conn"></a>

**`show servers conn [<backend>]`**

```haproxy
show servers conn [<backend>]
```

Выгружает состояние текущих и простаивающих соединений серверов указанного бэкенда (или всех бэкендов, если ни один не указан). Можно использовать имя или идентификатор бэкенда.

Вывод начинается со строки с названиями полей, затем каждый сервер занимает одну строку: имя и ID бэкенда, имя и ID сервера, адрес, порт и ряд значений. Число полей зависит от числа потоков. Точный формат вывода может немного различаться между версиями и в зависимости от числа потоков. При извлечении значений нужно учитывать строку заголовка для сопоставления столбцов и число потоков, поскольку последние столбцы относятся к отдельным потокам:

```text
bkname/svname         Имя бэкенда '/' имя сервера
bkid/svid             ID бэкенда '/' ID сервера
addr                  IP-адрес сервера
port                  Порт сервера (ноль, если отсутствует)
-                     Неиспользуемое поле, служит визуальным разделителем
purge_delay           Интервал между очистками соединений в миллисекундах
served                Число соединений, используемых в данный момент
used_cur              Число соединений, используемых в данный момент;
                      соединения, привязанные к сеансу, не учитываются
used_max              Наибольшее значение used_cur с запуска процесса
need_est              Плавающая оценка общего необходимого числа соединений
idle_sess             Число неактивных соединений, помеченных как частные
unsafe_nb             Число неактивных соединений, считающихся «небезопасными»
safe_nb               Число неактивных соединений, считающихся «безопасными»
idle_lim              Настроенный максимум числа неактивных соединений
idle_cur              Сумма текущего числа неактивных соединений по потокам
idle_per_thr[NB]      Неактивные соединения каждого из NB потоков
```

HAProxy закрывает часть `<idle_cur>` каждые `<purge_delay>`, когда сумма `<idle_cur>` + `<used_cur>` превышает оценку `<need_est>`. Эта оценка меняется в зависимости от активности соединений.

Из-за многопоточной обработки простаивающих соединений важно понимать, что некоторые значения могут измениться сразу после чтения, поэтому согласованность значений внутри строки не гарантируется. Этот вывод предназначен преимущественно для отладки и не подходит для регулярного мониторинга или построения графиков.

<a id="entry-9-3-show-sess"></a>

**`show sess [<options>*]`**

```haproxy

```

<a id="entry-9-3-show-sess-2"></a>


Выводит множество внутренних сведений о соответствующих потоках. Команда поддерживает два формата: краткий, используемый по умолчанию, если не запрошен конкретный идентификатор потока, и расширенный — при перечислении указанных потоков. Краткий формат, используемый по умолчанию командой "show sess", выводит каждый поток одной строкой с несколькими сведениями и его шестнадцатеричным идентификатором в начале строки (это указатель на поток).

В расширенной форме, используемой командами "show sess `<id>`" или "show sess all", каждый поток выводится с большим количеством отладочных сведений на нескольких строках (около 20 на поток), по-прежнему начинаясь с идентификатора. Разделителем между потоками служит идентификатор в начале строки; дополнительные строки того же потока начинаются с одного или нескольких пробелов (поток выводится с отступом). Выгрузка большого числа потоков может дать огромный объём вывода, занять много времени и сильно загрузить CPU, поэтому всегда лучше выводить только необходимый минимум. Большинству пользователей эти сведения бесполезны, но разработчики HAProxy могут использовать их для диагностики сложных ошибок. Точный формат вывода намеренно не документирован, чтобы он мог свободно меняться по мере необходимости, в том числе в стабильных ветках. При интерпретации этого вывода следует сверяться с функцией strm_dump_to_buffer() в src/stream.c для определения точного смысла некоторых полей.

Аргумент "help" вместо выгрузки потоков выводит подробную справку по команде.

Можно задать опции для настройки выгрузки или применения фильтров. Поддерживаются следующие опции: - backend `<b>` — показывать только потоки, привязанные к этому бэкенду - frontend `<f>` — показывать только потоки, привязанные к этому фронтенду - older `<age>` — показывать только потоки старше `<age>` секунд - server `<b/s>` — показывать только потоки, привязанные к этой паре бэкенд+сервер - show-uri — выводить URI транзакции, захваченный при анализе запроса; он отображается только при наличии захвата - susp — показывать только потоки, которые разработчики считают подозрительными по критериям, способным меняться со временем или между версиями.

<a id="entry-9-3-show-stat"></a>

**`show stat [domain <resolvers|proxy>] [{<iid>|<proxy>} <type> <sid>] \`**

```haproxy
show stat [domain <resolvers|proxy>] [{<iid>|<proxy>} <type> <sid>] \
          [typed|json] [desc] [up|no-maint]
```

Выгружает статистику. Домен определяет, какую статистику выводить; сейчас доступны resolvers и proxy. По умолчанию используется формат CSV. Можно включить расширенный типизированный формат, описанный выше, передав "typed" после остальных аргументов, либо формат JSON, передав "json" после остальных аргументов. Аргументы `<id>`, `<type>` и `<sid>` позволяют вывести только выбранные элементы: - `<iid>` — ID прокси, -1 для вывода всего. Вместо него можно указать имя прокси `<proxy>`; тогда ID этого прокси используется для выбора по ID. - `<type>` выбирает тип выводимых объектов: 1 для фронтендов, 2 для бэкендов, 4 для серверов, -1 для всего. Эти значения можно объединять побитовым ИЛИ, например:

```text
1 + 2     = 3   -> фронтенд + бэкенд.
1 + 2 + 4 = 7   -> фронтенд + бэкенд + сервер.
```

    - `<sid>` — ID сервера, -1 для вывода всего из выбранного прокси.

Пример:

```shell
    $ echo "show info;show stat" | socat stdio unix-connect:/tmp/sock1
>>> Name: HAProxy
    Version: 1.4-dev2-49
    Release_date: 2009/09/23
    Nbproc: 1
    Process_num: 1
    (...)

    # pxname,svname,qcur,qmax,scur,smax,slim,stot,bin,bout,dreq,  (...)
    stats,FRONTEND,,,0,0,1000,0,0,0,0,0,0,,,,,OPEN,,,,,,,,,1,1,0, (...)
    stats,BACKEND,0,0,0,0,1000,0,0,0,0,0,,0,0,0,0,UP,0,0,0,,0,250,(...)
    (...)
    www1,BACKEND,0,0,0,0,1000,0,0,0,0,0,,0,0,0,0,UP,1,1,0,,0,250, (...)

    $
```

В этом примере одновременно выполнены две команды. Так в многопроцессном режиме легко определить, к какому процессу относится статистика. В типизированном формате это не требуется, поскольку номер процесса указан в каждой строке. Обратите внимание на пустую строку после вывода информации: она обозначает конец первого блока. Такая же пустая строка есть в конце второго блока (статистики), чтобы получатель мог убедиться, что вывод не обрезан.

При указании "typed" формат вывода лучше подходит средствам мониторинга, поскольку предоставляет числовые позиции и тип каждого поля. Каждое значение занимает отдельную строку с номером процесса, номером элемента, характером, происхождением и областью действия. Тот же формат доступен через статистику HTTP при добавлении ";typed" после URI. Очень важно учитывать, что в типизированном формате вывод одного объекта идёт непрерывно, поэтому получателю не требуется хранить всё сразу.

Модификатор "up" приводит к выводу только серверов, которые считаются доступными или не проверяются. Недоступные серверы, серверы с неразрешённым адресом и серверы в режиме обслуживания не выводятся. Это аналог опции ";up" в статистике HTTP. Аналогично, модификатор "no-maint" действует как модификатор HTTP ";no-maint" и исключает из вывода отключённые серверы. Разница в том, что включённые, но недоступные серверы остаются в выводе.

В типизированном формате каждая строка состоит из 4 столбцов, разделённых двоеточиями (':'). Первый столбец — последовательность из 5 элементов, разделённых точками. Первый элемент — буква, указывающая тип описываемого объекта. Сейчас известны следующие типы: 'F' — фронтенд, 'B' — бэкенд, 'L' — слушатель и 'S' — сервер. Второй элемент — положительное целое число, представляющее уникальный идентификатор прокси, которому принадлежит объект. Он эквивалентен столбцу "iid" вывода CSV и соответствует значению необязательной директивы "id" в секции frontend или backend. Третий элемент — положительное целое число с уникальным идентификатором объекта внутри прокси, соответствующее столбцу "sid" вывода CSV. При выводе фронтенда или бэкенда указывается ID 0. Для слушателя или сервера это соответствующий ID внутри прокси. Четвёртый элемент — числовая позиция поля в списке (начиная с нуля). Эта позиция не должна меняться со временем, но возможны пропуски в зависимости от опций сборки или удаления некоторых полей в будущем. Пятый элемент — имя поля, как в выводе CSV. Шестой элемент — положительное целое число, относительный номер процесса, начинающийся с 1.

Остаток строки после первого двоеточия соответствует «типизированному формату вывода», описанному выше. Второй столбец (после первого ':') указывает происхождение, характер, область действия и признак сохранения переменной. Третий столбец задаёт тип поля: "s32", "s64", "u32", "u64", "flt" или "str". Четвёртый столбец содержит само значение; благодаря столбцу 3 получатель знает, как его разобрать, а благодаря столбцу 2 — как его обработать.

Если к команде добавлено "desc", в конец добавляется ещё одно двоеточие и строка в кавычках с описанием метрики. На момент написания это поддерживается только для формата "typed".

Таким образом, общий формат строки в типизированном режиме:

```text
<obj>.<px_id>.<id>.<fpos>.<fname>.<process_num>:<tags>:<type>:<value>
```

<a id="entry-9-3-show-ssl-sni"></a>

**`show ssl sni [-f <frontend>] [-A] [-t <offset>]`**

```haproxy
show ssl sni [-f <frontend>] [-A] [-t <offset>]
```

Выгружает все SNI, настроенные для указанного фронтенда, либо для всех фронтендов, если фронтенд не указан. Это позволяет увидеть, какие SNI предлагаются фронтендом, и определить, не задан ли один SNI несколько раз разными сертификатами для одного фронтенда.

Опция -A фильтрует список и показывает только сертификаты, дата notAfter которых уже прошла, то есть только сертификаты с истёкшим сроком действия.

Опция -t принимает смещение в секундах или с единицей времени (s, m, h, d), которое добавляется к текущему времени. Вместе с -A это позволяет проверить, у каких сертификатов срок действия истечёт к моменту с этим смещением. Например, чтобы проверить, какие сертификаты истекут через 30d, выполните "show ssl sni -A -t 30d".

Столбцы разделяются одним символом &#92;t, что упрощает разбор.

Столбец 'Frontend/Bind' показывает имя фронтенда и положение строки bind в конфигурации (frontend/file:linenum).

Столбец 'SNI' показывает SNI: это может быть CN, SAN или фильтр из crt-list. Для сертификатов строки bind, используемых по умолчанию (явно заданных через 'default-crt' либо первого сертификата строки bind, если не используется 'strict-sni'), в столбце SNI отображается символ '\*'.

Столбец 'Negative Filter' — список отрицательных фильтров, связанных с шаблоном подстановки; здесь показываются все отрицательные фильтры из той же строки crt-list. Если их нет, выводится дефис.

Столбец 'Type' показывает тип алгоритма шифрования: "rsa", "ecdsa" или "dsa".

Столбец 'Filename' может содержать имя файла из конфигурации или псевдоним, объявленный в crt-store.

Столбцы 'NotAfter' и 'NotBefore' извлекаются непосредственно из конечного сертификата X509.

<a id="entry-9-3-show-table-2"></a>

**`show table <name> [ data.<type> <operator> <value> [data.<type> ...]] |`**

```haproxy
show table <name> [ data.<type> <operator> <value> [data.<type> ...]] |
                  [ key <key> ] | [ ptr <ptr> ]
```

Выгружает содержимое таблицы привязок `<name>`. В этом режиме сначала выводится строка общих сведений о таблице, как в "show table", а затем все записи. Поскольку это может быть довольно затратно, можно задать фильтр, определяющий, какие записи выводить.

При использовании формы "data." фильтр применяется к сохранённым данным (см. "stick-table" в разделе 4.2). В `<type>` необходимо указать тип сохраняемых данных; этот тип должен храниться в таблице, иначе возвращается ошибка. Оператор `<operator>` определяет сравнение данных с 64-разрядным целым `<value>`. Операторы те же, что в ACL:

    - eq: записи, данные которых равны этому значению
    - ne: записи, данные которых не равны этому значению
    - le: записи, данные которых меньше или равны этому значению
    - ge: записи, данные которых больше или равны этому значению
    - lt: записи, данные которых меньше этого значения
    - gt: записи, данные которых больше этого значения

В этой форме можно задать несколько фильтров данных, не превышая максимума, установленного при сборке (по умолчанию 4).

При использовании формы key показывается запись `<key>`. Ключ должен иметь тот же тип, что и таблица; в настоящее время поддерживаются только IPv4, IPv6, целое число и строка.

При использовании формы ptr показывается запись `<ptr>`. `<ptr>` задаётся в виде 0xffff и должен соответствовать адресу, возвращённому предыдущей командой "show table". Поиск записи по указателю полезен, если найти её по ключу невозможно из-за пустого ключа или символов, несовместимых с cli.

Если data.`<type>` имеет тип массива, для доступа к определённому индексу можно использовать "[]", например: data.gpt[1]

Пример:

```shell
    $ echo "show table http_proxy" | socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:2
>>> 0x80e6a4c: key=127.0.0.1 use=0 exp=3594729 gpc0=0 conn_rate(30000)=1  \
      bytes_out_rate(60000)=187
>>> 0x80e6a80: key=127.0.0.2 use=0 exp=3594740 gpc0=1 conn_rate(30000)=10 \
      bytes_out_rate(60000)=191

    $ echo "show table http_proxy data.gpc0 gt 0" | socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:2
>>> 0x80e6a80: key=127.0.0.2 use=0 exp=3594740 gpc0=1 conn_rate(30000)=10 \
      bytes_out_rate(60000)=191

    $ echo "show table http_proxy data.conn_rate gt 5" | \
        socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:2
>>> 0x80e6a80: key=127.0.0.2 use=0 exp=3594740 gpc0=1 conn_rate(30000)=10 \
      bytes_out_rate(60000)=191

    $ echo "show table http_proxy key 127.0.0.2" | \
        socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:2
>>> 0x80e6a80: key=127.0.0.2 use=0 exp=3594740 gpc0=1 conn_rate(30000)=10 \
      bytes_out_rate(60000)=191

    $ echo "show table http_proxy ptr 0x80e6a80" | \
        socat stdio /tmp/sock1
>>> # table: http_proxy, type: ip, size:204800, used:2
>>> 0x80e6a80: key=127.0.0.2 use=0 exp=3594740 gpc0=1 conn_rate(30000)=10 \
      bytes_out_rate(60000)=191
```

Если критерий данных применяется к динамическому значению, зависящему от времени, например скорости передачи байтов, это значение вычисляется при оценке записи, чтобы решить, нужно ли её выводить. Поэтому запись может некоторое время соответствовать фильтру, а затем перестать: со временем средняя частота событий снижается.

Это можно использовать для получения списков адресов IP, с которых злоупотребляют службой, чтобы отслеживать их или даже вносить в чёрный список межсетевого экрана. Пример:

<a id="entry-9-3-show-threads"></a>

**`show threads`**

```haproxy
show threads
```

Выгружает для каждого потока некоторые внутренние состояния и структуры, которые могут помочь разработчикам понять проблему. Для удобства чтения каждому потоку отведён отдельный блок. Если haproxy собран с USE_THREAD_DUMP=1, применяется расширенный механизм выгрузки с сигналами потокам, чтобы каждый поток по очереди мог выгрузить собственное состояние. Без этой опции все подробности выводит поток, обрабатывающий команду, а сведения об остальных менее подробны. Перед потоком, обрабатывающим команду, показывается звёздочка ('\*'). Перед потоками, которые не продвинулись в работе с предыдущего вызова команды, также может показываться правая угловая скобка ('\>'); это указывает на ошибку в коде, о которой обязательно нужно сообщить. Если это происходит с двумя потоками, обычно причина — взаимная блокировка. Если поток один, это другая ошибка, например повреждённый список. В любом случае процесс уже не полностью работоспособен и нуждается в перезапуске.

Формат вывода намеренно не документирован, чтобы его можно было легко менять при появлении новых потребностей без сохранения обратной совместимости. Как и в случае "show activity", без исходного кода эти значения лишены смысла.

<a id="entry-9-3-show-tls-keys"></a>

**`show tls-keys [id|*]`**

```haproxy
show tls-keys [id|*]
```

Выгружает ссылки на все загруженные ключи билетов TLS. Показываются ID ссылки на ключи билетов TLS и файл, из которого загружены ключи. И то и другое можно использовать для обновления ключей TLS командой "set ssl tls-key". Если в качестве параметра задан ID, выгружаются билеты; при использовании \* выгружаются все ключи по всем ссылкам.

<a id="entry-9-3-show-schema-json"></a>

**`show schema json`**

```haproxy
show schema json
```

Выгружает схему, используемую для вывода "show info json" и "show stat json".

Чтобы уменьшить объём, вывод не содержит лишних пробелов. Для чтения человеком его может быть удобно пропустить через средство форматирования. Пример:

\$ echo "show schema json" \| socat /var/run/haproxy.sock stdio \| &#92;
python -m json.tool

Схема соответствует "JSON Schema" (json-schema.org), поэтому совместимые средства проверки можно использовать для проверки вывода "show info json" и "show stat json" на соответствие схеме.

<a id="entry-9-3-show-trace"></a>

**`show trace [<source>]`**

```haproxy
show trace [<source>]
```

Показывает текущее состояние трассировки. Для каждого источника выводится строка с односимвольным статусом: трассировка остановлена, ожидает или выполняется. Указывается используемый приёмник вывода (или "none", если он не задан), число отброшенных событий в этом приёмнике и краткое описание источника. Если указано имя источника, выводится подробный список всех поддерживаемых им событий и их состояние для каждого действия (report, start, pause, stop): "+", если они включены, и "-" в противном случае. Все эти события независимы: событие может запускать трассировку, само не попадая в вывод, и наоборот.

<a id="entry-9-3-show-version"></a>

**`show version`**


Показывает версию текущего процесса HAProxy. Доступно в CLI главного и рабочих процессов.
Пример:

```shell
$ echo "show version" | socat /var/run/haproxy.sock stdio

```

<a id="entry-9-3-shutdown-frontend"></a>

**`shutdown frontend <frontend>`**

```haproxy
shutdown frontend <frontend>
```

Полностью удаляет указанный фронтенд. Все порты, к которым он был привязан, освобождаются. После этой операции включить фронтенд снова невозможно. Команда предназначена для сред, где остановка прокси недопустима, но ошибочную конфигурацию прокси необходимо исправить. Таким способом можно освободить порт и привязать его к другому процессу, чтобы восстановить работу. После завершения фронтенд вообще не отображается на странице статистики.

Фронтенд можно указать по имени или по числовому ID с префиксом решётки ('#').

Команда имеет ограниченный доступ и может выполняться только через сокеты с уровнем "admin".

<a id="entry-9-3-shutdown-session"></a>

**`shutdown session <id>`**

```haproxy
shutdown session <id>
```

Немедленно завершает поток с указанным идентификатором. Этот идентификатор — первое поле в начале строк вывода "show sess" (он соответствует указателю на поток). Команду можно использовать для завершения длительного потока без ожидания тайм-аута или при бесконечной передаче данных. Завершённые таким образом потоки отмечаются в журналах флагом 'K'.

<a id="entry-9-3-shutdown-sessions-server"></a>

**`shutdown sessions server <backend>/<server>`**

```haproxy
shutdown sessions server <backend>/<server>
```

Немедленно завершает все потоки, привязанные к указанному серверу. Это можно использовать, например, для завершения длительных потоков после перевода сервера в режим обслуживания. Завершённые таким образом потоки отмечаются в журналах флагом 'K'.

Соединения бэкенда остаются в состоянии простоя, если сервер ещё не находится в режиме обслуживания; если находится, для них немедленно планируется удаление.

<a id="entry-9-3-trace"></a>

**`trace`**

```haproxy
trace
```

Команда "trace" без аргументов выводит список источников трассировки, их текущее состояние и краткие описания. Она служит только меню для перехода на следующие уровни; см. другие команды "trace" ниже.

<a id="entry-9-3-trace-0"></a>

**`trace 0`**

```haproxy
trace 0
```

Немедленно останавливает все трассировки. Это быстрый способ завершить сеанс отладки или экстренная мера, если на нескольких источниках включены сложные трассировки, влияющие на работу службы.

<a id="entry-9-3-trace-2"></a>

**`trace <source> [<args...>]`**

```haproxy
trace <source> [<args...>]
```

Настраивает трассировку для источника `<source>`. Без аргументов выводит все поддерживаемые подкоманды этого источника. Несколько подкоманд можно объединять в цепочку. Поддерживаются следующие подкоманды:

event [ [+\|-\|!]`<name>` ] Без аргумента выводит все события, поддерживаемые указанным источником. Перед ними стоит "-", если они отключены, или "+", если включены. Важно учитывать, что одна запись трассировки может быть помечена несколькими событиями; если хотя бы одно включённое событие совпадает с одной из меток записи, событие передаётся подсистеме трассировки. Например, получение кадра HTTP/2 типа HEADERS может вызвать и событие кадра, и событие потока, поскольку кадр создаёт новый поток. Если для этого источника включено хотя бы одно из них, кадр передаётся механизму трассировки.

    С аргументом можно переключать состояние каждого события, отдельно
    включая и отключая их. Поддерживаются два специальных ключевых слова:
    "none" не соответствует ни одному событию и отключает сразу все события,
    а "any" соответствует всем событиям и включает их все сразу.
    Остальные события зависят от источника. Чтобы включить событие,
    можно указать его имя, при желании добавив префикс '+' для наглядности.
    Чтобы отключить событие, нужно указать его имя с префиксом '-' или '!'.

    Полностью отключить источник трассировки можно, передав "event none";
    после этого он сразу будет полностью игнорироваться.

follow `<other_source>` Позволяет источнику `<source>` также выдавать записи трассировки, когда другой источник `<other_source>` привязан по определённому критерию и этот же критерий совпадает для текущего источника. Например, если источник привязан к сеансу, следование за ним из другого источника заставит второй источник выдавать записи для всех событий этого сеанса. В определённых пределах так можно отслеживать запросы бэкенда вместе с соответствующими соединениями фронтенда. Источник "session" упрощает это, предоставляя события "new" и "end", которые можно использовать для привязки. Учтите, что в этом случае трассировка источника `<source>` не обязательно должна быть включена, а её состояние также не меняется. Однако некоторые события могут отсутствовать, если они не содержат сведений для сопоставления с отслеживаемым элементом. С этой командой также можно использовать метаисточник "all": в этом случае все источники будут следовать за `<other_source>`.

Пример:

```text
trace h1 lock session start sess_new pause sess_end follow session
```

level [`<level>`] Без аргумента выводит все уровни трассировки этого источника, помечая текущий звёздочкой ('\*') перед ним. С аргументом меняет уровень трассировки на указанный. Уровни детализации — это фильтры, применяемые перед выводом событий. Они позволяют выборочно включать или исключать события в зависимости от их важности. Например, разработчику может потребоваться точно знать, в каком месте кода заголовок HTTP признан недопустимым, тогда как конечному пользователю его корректность может быть вовсе не важна. Сейчас существует 5 уровней трассировки:

```text
user       выводит информацию, подходящую обычному пользователю HAProxy,
           который хочет наблюдать за своим трафиком. Обычно выводятся
           некоторые запросы и ответы HTTP без особой детализации.
           Для упрощения эксплуатации большинство источников используют
           этот уровень по умолчанию.

proto      помимо информации уровня "user", показывает изменения на
           уровне протокола, например типы кадров или заголовки HTTP
           после декодирования.

state      помимо информации уровня "proto", показывает переходы
           состояний (или неудачные переходы) в парсерах. Таким образом,
           здесь видны попытки выполнить операцию, тогда как уровень
           "proto" показывает только конечную операцию.

data       помимо информации уровня "state", включает передачи данных
           между различными уровнями.

developer  выводит всю доступную информацию, в том числе подробности
           вроде «выход из этого цикла», которые нужны только разработчику,
           разбирающему редкую ошибку в рабочей среде. Имена функций
           выводятся только на этом уровне.
```

    Настоятельно рекомендуется всегда использовать только уровень "user"
    и переходить на другие уровни лишь по указанию разработчика. Кроме того,
    полезно сначала настроить события и только затем повышать уровень:
    это поможет избежать огромного вывода при отсутствии фильтров.
    С этой командой также можно использовать метаисточник "all": тогда
    уровень применяется сразу ко всем существующим источникам.

lock [criterion] Без аргумента выводит все критерии привязки, поддерживаемые этим источником, и помечает текущий выбор звёздочкой ('\*') перед ним. Привязка означает, что источник сосредоточится на первом подходящем событии и будет придерживаться только критерия, вызвавшего это событие, игнорируя остальные до остановки трассировки. Это позволяет, например, получить трассировку одного соединения или одного потока. Следующие критерии поддерживаются некоторыми трассировками, но не обязательно всеми, поскольку часть критериев может быть недоступна источнику:

```text
backend      привязаться к бэкенду, с которого началась трассировка
connection   привязаться к соединению, с которого началась трассировка
frontend     привязаться к фронтенду, с которого началась трассировка
listener     привязаться к слушателю, с которого началась трассировка
nothing      ни к чему не привязываться
server       привязаться к серверу, с которого началась трассировка
session      привязаться к сеансу, с которого началась трассировка
thread       привязаться к потоку, с которого началась трассировка
```

    Кроме того, каждый источник может предоставлять до 4 собственных
    критериев, например внутренние состояния или ID соединений. Так, в HTTP/2
    можно привязаться к потоку H2 и игнорировать остальные потоки
    после начала трассировки.

    Если критерий передан аргументом, он используется вместо остальных,
    а текущее отслеживание немедленно завершается, чтобы его можно было
    начать заново с новым критерием. Все источники поддерживают специальное
    ключевое слово "nothing" для постоянного отключения отслеживания.

{ pause \| start \| stop } [ [+\|-\|!]event] Без аргумента выводит события, включённые для автоматической приостановки, запуска или остановки трассировки этого источника. Эти события зависят от источника трассировки. С аргументом включает событие для указанного действия (можно добавить префикс '+') либо отключает его (с префиксом '-' или '!'). Специальное ключевое слово "now" не является событием и требует немедленно выполнить действие. Ключевые слова "none" и "any" поддерживаются так же, как в "trace event".

    Поддерживаются 3 действия: "pause", "start" и "stop".
    Действие "pause" перечисляет события, при которых выполняемая трассировка
    останавливается и ожидает нового события запуска для возобновления.
    Действие "start" перечисляет события, переводящие трассировку в режим
    ожидания одного из событий запуска. Действие "stop" перечисляет события,
    окончательно останавливающие трассировку до повторного ручного включения.
    На практике удобно запускать трассировку вручную через "start now",
    не заботясь о событиях, и останавливать через "stop now".
    Для захвата более сложных последовательностей событий можно назначить
    "start" обычное событие (например, получение запроса HTTP), а "stop" —
    очень редкое событие, например выдачу определённой ошибки. Тогда последние
    захваченные события будут соответствовать нужным критериям.
    Событие pause полезно для определения конца последовательности,
    снятия привязки и ожидания следующей возможности захвата. В этом случае
    имеет смысл включить привязку по одному конкретному критерию
    (например, потоку), задать "start" всё, что начинает этот критерий
    (например, все события создания потока), "stop" — ожидаемую аномалию,
    а "pause" — всё, что завершает критерий (например, любое событие
    завершения потока). Тогда журнал трассировки будет содержать полные,
    полностью нормальные последовательности событий одного объекта вплоть
    до последней последовательности, включающей всё от начала до аномалии.

sink [`<sink>`] Без аргумента выводит все приёмники событий, доступные этому источнику, помечая текущий настроенный приёмник звёздочкой ('\*') перед ним. Приёмник "none" доступен всегда и означает, что все события просто отбрасываются, но их обработка не пропускается (например, привязка всё равно выполняется). Доступность других приёмников зависит от конфигурации и опций сборки; обычно в режиме отладки можно использовать "stdout" и "stderr", также должны быть доступны кольцевые буферы в памяти. При указании имени приёмник для заданного источника меняется немедленно. Смена приёмника не меняет события. В худшем случае некоторые события могут потеряться при использовании недопустимого приёмника (или "none"), но обработка продолжается с другим назначением вывода. С этой командой также можно использовать метаисточник "all": в этом случае приёмник применяется сразу ко всем существующим источникам.

verbosity [`<level>`] Без аргумента выводит все уровни подробности этого источника, помечая текущий звёздочкой ('\*') перед ним. С аргументом меняет уровень подробности на указанный.

    Уровни подробности определяют, насколько глубоко декодер трассировки
    должен разбирать данные для получения подробных сведений. Это зависит
    от источника: некоторые источники вообще не предоставляют отдельного
    декодера. Уровень "quiet" доступен всегда и отключает декодирование.
    Он полезен, чтобы сначала понять, что происходит, не углубляясь в детали:
    его влияние на производительность и размер трассировки очень мало.
    Если источник не объявляет уровней подробности, доступен уровень
    "default", при котором декодер вызывается, если он указан в трассировке.
    Декодирование выполняется по мере возможности. Если источник объявляет
    уровни подробности, они перечисляются с описанием своего назначения.
    В этом случае декодер источника работает с максимально возможной
    точностью на основе сведений, доступных в точке трассировки.
    По умолчанию устанавливается первый уровень выше "quiet".

<a id="entry-9-3-update-ssl-ocsp-response"></a>

**`update ssl ocsp-response <certfile>`**

```haproxy
update ssl ocsp-response <certfile>
```

Создаёт запрос OCSP для указанного `<certfile>` и отправляет его ответчику OCSP, чей URI следует указать в разделе "Authority Information Access" сертификата. Учитывается только первый URI. Полученный ответ OCSP затем проверяется и вставляется в локальное дерево ответов OCSP. Команда работает только для сертификатов, у которых уже был сохранённый ответ OCSP: он был предоставлен при инициализации либо ранее задан командами "set ssl cert" или "set ssl ocsp-response". Если полученный ответ OCSP корректен и успешно вставлен в локальное дерево, его содержимое выводится в стандартный вывод. Формат тот же, что описан для "show ssl ocsp-response".

<a id="entry-9-3-wait"></a>

**`wait { -h | <delay> } [<condition> [<args>...]]`**

```haproxy
wait { -h | <delay> } [<condition> [<args>...]]
```

В простейшей форме, без условия, просто ожидает указанное время перед продолжением. Это можно использовать для сбора метрик с определённым интервалом.

С условием и необязательными аргументами команда ожидает выполнения указанного условия, неустранимой ошибки либо истечения всего времени `<delay>` без выполнения условия. Поддерживаются следующие условия:

- be-removable `<proxy>`: ожидает, пока указанный прокси бэкенда можно будет удалить командой "del
  backend". Некоторые состояния недопустимы в любом случае (например, бэкенд ещё не снят с публикации
  или содержит серверы); при них выводится конкретная ошибка с указанием невыполненного условия.
  Если до истечения времени все условия выполнены, возвращается успех и операция завершается.

- srv-removable `<proxy>`/`<server>`: ожидает, пока указанный сервер можно будет удалить командой
  "del server", то есть пока он не окажется в режиме обслуживания без каких-либо соединений
  (активных или простаивающих). Некоторые состояния недопустимы в любом случае (например, сервер
  не в режиме обслуживания); при них выводится конкретная ошибка с указанием невыполненного условия.
  Сервер может даже быть удалён параллельно и больше не существовать. Если до истечения времени
  все условия выполнены, возвращается успех и операция завершается.

Единица задержки по умолчанию — миллисекунды, но допускаются и другие единицы с обычными временными суффиксами (us, ms, s, m, h, d). При использовании с утилитой 'socat' не забудьте увеличить тайм-аут закрытия socat, чтобы он покрывал время ожидания. Передача "-h" первым или вторым аргументом выводит справку по команде. Пример:

```shell
$ socat -t20 /path/to/socket - <<< "show activity; wait 10s; show activity"

$ socat -t5 /path/to/socket - <<< "
    disable server px/srv1
    shutdown sessions server px/srv1
    wait 2s srv-removable px/srv1
    del server px/srv1"
```

## 9.4. CLI главного процесса {#section-9-4}

CLI главного процесса — это сокет, привязанный к главному процессу в режиме master-worker. Этот CLI предоставляет доступ к командам сокета unix во всех работающих или завершающихся процессах и позволяет выполнять базовый контроль за ними.

CLI главного процесса настраивается только аргументами программы haproxy через опцию -S. Эта опция также принимает опции bind, разделённые запятыми.

Пример:

```haproxy
# haproxy -W -S 127.0.0.1:1234 -f test1.cfg
# haproxy -Ws -S /tmp/master-socket,uid,1000,gid,1000,mode,600 -f test1.cfg
# haproxy -W -S /tmp/master-socket,level,user -f test1.cfg
```

### 9.4.1. Команды CLI главного процесса {#section-9-4-1}

<a id="entry-9-4-1-entry"></a>

**`@<[!]pid>`**

```haproxy
@<[!]pid>
```

Для доступа к нескольким процессам CLI главного процесса использует специальную запись с префиксом. Её легко распознать по начальному символу @.

После префикса @ можно указать относительный номер процесса либо восклицательный знак и PID (например, @1 или @!1271). Одиночный @ обозначает главный процесс. Завершающиеся процессы доступны только по PID, поскольку относительные номера можно использовать лишь для текущих процессов.

Этот префикс можно поставить перед командой, чтобы только она была отправлена указанному процессу. В этом случае полная команда заканчивается переводом строки или точкой с запятой, как обычная команда.

Ошибки: известно, что протокол sockpair@, используемый для связи между главным и рабочим процессами, ненадёжно работает в macOS из-за проблемы в реализации sendmsg(2) в macOS. Из-за этого команда может остаться без ответа.

Примеры:

```shell
$ socat /var/run/haproxy-master.sock readline
prompt
master> @1 show info; @2 show info
[...]
Process_num: 1
Pid: 1271
[...]
Process_num: 2
Pid: 1272
[...]
master>

$ echo '@!1271 show info; @!1272 show info' | socat /var/run/haproxy-master.sock -
[...]
```

Префикс также можно использовать как самостоятельную команду, переключающую контекст выполнения по умолчанию на указанный процесс. Тогда все последующие команды выполняются в нём, пока новая команда '@' снова не сменит контекст.

Примеры:

```shell
$ socat /var/run/haproxy-master.sock readline
prompt
master> @1
1271> show info
[...]
1271> show stat
[...]
1271> @
master>

$ echo '@1; show info; show stat; @2; show info; show stat' | socat /var/run/haproxy-master.sock -
[...]
```

Примечание об ограничениях: некоторые редко используемые команды меняют состояние сеанса CLI (например, "set anon", "set timeout") и при запуске из CLI главного процесса могут вести себя несколько иначе, поскольку команды отправляются по одной, каждая в собственном сеансе CLI. Аналогично, некоторые редкие команды ("show events", "wait") активно отслеживают ввод или закрытие CLI и немедленно прерываются при закрытии CLI. Через CLI главного процесса они не будут работать ожидаемым образом, поскольку после каждой команды её вход закрывается. В таких редких случаях лучше может подойти вариант "@@", описанный ниже.

<a id="entry-9-4-1-entry-2"></a>

**`@@<[!]pid> [command...]`**

```haproxy
@@<[!]pid> [command...]
```

Этот префикс или команда очень похож на описанный выше префикс "@", но переходит в рабочий процесс, передаёт ему всю командную строку без изменений и остаётся там до завершения команды. Точки с запятой тоже передаются, что позволяет выполнить в рабочем процессе всю последовательность команд. Соединение с рабочим процессом остаётся открытым до выполнения списка команд. Любые данные, отправленные после команд, пересылаются в CLI рабочего процесса, могут быть прочитаны выполняемыми командами и будут потеряны для CLI главного процесса. Таким образом обеспечивается полноценное двунаправленное соединение с рабочим процессом. Поэтому пользователи таких команд должны внимательно дожидаться завершения команды, прежде чем отправлять новые команды в CLI главного процесса.

Вместо выполнения одной команды можно открыть полностью интерактивный сеанс в рабочем процессе, не указав команду (то есть введя "@@1" в отдельной строке). Такой сеанс завершается закрытием соединения или выходом из сеанса рабочего процесса (командой "quit"). В этом случае режим приглашения сокета главного процесса (interactive, prompt, timed) передаётся рабочему процессу.

Ошибки: известно, что протокол sockpair@, используемый для связи между главным и рабочим процессами, ненадёжно работает в macOS из-за проблемы в реализации sendmsg(2) в macOS. Из-за этого команда может остаться без ответа.

Примеры:

```shell
# gracefully close connections and delete a server once idle (wait max 10s)
$ socat -t 11 /var/run/haproxy-master.sock - <<< \
   "@@1 disable server app2/srv36; \
   wait 10000 srv-removable app2/srv36; \
   del server app2/srv36"

# forcefully close connections and quickly delete a server
$ socat /var/run/haproxy-master.sock - <<< \
   "@@1 disable server app2/srv36; \
   shutdown sessions server app2/srv36; \
   wait 100 srv-removable app2/srv36; \
   del server app2/srv36"

# show messages arriving to this ring in real time ("tail -f" equivalent)
$ (echo "show events buf0 -w"; read) | socat /var/run/haproxy-master.sock -
```

<a id="entry-9-4-1-expert-mode"></a>

**`expert-mode [on|off]`**

```haproxy
expert-mode [on|off]
```

Эта команда включает "expert-mode" для каждого рабочего процесса, к которому обращаются из CLI главного процесса. В сочетании с "mcli-debug-mode" также активирует команду в главном процессе. В приглашении CLI главного процесса отображается флаг "e".

См. также "expert-mode" в [разделе 9.3](/ru/haproxy/statistics-and-monitoring/#section-9-3) и "mcli-debug-mode" в 9.4.1.

<a id="entry-9-4-1-experimental-mode"></a>

**`experimental-mode [on|off]`**

```haproxy
experimental-mode [on|off]
```

Эта команда включает "experimental-mode" для каждого рабочего процесса, к которому обращаются из CLI главного процесса. В сочетании с "mcli-debug-mode" также активирует команду в главном процессе. В приглашении CLI главного процесса отображается флаг "x".

См. также "experimental-mode" в [разделе 9.3](/ru/haproxy/statistics-and-monitoring/#section-9-3) и "mcli-debug-mode" в 9.4.1.

<a id="entry-9-4-1-hard-reload"></a>

**`hard-reload`**

```haproxy
hard-reload
```

Эта команда делает то же, что "reload" через CLI главного процесса, но выполняет жёсткую остановку (-st) вместо остановки (-sf) прежнего процесса. Это означает, что прежний процесс ничего не дожидается перед выходом, поэтому все соединения будут закрыты.

См. также команду "reload".

<a id="entry-9-4-1-mcli-debug-mode"></a>

**`mcli-debug-mode [on|off]`**

```haproxy
mcli-debug-mode [on|off]
```

Это ключевое слово включает в CLI главного процесса специальный режим, в котором доступны все ключевые слова, предназначенные для CLI рабочего процесса. Так можно отлаживать главный процесс. После включения новые доступные ключевые слова CLI можно вывести командой "help". В сочетании с "experimental-mode" или "expert-mode" доступно ещё больше ключевых слов. В приглашении CLI главного процесса отображается флаг "d".

<a id="entry-9-4-1-prompt"></a>

**`prompt`**

```haproxy
prompt
```

При включённом приглашении (через команду "prompt") в нём отображается контекст, с которым работает CLI. Главный процесс обозначается строкой "master", остальные процессы — своим PID. Если последняя перезагрузка завершилась с ошибкой, приглашение главного процесса меняется на "master[ReloadFailed]\>", чтобы было видно, что процесс всё ещё работает с прежней конфигурацией, а новая не действует.

Приглашение CLI главного процесса может отображать несколько флагов включённых режимов: "d" для mcli-debug-mode, "e" для expert-mode и "x" для experimental-mode.

Пример:

```shell
$ socat /var/run/haproxy-master.sock -
prompt
master> expert-mode on
master(e)> experimental-mode on
master(xe)> mcli-debug-mode on
master(xed)> @1
95191(xed)>
```

<a id="entry-9-4-1-reload"></a>

**`reload`**

```haproxy
reload
```

Главный процесс HAProxy также можно перезагрузить командой "reload", которая действует так же, как `kill -USR2` для главного процесса, если пользователь имеет как минимум права "operator" или "admin".

Команда позволяет выполнить синхронную перезагрузку и возвращает её статус после завершения. При разборе результата инструментом учитывайте тайм-аут: статус возвращается только после разбора конфигурации и создания нового рабочего процесса через fork. Команда "socat" по умолчанию использует тайм-аут 0.5s, поэтому при слишком долгой перезагрузке завершится до вывода сообщения. У "ncat" тайм-аута по умолчанию нет. При сборке с USE_SHM_OPEN=1 команда reload также может выгружать startup-logs главного процесса.

Пример:

```shell
$ echo "reload" | socat -t300 /var/run/haproxy-master.sock stdin
Success=1
--
[NOTICE]   (482713): haproxy version is 2.7-dev7-4827fb-69
[NOTICE]   (482713): path to executable is ./haproxy
[WARNING]  (482713): config: 'http-request' rules ignored for proxy 'frt1' as they require HTTP mode.
[NOTICE]   (482713): New worker (482720) forked
[NOTICE]   (482713): Loading success.

$ echo "reload" | socat -t300 /var/run/haproxy-master.sock stdin
Success=0
--
[NOTICE]   (482886): haproxy version is 2.7-dev7-4827fb-69
[NOTICE]   (482886): path to executable is ./haproxy
[ALERT]    (482886): config: parsing [test3.cfg:1]: unknown keyword 'Aglobal' out of section.
[ALERT]    (482886): config: Fatal errors found in configuration.
[WARNING]  (482886): Loading failure!

$
```

Команда reload выполняется в CLI главного процесса последней; все последующие команды игнорируются. После возврата статуса reload закрывает соединение с CLI.

Учтите, что перезагрузка закрывает все соединения с CLI главного процесса. См. также команду "hard-reload".

<a id="entry-9-4-1-show-proc"></a>

**`show proc [debug]`**

```haproxy
show proc [debug]
```

В CLI главного процесса предусмотрена команда 'show proc' для контроля процессов.

Пример:

```shell
$ echo 'show proc' | socat /var/run/haproxy-master.sock -
#<PID>          <type>          <reloads>       <uptime>        <version>
1162            master          5 [failed: 0]   0d00h02m07s     2.5-dev13
# workers
1271            worker          1               0d00h00m00s     2.5-dev13
# old workers
1233            worker          3               0d00h00m43s     2.0-dev3-6019f6-289
```

В этом примере главный процесс перезагружался 5 раз, но один из старых рабочих процессов всё ещё работает и пережил 3 перезагрузки. Можно обратиться к CLI этого рабочего процесса, чтобы выяснить причину.

Параметр 'debug' выводит отладочные подробности; сейчас это FD для связи IPC. Учтите, что стабильность отладочного вывода между версиями haproxy не гарантируется.

<a id="entry-9-4-1-show-startup-logs"></a>

**`show startup-logs`**

```haproxy
show startup-logs
```

Для корректной работы в CLI главного процесса HAProxy должен быть собран с USE_SHM_OPEN=1, иначе будут видны не все сообщения.

Как и аналогичная команда на сокете статистики, эта команда показывает сообщения запуска HAProxy. Однако она выгружает сообщения не текущего рабочего процесса, а последнего запуска или перезагрузки, то есть может вывести сообщения разбора конфигурации при неудачной перезагрузке.

Эти сообщения также выгружаются командой "reload".

## 9.5. Файл статистики {#section-9-5}

Так называемый stats-file позволяет при запуске процесса предварительно загрузить ненулевые значения внутренних счётчиков haproxy. Его основное назначение — сохранять статистику рабочих процессов при перезагрузках. В stats-file содержится лишь часть всей публикуемой статистики haproxy, поскольку предварительно загружать имеет смысл только значения типа метрик.

В настоящее время stats-file поддерживает только счётчики прокси. Это позволяет предварительно загружать значения для фронтендов, бэкендов, серверов и слушателей. Однако в stats-file сохраняются только экземпляры объектов с непустым GUID. Это гарантирует загрузку значения для объекта с совпадающими типом и GUID, даже если другие параметры отличаются.

Команда CLI "dump stats-file" предназначена для создания stats-file. Его формат определяется внутренней реализацией и может свободно меняться и расширяться в будущем. Он рассчитан на совместимость как минимум между выпусками соседних стабильных веток haproxy, но при загрузке stats-file в процесс, работающий на более старой версии, могут потребоваться дополнительные настройки.
