الأقسام الموضحة أدناه أقل شيوعًا في الاستخدام، وعادةً لا تدعم سوى عدد قليل من المعاملات. لا توجد أي علاقة ضمنية بين أي منها. تبدأ جميعها باستخدام كلمة مفتاحية واحدة. لا يُسمح بأي منها قبل قسم "global". قد يكون دعم بعضها مشروطًا بخيارات البناء (مثل أي شيء متعلق بـ SSL).

## 12.1. التتبع {#section-12-1}

لأغراض التصحيح، من الممكن تنشيط التتبع على أحد الأنظمة الفرعية لـ HAProxy. سيؤدي ذلك إلى إخراج رسائل تصحيح حول نظام فرعي محدد. إنها أداة قوية جدًا لتشخيص المشكلات. يمكن تهيئة التتبع ديناميكيًا عبر واجهة CLI. من الممكن أيضًا تعريف بعض الإعدادات مسبقًا في ملف الإعداد، في أقسام مخصصة باسم "traces". يمكن العثور على مزيد من التفاصيل حول التتبع في دليل الإدارة. تظل أداةً للمطورين تُستخدم خلال جلسات التصحيح المعقدة. إنها مطوَّلة جدًا وذات تكلفة، لذا استخدمها بحذر. ولأنها أداة للمطورين، فلا يوجد أي ضمان بشأن التوافق مع الإصدارات السابقة لهذا القسم.

<a id="entry-12-1-traces"></a>

**`traces`**

```haproxy
traces
```

يبدأ قسم traces جديدًا. يمكن استخدام قسم "traces" واحد أو عدة أقسام. تُقيَّم جميع التوجيهات بترتيب التصريح بها، بحيث تتجاوز الأخيرة منها ما قبلها.

<a id="entry-12-1-trace"></a>

**`trace <source> <args...>`**

```haproxy
trace <source> <args...>
```

يهيئ التتبع على نظام فرعي "trace". يمكن العثور على كل منها في دليل الإدارة، وهي تتبع الصياغة نفسها تمامًا. سيُصدر أي خرج كان سينتجه أمر "trace" خلال مرحلة تحليل القسم. في معظم الأحيان ستكون هذه أخطاء وتحذيرات، لكن بعض الأوامر غير المكتملة قد تعرض قائمة بالخيارات المسموح بها. هذا الأمر غير مخصص للاستخدام المنتظم؛ عمومًا لن يقترحه سوى المطورين خلال جلسات تصحيح معقدة. من المهم أن تضع في اعتبارك أنه، تبعًا لمستوى التتبع وتفاصيله، قد يؤدي تمكين التتبع إلى تدهور حاد في الأداء العام. يرجى الرجوع إلى دليل الإدارة للاطلاع على صياغة العبارات.

مثال:

```text
ring buf1
  size 10485760 # 10MB
  format timed
  backing-file /tmp/h1.traces

ring buf2
  size 10485760 # 10MB
  format timed
  backing-file /tmp/h2.traces

traces
  trace h1 sink buf1 level developer verbosity complete start now
  trace h2 sink buf1 level developer verbosity complete start now
```

## 12.2. قوائم المستخدمين {#section-12-2}

من الممكن التحكم في الوصول إلى أقسام frontend/backend/listen أو إلى واجهة إحصاءات http بالسماح للمستخدمين الموثَّقين والمخوَّلين فقط. للقيام بذلك، يلزم إنشاء قائمة مستخدمين واحدة على الأقل وتعريف المستخدمين.

<a id="entry-12-2-userlist"></a>

**`userlist <listname>`**

```haproxy
userlist <listname>
```

ينشئ قائمة مستخدمين جديدة بالاسم `<listname>`. يمكن استخدام العديد من قوائم المستخدمين المستقلة لتخزين بيانات المصادقة والتفويض لعملاء مستقلين.

<a id="entry-12-2-group"></a>

**`group <groupname> [users <user>,<user>,(...)]`**

```haproxy
group <groupname> [users <user>,<user>,(...)]
```

يضيف المجموعة `<groupname>` إلى قائمة المستخدمين الحالية. من الممكن أيضًا إرفاق مستخدمين بهذه المجموعة باستخدام قائمة أسماء مفصولة بفواصل تسبقها الكلمة المفتاحية "users".

<a id="entry-12-2-user"></a>

**`user <username> [password|insecure-password <password>]`**

```haproxy
user <username> [password|insecure-password <password>]
                [groups <group>,<group>,(...)]
```

يضيف المستخدم `<username>` إلى قائمة المستخدمين الحالية. يمكن استخدام كلمات المرور الآمنة (المشفرة) وغير الآمنة (غير المشفرة). تُقيَّم كلمات المرور المشفرة باستخدام الدالة crypt(3)، لذا تُدعم خوارزميات مختلفة تبعًا لقدرات النظام. فعلى سبيل المثال، تدعم أنظمة Linux الحديثة المبنية على Glibc كلًّا من MD5 و SHA-256 و SHA-512، وكذلك بالطبع الأسلوب الكلاسيكي المبني على DES لتشفير كلمات المرور.

تنبيه: كن على علم بأن استخدام كلمات المرور المشفرة قد يتسبب في زيادة كبيرة في استهلاك المعالج، تبعًا لعدد الطلبات والخوارزمية المستخدمة. بالنسبة إلى أي من الصيغ المُجزَّأة (hashed)، يجب معالجة كلمة المرور لكل طلب عبر الخوارزمية المختارة قبل أن يمكن مقارنتها بالقيمة المحددة في ملف الإعداد. صُممت معظم الخوارزميات الحالية عمدًا لتكون مكلفة حسابيًا لتحقيق مقاومة هجمات القوة الغاشمة. فهي لا تُجزِّئ كلمة المرور النصية مع إضافة الملح مرة واحدة فحسب، بل آلاف المرات. يمكن أن يتحول هذا سريعًا إلى عامل رئيسي في استهلاك HAProxy الإجمالي للمعالج، بل قد يؤدي إلى انهيار التطبيقات!

لمعالجة الاستهلاك المرتفع للمعالج بواسطة دوال التجزئة، يتمثل أحد الأساليب في تقليل عدد جولات دالة التجزئة (خوارزميات عائلة SHA) أو خفض "التكلفة" (cost) الخاصة بالدالة، إذا كانت الخوارزمية تدعم ذلك.

كملاحظة جانبية، من المعروف أن تطبيقات musl (مثل Alpine Linux) أبطأ من نظيراتها glibc عند حساب قيم التجزئة، لذا قد ترغب في أخذ هذا الجانب في الاعتبار أيضًا.

تُعامَل جميع كلمات المرور كوسائط عادية، وهي بالتالي تخضع لقواعد الاقتباس والإفلات (escaping) المعتادة الواردة في [القسم 2.2](/ar/haproxy/configuration-basics/#section-2-2). لذا يُوصى بوضع كلمات المرور بين علامتَي اقتباس مفردتين.

مثال:

```text
userlist L1
  group G1 users tiger,scott
  group G2 users xdb,scott

  user tiger password $6$k6y3o.eP$JlKBx9za9667qe4(...)xHSwRv6J.C0/D7cV91
  user scott insecure-password 'elgato'
  user xdb insecure-password 'hello'

userlist L2
  group G1
  group G2

  user tiger password $6$k6y3o.eP$JlKBx(...)xHSwRv6J.C0/D7cV91 groups G1
  user scott insecure-password 'elgato' groups G1,G2
  user xdb insecure-password 'hello' groups G2
```

يرجى ملاحظة أن القائمتين متطابقتان وظيفيًا.

## 12.3. خوادم البريد {#section-12-3}

من الممكن إرسال تنبيهات بالبريد الإلكتروني عند تغير حالة الخوادم. إذا تمت تهيئة تنبيهات البريد الإلكتروني، فتُرسَل إلى كل خادم بريد مهيَّأ في قسم mailers. يُرسَل البريد إلى خوادم البريد عبر Lua (انظر examples/lua/mailers.lua).

<a id="entry-12-3-mailers"></a>

**`mailers <mailersect>`**

```haproxy
mailers <mailersect>
```

ينشئ قائمة خوادم بريد جديدة بالاسم `<mailersect>`. إنه قسم مستقل تُشير إليه واجهات وكيل (proxy) واحدة أو أكثر.

<a id="entry-12-3-mailer"></a>

**`mailer <mailername> <ip>:<port>`**

```haproxy
mailer <mailername> <ip>:<port>
```

يُعرِّف خادم بريد داخل قسم mailers.

مثال:

```text
global
    # mailers.lua file as provided in the git repository
    # adjust path as needed
    lua-load examples/lua/mailers.lua

mailers mymailers
    mailer smtp1 192.168.0.1:587
    mailer smtp2 192.168.0.2:587

backend mybackend
    mode tcp
    balance roundrobin

    email-alert mailers mymailers
    email-alert from test1@horms.org
    email-alert to test2@horms.org

    server srv1 192.168.0.30:80
    server srv2 192.168.0.31:80
```

<a id="entry-12-3-timeout-mail"></a>

**`timeout mail <time>`**

```haproxy
timeout mail <time>
```

يحدد الوقت المتاح للاتصال بخادم البريد وإرسال رسالة إليه. إذا لم يُعرَّف، فالقيمة الافتراضية هي 10 ثوانٍ. للسماح بإرسال حزمتي SYN-ACK على الأقل خلال مصافحة TCP الأولية، يُنصح بالإبقاء على هذه القيمة أعلى من 4 ثوانٍ.

مثال:

```text
mailers mymailers
    timeout mail 20s
    mailer smtp1 192.168.0.1:587
```

## 12.4. أخطاء HTTP {#section-12-4}

من الممكن التصريح على مستوى عام بعدة مجموعات من أخطاء HTTP، ليُستورد منها لاحقًا في أي قسم وكيل (proxy). يمكن الإشارة إلى المجموعة نفسها في عدة مواضع، ويمكن استيرادها كليًا أو جزئيًا.

<a id="entry-12-4-http-errors"></a>

**`http-errors <name>`**

```haproxy
http-errors <name>
```

ينشئ مجموعة http-errors جديدة بالاسم `<name>`. وهو قسم مستقل يمكن أن يشير إليه وكيل واحد أو أكثر باستخدام اسمه.

<a id="entry-12-4-errorfile"></a>

**`errorfile <code> <file>`**

```haproxy
errorfile <code> <file>
```

يربط محتويات ملف برمز خطأ HTTP

الوسائط:

```text
<code>    هو رمز حالة HTTP. حاليًا، يستطيع HAProxy توليد
          الرموز 200 و 400 و 401 و 403 و 404 و 405 و 407 و 408 و
          410 و 425 و 429 و 500 و 501 و 502 و 503 و 504.

<file>    يشير إلى ملف يحتوي على استجابة HTTP الكاملة. يُوصى باتباع
          الممارسة الشائعة بإلحاق ".http" باسم الملف حتى لا يخلط
          القراء بين الاستجابة وصفحات خطأ HTML، وباستخدام مسارات
          مطلقة، إذ تُقرأ الملفات قبل إجراء أي chroot.
```

يرجى الرجوع إلى الكلمة المفتاحية "errorfile" في [القسم 4](/ar/haproxy/proxies/) للتفاصيل.

مثال:

```text
http-errors website-1
    errorfile 400 /etc/haproxy/errorfiles/site1/400.http
    errorfile 404 /etc/haproxy/errorfiles/site1/404.http
    errorfile 408 /dev/null  # work around Chrome pre-connect bug

http-errors website-2
    errorfile 400 /etc/haproxy/errorfiles/site2/400.http
    errorfile 404 /etc/haproxy/errorfiles/site2/404.http
    errorfile 408 /dev/null  # work around Chrome pre-connect bug
```

## 12.5. المخازن الحلقية {#section-12-5}

من الممكن التصريح على مستوى عام بمخازن حلقية (ring buffers) لتُستخدم وجهةً لخوادم السجلات أو التتبع.

<a id="entry-12-5-ring"></a>

**`ring <ringname>`**

```haproxy
ring <ringname>
```

ينشئ مخزنًا حلقيًا جديدًا بالاسم `<ringname>`.

<a id="entry-12-5-backing-file"></a>

**`backing-file <path>`**

```haproxy
backing-file <path>
```

يستبدل هذا الخيار تخصيص الذاكرة المعتاد بملف مُعيَّن في ذاكرة RAM لتخزين المخزن الحلقي. قد يكون ذلك مفيدًا لجمع التتبعات أو السجلات لأغراض التحليل البعدي للأعطال دون الحاجة إلى إرفاق عميل بطيء بواجهة CLI. ستستبدل المحتويات الأحدث المحتويات الأقدم تلقائيًا بحيث تكون أحدث المحتويات متاحة دائمًا. ستكون المحتويات المكتوبة إلى المخزن الحلقي مرئية في ذلك الملف بعد توقف العملية (وفي معظم الحالات ستظهر حتى بعد وقت قصير جدًا، لكن لا يوجد مثل هذا الضمان لأن الكتابات ليست متزامنة).

عند استخدام هذا الخيار، تنخفض مساحة التخزين الإجمالية بمقدار حجم "struct ring" الذي يبدأ عند بداية المساحة واللازم لاستعادة محتوياتها. سيُنشأ الملف بملكية المستخدم الذي بدأ التشغيل وبالنمط 0600، وسيكون بالحجم المهيَّأ بواسطة التوجيه "size". عند تحليل التوجيه (أي حتى أثناء فحوصات الإعداد)، تُعاد تسمية أي ملف موجود غير فارغ أولًا بإضافة اللاحقة الإضافية ".bak"، ويُحذف أي ملف سابق موجود باللاحقة ".bak". يضمن هذا ألا تمحو إعادة التحميل الفورية أو إعادة تشغيل العملية معلومات تصحيح ثمينة، وأن يبقى الوقت متاحًا لمسؤول كي يلاحظ ملف ".bak" الجديد هذا ويؤرشفه إن لزم. وعليه، بعد الانهيار سيحتوي الملف المحدد بـ `<path>` على أحدث المعلومات، وإذا أُعيد تشغيل الخدمة فإن الملف "`<path>`.bak" سيحملها بدلًا منه. ويعني هذا أن سعة التخزين الإجمالية المطلوبة ستكون ضعف حجم المخزن الحلقي. تُتجاهل بصمت إخفاقات تدوير الملف، لذا يكفي وضع الملف في دليل بلا أذونات كتابة لتجنب ملف النسخة الاحتياطية إن لم يكن مرغوبًا فيه.

تحذير: هناك تبعات تتعلق بالاستقرار والأمان في استخدام هذه الميزة. أولًا، إسناد المخزن الحلقي إلى جهاز بطيء (مثل قرص صلب فيزيائي) قد يسبب تباطؤًا محسوسًا أثناء عمليات الوصول، وربما حتى حالات ذعر (panics) إذا تنافست خيوط كثيرة على الوصول. ثانيًا، عملية خارجية تعدل المساحة قد تتسبب في انهيار عملية haproxy أو في كتابتها فوق جزء من ذاكرتها نفسها بتتبعات. ثالثًا، إذا امتلأ نظام الملفات قبل المخزن الحلقي، فقد تتسبب الكتابات إلى المخزن الحلقي في انهيار العملية.

المعلومات الموجودة في هذا المخزن الحلقي مهيكلة وليست قابلة للقراءة مباشرة باستخدام محرر نصوص (رغم أن معظمها يبدو بالكاد مقروءًا). خرج هذا الملف مخصص للمطورين فقط.

<a id="entry-12-5-description"></a>

**`description <text>`**

```haproxy
description <text>
```

الوصف سلسلة وصف اختيارية للمخزن الحلقي. سيظهر على واجهة CLI. افتراضيًا، يُعاد استخدام `<name>` لتعبئة هذا الحقل.

<a id="entry-12-5-format"></a>

**`format <format>`**

```haproxy
format <format>
```

الصيغة المستخدمة لتخزين الأحداث في المخزن الحلقي.

الوسائط:

```text
<format> هي صيغة السجل المستخدمة عند توليد رسائل syslog. يمكن أن
          تكون إحدى الصيغ التالية:

  iso     رسالة تحتوي على تاريخ ISO فقط، يتبعه النص. تُحذف
          الـ PID واسم العملية واسم النظام. صُممت هذه
          لتُستخدم مع خادم سجلات محلي.

  local   مماثلة لصيغة رسالة syslog وفق rfc3164 باستثناء أن حقل
          اسم المضيف محذوف. هذه هي القيمة الافتراضية.
          ملاحظة: الخيار "log-send-hostname" يحوّل الافتراضي إلى
          rfc3164.

  raw     رسالة تحتوي على النص فقط. يُحذف المستوى والـ PID والتاريخ
          والوقت واسم العملية واسم النظام. صُممت هذه لتُستخدم في
          الحاويات أو أثناء التطوير، حيث تعتمد درجة الخطورة
          فقط على واصف الملف المستخدم (stdout/stderr). هذه هي
          القيمة الافتراضية.

  rfc3164 صيغة رسالة syslog وفق RFC3164.
          (https://tools.ietf.org/html/rfc3164)

  rfc5424 صيغة رسالة syslog وفق RFC5424.
          (https://tools.ietf.org/html/rfc5424)

  short   رسالة تحتوي على مستوى فقط بين قوسين زاويين مثل
          '<3>'، يتبعه النص. تُحذف الـ PID والتاريخ والوقت واسم
          العملية واسم النظام. صُممت هذه لتُستخدم مع خادم سجلات
          محلي. هذه الصيغة متوافقة مع ما يستهلكه مسجِّل systemd.

 priority رسالة تحتوي على مستوى فقط مع فئة syslog بين قوسين
          زاويين مثل '<63>'، يتبعه النص. تُحذف الـ PID والتاريخ
          والوقت واسم العملية واسم النظام. صُممت هذه لتُستخدم
          مع خادم سجلات محلي.

  timed   رسالة تحتوي على مستوى فقط بين قوسين زاويين مثل
          '<3>'، يتبعه تاريخ ISO ثم النص. تُحذف الـ PID واسم
          العملية واسم النظام. صُممت هذه لتُستخدم مع خادم
          سجلات محلي.
```

<a id="entry-12-5-maxlen"></a>

**`maxlen <length>`**

```haproxy
maxlen <length>
```

الطول الأقصى لرسالة حدث مخزنة في المخزن الحلقي، شاملةً الترويسة المنسَّقة. إذا كانت رسالة الحدث أطول من `<length>`، فستُقتطع إلى هذا الطول.

<a id="entry-12-5-server"></a>

**`server <name> <address> [param*]`**

```haproxy
server <name> <address> [param*]
```

يُستخدم لتهيئة خادم syslog عبر TCP لإعادة توجيه الرسائل من المخزن الحلقي. يدعم هذا جميع معاملات "server" الواردة في الفقرة 5.2. بعض هذه المعاملات غير ذي صلة بأقسام "ring". نقطة مهمة: نادرًا ما يوجد مبرر لإضافة أكثر من خادم واحد إلى مخزن حلقي، لأن جميع الخوادم ستتلقى النسخة نفسها تمامًا من محتويات المخزن، وعليه سيتقدم المخزن بسرعة أبطأ خادم. إذا لم يستجب أحد الخوادم، فسيمنع ذلك إزالة الرسائل القديمة وقد يمنع إدراج رسائل جديدة في المخزن. الطريقة الصحيحة لإرسال الرسائل إلى خوادم متعددة هي استخدام مخزن حلقي منفصل لكل خادم سجلات، لا إرفاق عدة خوادم بالمخزن الحلقي نفسه. لاحظ أن توجيه الخادم المخصص "log-proto" يُستخدم لتعيين البروتوكول المستخدم لإرسال الرسائل.

<a id="entry-12-5-size"></a>

**`size <size>`**

```haproxy
size <size>
```

هذا هو الحجم الاختياري بالبايت للمخزن الحلقي. تُضبط القيمة الافتراضية على BUFSIZE.

<a id="entry-12-5-timeout-connect"></a>

**`timeout connect <timeout>`**

```haproxy
timeout connect <timeout>
```

يضبط أقصى وقت للانتظار حتى تنجح محاولة اتصال بخادم.

الوسائط:

```text
<timeout> هي قيمة المهلة محددةً بالميلي ثانية افتراضيًا، لكن يمكن
          التعبير عنها بأي وحدة أخرى إذا لُحق الرقم بوحدته،
          كما هو مشروح في أعلى هذا المستند.
```

<a id="entry-12-5-timeout-server"></a>

**`timeout server <timeout>`**

```haproxy
timeout server <timeout>
```

يضبط أقصى وقت لبقاء البيانات المعلقة في مخزن الإخراج.

الوسائط:

```text
<timeout> هي قيمة المهلة محددةً بالميلي ثانية افتراضيًا، لكن يمكن
          التعبير عنها بأي وحدة أخرى إذا لُحق الرقم بوحدته،
          كما هو مشروح في أعلى هذا المستند.
```

مثال:

```text
global
    log ring@myring local7

ring myring
    description "My local buffer"
    format rfc5424
    maxlen 1200
    size 32764
    timeout connect 5s
    timeout server 10s
    server mysyslogsrv 127.0.0.1:6514 log-proto octet-count
```

## 12.6. إعادة توجيه السجلات {#section-12-6}

من الممكن التصريح بقسم واحد أو عدة أقسام لإعادة توجيه السجلات، وسيعيد HAProxy توجيه جميع رسائل السجل المستلمة إلى قائمة خوادم سجلات.

<a id="entry-12-6-log-forward"></a>

**`log-forward <name>`**

```haproxy
log-forward <name>
```

ينشئ وكيل إعادة توجيه سجلات جديدًا يُعرَّف بالاسم `<name>`.

<a id="entry-12-6-backlog"></a>

**`backlog <conns>`**

```haproxy
backlog <conns>
```

يقدم تلميحات إلى النظام بشأن الحجم التقريبي المطلوب لطابور الاستماع المتراكم عند قبول الاتصالات.

<a id="entry-12-6-bind"></a>

**`bind <addr> [param*]`**

```haproxy
bind <addr> [param*]
```

يُستخدم لتهيئة مستمع سجلات انسيابي (stream) لاستقبال الرسائل المطلوب إعادة توجيهها. يدعم هذا معاملات "bind" الواردة في الفقرة 5.1 بما في ذلك تلك المتعلقة بـ ssl، لكن بعض العبارات مثل "alpn" قد تكون غير ذات صلة ببروتوكول syslog عبر TCP. تدعم هذه المستمعات كلا الوضعين "Octet Counting" و "Non-Transparent-Framing" كما هما محددان في rfc-6587.

<a id="entry-12-6-dgram-bind"></a>

**`dgram-bind <addr> [param*]`**

```haproxy
dgram-bind <addr> [param*]
```

يُستخدم لتهيئة مستمع سجلات رزم بيانات (datagram) لاستقبال الرسائل المطلوب إعادة توجيهها. يجب أن تكون العناوين بصيغة IPv4 أو IPv6 يتبعها منفذ. يدعم هذا بعض معاملات "bind" الواردة في الفقرة 5.1، من بينها "interface" و "namespace" و "transparent"، فيما تُتجاهل البقية بصمت لعدم ملاءمتها لحالة UDP/syslog.

<a id="entry-12-6-log-global"></a>

**`log global`**

```haproxy
log global
log <target> [len <length>] [format <format>] [sample <ranges>:<sample_size>]
    <facility> [<level> [<minlevel>]]
```

يُستخدم لتهيئة خوادم السجلات الهدف. راجع وثائق الوكلاء لمزيد من التفاصيل. إذا لم تُحدَّد صيغة، يحاول HAProxy الحفاظ على صيغة السجل الواردة. تُتجاهل الـ facility المهيأة، إلا إذا كانت الرسالة الواردة لا تحمل facility بينما يكون وجوده إلزاميًا في الصيغة الصادرة. إذا لم يتوفر أي طابع زمني في صيغة الإدخال، لكن الحقل موجود في صيغة الإخراج، فسيستخدم HAProxy التاريخ المحلي.

مثال:

```text
global
   log stderr format iso local7

ring myring
    description "My local buffer"
    format rfc5424
    maxlen 1200
    size 32764
    timeout connect 5s
    timeout server 10s
    # syslog tcp server
    server mysyslogsrv 127.0.0.1:514 log-proto octet-count

log-forward sylog-loadb
    dgram-bind 127.0.0.1:1514
    bind 127.0.0.1:1514
    # all messages on stderr
    log global
    # all messages on local tcp syslog server
    log ring@myring local0
    # load balance messages on 4 udp syslog servers
    log 127.0.0.1:10001 sample 1:4 local0
    log 127.0.0.1:10002 sample 2:4 local0
    log 127.0.0.1:10003 sample 3:4 local0
    log 127.0.0.1:10004 sample 4:4 local0
```

<a id="entry-12-6-maxconn"></a>

**`maxconn <conns>`**

```haproxy
maxconn <conns>
```

يضبط الحد الأقصى لعدد الاتصالات المتزامنة على مُعيد توجيه السجلات. القيمة الافتراضية هي 10.

<a id="entry-12-6-timeout-client"></a>

**`timeout client <timeout>`**

```haproxy
timeout client <timeout>
```

يضبط أقصى وقت خمول على جانب العميل.

<a id="entry-12-6-option-assume-rfc6587-ntf"></a>

**`option assume-rfc6587-ntf`**

```haproxy
option assume-rfc6587-ntf
```

يوجّه HAProxy إلى معاملة تدفقات سجلات TCP الواردة دائمًا على أنها تستخدم التأطير غير الشفاف (non-transparent framing). يبسّط هذا الخيار منطق التأطير ويضمن معالجة متسقة للرسائل، وهو مفيد على نحو خاص عند التعامل مع محارف بداية مشوَّهة التكوين.

<a id="entry-12-6-option-dont-parse-log"></a>

**`option dont-parse-log`**

```haproxy
option dont-parse-log
```

يمكّن HAProxy من ترحيل رسائل syslog دون محاولة تحليلها وإعادة هيكلتها، وهو أمر مفيد لإعادة توجيه رسائل قد لا تتقيد بالصيغ التقليدية. ينبغي استخدام هذا الخيار مع إعداد format raw على أهداف سجل الوجهة لضمان الحفاظ على محتوى الرسالة الأصلي.

<a id="entry-12-6-option-host"></a>

**`option host { replace | fill | keep | append }`**

```haproxy
option host { replace | fill | keep | append }
```

يضبط استراتيجية المضيف التي ينبغي استخدامها على قسم log-forward فيما يخص حقل اسم مضيف syslog للرسائل الصادرة بصيغة rfc3164 أو rfc5424.

      replace إذا كانت رسالة الإدخال تحتوي بالفعل على قيمة لحقل hostname،
              فسنستبدلها بعنوان IP المصدر للمرسِل.
              إذا لم تحتوِ رسالة الإدخال على قيمة لحقل hostname
              (أي: '-' في رسالة rfc5424 أو رسالة غير مطابقة لـ rfc3164
              أو rfc5424)، فسنستخدم عنوان IP المصدر للمرسِل
              كقيمة لحقل hostname.

      fill    إذا كانت رسالة الإدخال تحتوي بالفعل على قيمة لحقل hostname،
              فسنحتفظ بها.
              إذا لم تحتوِ رسالة الإدخال على قيمة لحقل hostname
              (أي: '-' في رسالة rfc5424 أو رسالة غير مطابقة لـ rfc3164
              أو rfc5424)، فسنستخدم عنوان IP المصدر للمرسِل كقيمة
              لحقل hostname.
              (هذه هي القيمة الافتراضية)

      keep    إذا كانت رسالة الإدخال تحتوي بالفعل على قيمة لحقل hostname،
              فسنحتفظ بها.
              إذا لم تحتوِ رسالة الإدخال على قيمة لحقل hostname،
              فسنضبطها على 'localhost' (rfc3164) أو '-' (rfc5424).

      append  إذا كانت رسالة الإدخال تحتوي بالفعل على قيمة لحقل hostname،
              فسنُلحق فاصلة يتبعها عنوان IP للمرسِل.
              إذا لم تحتوِ رسالة الإدخال على قيمة لحقل hostname،
              فسنستخدم عنوان IP المصدر للمرسِل.

بالنسبة إلى جميع الخيارات أعلاه، إذا لم يكن عنوان IP المصدر للمرسِل متاحًا (أي: مقبس UNIX/ABNS)، فإن الاستراتيجية الناتجة هي "keep".

لاحظ أن هذا الخيار ذو صلة فقط بصيغتَي سجل الوجهة rfc3164 و rfc5424. فيما عدا ذلك، لن يكون لضبط الخيار أي أثر مرئي.

## 12.7. مخزن الشهادات {#section-12-7}

يستخدم HAProxy آلية تخزين داخلية لتحميل الشهادات المستخدمة في الإعداد وتخزينها. يمكن تهيئة هذا التخزين باستخدام قسم "crt-store". يتيح ذلك تهيئة تعريفات الشهادات وتحديد الملفات التي ينبغي تحميلها فيه. يجب كتابة تعريف الشهادة قبل استخدامه في أي موضع آخر من الإعداد.

crt-store [`<name>`]

يقبل "crt-store" اسمًا اختياريًا كوسيطة. إذا حُدد اسم، فيجب الإشارة إلى كل شهادة في هذا المخزن باستخدام "@`<name>`/`<crt>`" أو "@`<name>`/`<alias>`".

يمكن أيضًا تحديث الملفات في مخزن الشهادات ديناميكيًا عبر واجهة CLI. انظر "set ssl cert" في [القسم 9.3](/ar/haproxy/statistics-and-monitoring/#section-9-3) من دليل الإدارة.

الكلمات المفتاحية التالية مدعومة في قسم "crt-store":

- crt-base
- key-base
- load

<a id="entry-12-7-crt-base"></a>

**`crt-base <dir>`**

```haproxy
crt-base <dir>
```

يعيّن دليلًا افتراضيًا لجلب شهادات SSL منه عندما يُستخدم مسار نسبي مع توجيهات "crt". المواقع المطلقة المحددة لها الأولوية وتتجاهل "crt-base". عند استخدامه في crt-store، يُتجاهل crt-base الخاص بالقسم global.

<a id="entry-12-7-key-base"></a>

**`key-base <dir>`**

```haproxy
key-base <dir>
```

يعيّن دليلًا افتراضيًا لجلب مفاتيح SSL الخاصة منه عندما يُستخدم مسار نسبي مع توجيهات "key". المواقع المطلقة المحددة لها الأولوية وتتجاهل "key-base". عند استخدامه في crt-store، يُتجاهل key-base الخاص بالقسم global.

<a id="entry-12-7-load"></a>

**`load [crt <filename>] [param*]`**

```haproxy
load [crt <filename>] [param*]
```

يحمّل ملفات SSL في مخزن الشهادات. للحصول على قائمة المعاملات، انظر قسم "12.7.1. خيارات التحميل"

مثال:

```text
crt-store
    load crt "site1.crt" key "site1.key" ocsp "site1.ocsp" alias "site1"
    load crt "site2.crt" key "site2.key"

frontend in2
    bind *:443 ssl crt "@/site1" crt "site2.crt"

crt-store web
    crt-base /etc/ssl/certs/
    key-base /etc/ssl/private/
    load crt "site3.crt" alias "site3"
    load crt "site4.crt" key "site4.key"

frontend in2
    bind *:443 ssl crt "@/site1" crt "site2.crt"  crt "@web/site3" crt "@web/site4.crt"
```

### 12.7.1. خيارات التحميل {#section-12-7-1}

يحمّل ملفات SSL في مخزن الشهادات. يمكن للكلمة المفتاحية load أن تأخذ عدة معاملات مدرجة أدناه. هذه الكلمات المفتاحية قابلة للاستخدام في crt-list أيضًا.

<a id="entry-12-7-1-crt"></a>

**`crt <filename>`**

```haproxy
crt <filename>
```

هذه الوسيطة إلزامية، فهي تحمّل ملف PEM يجب أن يحتوي على الشهادة العامة، لكن يمكن أن يحتوي أيضًا على الشهادات الوسيطة والمفتاح الخاص. إذا لم يُوفر مفتاح خاص في هذا الملف، فيمكن توفير مفتاح باستخدام الكلمة المفتاحية "key".

<a id="entry-12-7-1-acme"></a>

**`acme <string>`**

```haproxy
acme <string>
```

يتيح هذا الخيار تهيئة بروتوكول ACME لشهادة معينة. هذه ميزة تجريبية تتطلب الكلمة المفتاحية "expose-experimental-directives" في القسم global.

عند استخدام الكلمة المفتاحية "acme" في crt-store، من الممكن البدء دون شهادة موجودة على القرص. وبدلًا من ذلك، سيُستخدم زوج مفاتيح مؤقت حتى تُولَّد شهادة ACME. هذا السلوك حصري لمخازن crt-store؛ فلا سطر crt-list ولا سطر ssl-f-use يمكنه تحقيق الشيء نفسه دون التصريح بمخزن crt-store أولًا.

انظر أيضًا [القسم 12.8](/ar/haproxy/other-sections/#section-12-8) ("ACME") و "domains" في هذا القسم.

<a id="entry-12-7-1-alias"></a>

**`alias <string>`**

```haproxy
alias <string>
```

وسيطة اختيارية. تتيح تسمية الشهادة باسم مستعار، بحيث يمكن الإشارة إليها به في الإعداد. يجب أن يُسبَق الاسم المستعار بـ '@/' عندما يُستدعى في موضع آخر من الإعداد.

<a id="entry-12-7-1-domains"></a>

**`domains <string>`**

```haproxy
domains <string>
```

يهيئ قائمة النطاقات التي ستُستخدم لشهادات ACME. يُستخدم أول نطاق في القائمة بوصفه CN. تُفصل النطاقات بفواصل في القائمة.

انظر أيضًا [القسم 12.8](/ar/haproxy/other-sections/#section-12-8) ("ACME") و "acme" في هذا القسم.

مثال:

```text
load crt "example.com.pem" acme LE domains "bar.example.com,foo.example.com"
```

<a id="entry-12-7-1-ips"></a>

**`ips <string>`**

```haproxy
ips <string>
```

يهيئ قائمة عناوين IP التي ستُدرَج بوصفها IP SANs في شهادة ACME. تُفصل عناوين IP بفواصل في القائمة.

قد يتطلب توليد شهادة بعناوين IP استخدام ملف التعريف "shortlived".

انظر أيضًا [القسم 12.8](/ar/haproxy/other-sections/#section-12-8) ("ACME") و "acme" و "domains" في هذا القسم.

مثال:

```text
load crt "server.pem" acme LE ips "192.0.2.1,2001:db8::1"
```

<a id="entry-12-7-1-key"></a>

**`key <filename>`**

```haproxy
key <filename>
```

هذه الوسيطة اختيارية. تحمّل مفتاحًا خاصًا بصيغة PEM. إذا كان مفتاح خاص قد عُرِّف بالفعل في "crt"، فسيحل هذا محلَّه.

<a id="entry-12-7-1-ocsp"></a>

**`ocsp <filename>`**

```haproxy
ocsp <filename>
```

هذه الوسيطة اختيارية، فهي تحمّل استجابة OCSP بصيغة DER. يمكن تحديثها عبر واجهة CLI.

<a id="entry-12-7-1-issuer"></a>

**`issuer <filename>`**

```haproxy
issuer <filename>
```

هذه الوسيطة اختيارية. تحمّل مُصدر OCSP بصيغة PEM. لتحديد الشهادة التي تنطبق عليها استجابة OCSP، تكون شهادة المُصدر ضرورية. إذا لم يُعثر على شهادة المُصدر في ملف "crt"، فيمكن تحميلها من ملف بهذه الوسيطة.

<a id="entry-12-7-1-sctl"></a>

**`sctl <filename>`**

```haproxy
sctl <filename>
```

هذه الوسيطة اختيارية. يُفعَّل دعم امتداد Certificate Transparency (RFC6962) الخاص بـ TLS. يجب أن يحتوي الملف على قائمة صالحة من الطوابع الزمنية الموقَّعة للشهادات، كما هو موصوف في RFC. يُحلَّل الملف للتحقق من الصياغة الأساسية، لكن لا يُتحقق من أي توقيعات.

<a id="entry-12-7-1-ocsp-update"></a>

**`ocsp-update [ off | on ]`**

```haproxy
ocsp-update [ off | on ]
```

يُفعِّل التحديث التلقائي لاستجابة OCSP عند الضبط على 'on'، ويعطّله فيما عدا ذلك. قيمته الافتراضية هي 'off'. لتمكين التحديث التلقائي لـ OCSP على سطر bind، يمكنك استخدام هذا الخيار في crt-store أو استخدام الخيار العام "tune.ocsp-update.mode". إذا كانت شهادة معينة مستخدمة في عدة crt-lists بقيم مختلفة للخيار 'ocsp-update'، فسيُرفَع خطأ. وبالمثل، إذا ورثت شهادة الخيار العام على سطر bind وكان لها خيار 'ocsp-update' صريح غير متوافق مضبوط في crt-list، فسيُرفَع الخطأ نفسه.

أمثلة:

إليك مثال إعداد يمكّنه باستخدام crt-list:

haproxy.cfg:

```text
frontend fe
    bind :443 ssl crt-list haproxy.list
```

haproxy.list:

```text
server_cert.pem [ocsp-update on] foo.bar
```

وإليك مثال إعداد يمكّنه باستخدام crt-store:

haproxy.cfg:

```text
crt-store
  load crt foobar.pem ocsp-update on

frontend fe
    bind :443 ssl crt foobar.pem
```

عند ضبط الخيار على 'on'، سنحاول الحصول على استجابة ocsp كلما وُجد uri لـ ocsp في شهادة الواجهة الأمامية. القيد الوحيد في هذا الوضع هو أن يكون مُصدر الشهادة معروفًا كي يمكن بناء certid الخاص بـ OCSP. ستُحدَّث كل استجابة OCSP مرة واحدة على الأقل في الساعة، وبوتيرة أكثر تكرارًا إذا كان لاستجابة OCSP معينة تاريخ انتهاء أبكر من حد الساعة هذا. سيظل هناك حد أدنى لفاصل التحديث مقداره 5 دقائق لتجنب التحديث المفرط للاستجابات ذات مدة انتهاء قصيرة جدًا أو حتى التي لا تحتوي على 'Next Update' أصلًا. بسبب هذا الحد الصارم، يرجى ملاحظة أنه عند ضبط التحديث التلقائي على 'on'، لن تُحدَّث أي استجابة OCSP حُمِّلت أثناء التهيئة قبل مرور 5 دقائق على الأقل، حتى لو كان وقت انتهائها ينتهي قبل now+5m. لا ينبغي أن يشكل هذا عبئًا كبيرًا لأن استجابة OCSP يجب أن تكون صالحة عند تحميلها أثناء التهيئة (يجب أن يكون وقت انتهائها في المستقبل)، ومن غير المرجح أن تنتهي صلاحية الاستجابة في وقت قصير كهذا بعد التهيئة. ومن جهة أخرى، إذا كانت شهادة ما تحدد uri لـ OCSP وليس لديها استجابة OCSP، فسيضمن ضبط هذا الخيار على 'on' لتلك الشهادة جلب استجابة OCSP تلقائيًا مباشرة بعد التهيئة. يمكن تهيئة الحدَّين الافتراضيين الأدنى والأقصى للتأخير (5 دقائق وساعة واحدة على التوالي) عبر الخيارين العامين "ocsp-update.maxdelay" و "ocsp-update.mindelay".

كلما جرى تحديث استجابة OCSP بواسطة مهمة التحديث التلقائي أو عقب استدعاء أمر CLI المسمى "update ssl ocsp-response"، يُصدَر سطر سجل مخصص. يتبع صيغة مخصصة تحتوي على الترويسة "`<OCSP-UPDATE>`" وتتبعها معلومات محددة متعلقة بـ OCSP: - مسار شهادة الواجهة الأمامية المقابلة - حالة تحديث رقمية - حالة تحديث نصية - عدد إخفاقات التحديث للاستجابة المعنية - عدد نجاحات التحديث للاستجابة المعنية. انظر أمر CLI المسمى "show ssl ocsp-updates" للحصول على القائمة الكاملة لرموز الأخطاء ورسائلها. يُصدَر هذا السطر بغض النظر عن نجاح تحديث استجابة OCSP المعنية أو فشله. يُرسَل طلب/استجابة OCSP وتُستقبَل عبر نسخة http_client مضبوط عليها الخيار dontlog-normal وتستخدم صيغة سجل HTTP المعتادة في حالة الخطأ (تعذُّر الوصول إلى مستجيب OCSP على سبيل المثال). إذا حدث خطأ من هذا القبيل، فسيُصدَر سطر سجل آخر يحتوي على معلومات متعلقة بـ HTTP إلى جانب سطر OCSP "الاعتيادي" (الذي سيحمل غالبًا "HTTP error" بوصفها الحالة النصية). أما إذا حدث خطأ HTTP بحت (تعذُّر الوصول إلى مستجيب OCSP على سبيل المثال)، فسيُصدَر سطر سجل إضافي يتبع صيغة سجل HTTP المعتادة. فيما يلي مثالان لمثل هذه الأسطر، أولًا سطر سجل لتحديث OCSP ناجح ثم مثال لخطأ HTTP بالسطرين المختلفين (قُسِّمت الأسطر وقُصِّر عنوان URL من أجل القراءة):

```text
<133>Mar  6 11:16:53 haproxy[14872]: <OCSP-UPDATE> /path_to_cert/foo.pem 1 \
        "Update successful" 0 1

<133>Mar  6 11:18:55 haproxy[14872]: <OCSP-UPDATE> /path_to_cert/bar.pem 2 \
        "HTTP error" 1 0
<133>Mar  6 11:18:55 haproxy[14872]: -:- [06/Mar/2023:11:18:52.200] \
        <OCSP-UPDATE> -/- 2/0/-1/-1/3009 503 217 - - SC-- 0/0/0/0/3 0/0 {} \
        "GET http://127.0.0.1:12345/MEMwQT HTTP/1.1"
```

استكشاف الأخطاء وإصلاحها: خطأ شائع قد يحدث مع شهادات Let's Encrypt هو أن يوفر حل DNS عنوان IPv6 بينما لا يملك نظامك مسار IPv6 صادرًا صالحًا. في هذه الحالة، يمكنك إما إنشاء المسار المناسب أو ضبط الخيار "httpclient.resolvers.prefer ipv4" في القسم global. في حالة خطأ "OCSP response check failure"، قد ترغب في التحقق من أن شهادة المُصدر التي قدمتها صالحة. قد تُعرَض أيضًا رسالة خطأ أدق بين قوسين بعد رسالة الخطأ "العامة". يمكن أن يحدث ذلك مع خطأي "OCSP response check failure" أو "Error during insertion".

يسمح باستخدام هذه الشهادة للتحقق من JWT أو فك تشفيره عبر المحوِّلات "jwt_verify_cert" و "jwt_decrypt_cert" أو "jwt_decrypt" عند الضبط على 'on'. قيمته الافتراضية هي 'off'.

عند ضبطه على 'on' لشهادة معينة، لن يعمل أمر CLI المسمى "del ssl cert". ولكي تُحذف الشهادة، يجب ألا تكون مستخدمة، لا لمصافحات SSL ولا للتحقق من JWT.

يمكن تغيير هذا الخيار أثناء التشغيل عبر أمرَي CLI المسميين "add ssl jwt" و "del ssl jwt". انظر أيضًا أمر CLI المسمى "show ssl jwt".

(انظر أيضًا "keytype" و "bits" و "curves").

## 12.8. ACME {#section-12-8}

acme `<name>`

يمكن تهيئة بروتوكول ACME باستخدام قسم "acme". يأخذ القسم وسيطة "`<name>`" تُستخدم لربط شهادة بالقسم.

يتيح قسم ACME تهيئة HAProxy بوصفه عميل ACMEv2. هذه الميزة تجريبية، ما يعني أنه يجب وجود "expose-experimental-directives" في القسم global حتى يمكن استخدامها.

يتوفر دليل على ويكي HAProxy
<https://github.com/haproxy/wiki/wiki/ACME:--native-haproxy>

القيود الحالية: <a id="entry-12-8-the-feature-is"></a>

**`- الميزة محدودة بتحديات http-01 و dns-01 أو dns-persist-01`**

```haproxy
- الميزة محدودة بتحديات http-01 و dns-01 أو dns-persist-01
```

في الوقت الحالي. يتعامل HAProxy مع http-01 بالكامل، لكن dns-01 و dns-persist-01 يتطلبان إما dataplaneAPI أو أداة خارجية أخرى للتخاطب مع API لمزود DNS. لا يتطلب dns-persist-01 سوى تعيين سجل TXT مرة واحدة، لذا يمكن تعيينه يدويًا دون أداة.
<a id="entry-12-8-it-is-possible"></a>

**`- من الممكن البدء دون شهادة موجودة على القرص. للقيام`**

```haproxy
- من الممكن البدء دون شهادة موجودة على القرص. للقيام
```

بذلك، يجب تهيئة الشهادة في crt-store. عند استخدام الكلمة المفتاحية "acme" في crt-store، سيُستخدم زوج مفاتيح مؤقت حتى تُولَّد شهادة ACME.
<a id="entry-12-8-the-current-haproxy"></a>

**`- بنية HAProxy الحالية نموذج غير معيق، والوصول إلى القرص`**

```haproxy
- بنية HAProxy الحالية نموذج غير معيق، والوصول إلى القرص
```

لا يُفترض أن يجري بعد تحميل الإعداد، لأن ذلك قد يعيق حلقة الأحداث، مُعطِّلًا حركة المرور على الخيط نفسه. ما يعني أن الشهادات والمفاتيح المولَّدة من HAProxy سيلزم تفريغها من خارج HAProxy باستخدام "dump ssl cert" على مقبس الإحصاءات. من الممكن أتمتة تفريغ الشهادات باستخدام dataplaneAPI أو النص البرمجي haproxy-dump-certs المتوفر في دليل admin/cli/.

يبدأ مجدول ACME عند بدء تشغيل HAProxy، وسيمرّ على الشهادات ويبدأ مهمة تجديد ACME عندما يتجاوز notAfter القيمة curtime + (notAfter - notBefore) / 12، أو 7 أيام إذا لم يكن notBefore معرفًا. بعدها ينام المجدول ويستيقظ بعد 12 ساعة. من الممكن بدء مهمة تجديد يدويًا بواسطة "acme renew". انظر أيضًا "acme status" في دليل الإدارة.

الكلمات المفتاحية التالية قابلة للاستخدام في قسم ACME:

<a id="entry-12-8-account-key"></a>

**`account-key <filename>`**

```haproxy
account-key <filename>
```

يهيئ المسار إلى مفتاح الحساب. يجب توليد المفتاح قبل إطلاق HAProxy. إذا لم تُستخدم الكلمة المفتاحية account، فسيحاول قسم acme تحميل ملف باستخدام اسم القسم "`<name>`.account.key". إذا لم يكن الملف موجودًا، فسيولّد HAProxy واحدًا باستخدام المعاملات من قسم acme.

يمكنك أيضًا توليد مفتاح خاص RSA يدويًا باستخدام openssl:

```text
openssl genrsa -out account.key 2048
```

أو مفتاح ecdsa:

```text
openssl ecparam -name secp384r1 -genkey -noout -out account.key
```

<a id="entry-12-8-acme-vars"></a>

**`acme-vars <string>`**

```haproxy
acme-vars <string>
```

يمرر متغيرات اعتباطية إلى أداة تزويد DNS الخارجية (مثل dataplaneAPI) عبر وجهة الإخراج المسماة "dpapi". الدلالات خاصة بالأداة؛ راجع وثائق أداة تزويد DNS لديك.

لا تكون هذه الكلمة المفتاحية ذات معنى إلا عندما يكون نوع التحدي "dns-01" أو "dns-persist-01".

انظر أيضًا: "challenge" و "provider-name"

<a id="entry-12-8-bits"></a>

**`bits <number>`**

```haproxy
bits <number>
```

يهيئ عدد البتات لتوليد شهادة RSA. القيمة الافتراضية هي 2048. قد يؤدي ضبط قيمة مرتفعة جدًا إلى إطلاق تحذير إذا لم تكن آلتك قوية بما يكفي. (يمكن تهيئة ذلك باستخدام "warn-blocked-traffic-after"، لكن تعطيل الحركة لفترة طويلة قد ينشّط الـ watchdog (المراقب).)

<a id="entry-12-8-challenge"></a>

**`challenge <string>`**

```haproxy
challenge <string>
```

يأخذ نوع التحدي كمعامل، ويجب أن يكون http-01 أو dns-01 أو dns-persist-01. عند عدم الاستخدام، القيمة الافتراضية هي http-01.

ينفذ dns-persist-01 مسودة draft-ietf-acme-dns-persist. على خلاف dns-01، يستخدم سجل TXT ثابتًا عند "\_validation-persist.`<domain>`" يُعيَّن مرة واحدة ولا يتغير بين التجديدات أبدًا. يجب أن يحتوي السجل على URI الحساب وسياسة اختيارية. لا يتطلب نوع التحدي هذا وصولًا كتابيًا إلى API مزود DNS عند كل تجديد.

<a id="entry-12-8-challenge-ready"></a>

**`challenge-ready <value>[,<value>]*`**

```haproxy
challenge-ready <value>[,<value>]*
```

يهيئ الشروط التي يجب استيفاؤها قبل إشعار خادم ACME بأن تحدي dns-01 جاهز للتحقق. القيم المقبولة هي:

```text
cli  - ينتظر إشارة جاهزية من مشغِّل عبر أمر CLI المسمى
       "acme challenge_ready <crt> domain <domain>" على CLI الرئيسية
       (master CLI) أو على مقبس الإحصاءات. يتيح ذلك لأداة تزويد DNS
       خارجية تأكيد تعيين سجل TXT قبل أن يواصل HAProxy.

dns  - ينفذ فحص DNS مسبقًا بتحليل سجل TXT الخاص بـ
       "_acme-challenge.<domain>" باستخدام قسم resolvers المضبوط
       باسم "default"، لا خوادم الأسماء المرجعية. لا يُقدَّم
       التحدي حتى يطابق سجل TXT الرمز المميز (token) المتوقع.
       لذا قد تتأثر النتائج بالتخزين المؤقت لـ DNS على مستوى
       المحلل. يتحكم "dns-delay" في التأخير بين محاولات التحليل.
       هذا الخيار مستقل عن أمر CLI، فلا حاجة إلى أي تدخل بشري.

       بالنسبة إلى dns-01، يُحلَّل سجل TXT عند
       "_acme-challenge.<domain>" ويجب أن يطابق الرمز المميز المتوقع.
       وبالنسبة إلى dns-persist-01، يُحلَّل سجل TXT عند
       "_validation-persist.<domain>" ولا يُتحقق إلا من وجوده.

delay - يطبق انتظارًا أوليًا مقداره "dns-delay" قبل المتابعة. بدون
        "dns"، يُقدَّم التحدي بعد انقضاء هذا التأخير. وعند الدمج مع
        "dns"، يُطبَّق الانتظار الأولي قبل بدء فحوص DNS المسبقة.

none - لا شرط جاهزية؛ يُقدَّم التحدي إلى خادم ACME فورًا دون انتظار
       أي تأكيد خارجي. لا يمكن الجمع بين هذا الخيار وغيره.
```

يمكن دمج عدة قيم بفاصلة. عندما تُحدد عدة شروط، يعالجها HAProxy بالترتيب التالي: أولًا ينتظر تأكيد CLI ("cli")، ثم يطبق التأخير الأولي ("delay")، ثم ينفذ فحوص DNS المسبقة ("dns").

هذا الخيار متوافق فقط مع نوعي التحدي dns-01 و dns-persist-01.

عند ضبط "challenge" على "dns-01" وعدم تهيئة هذا الخيار، تكون القيمة الافتراضية "cli".

عند ضبط "challenge" على "dns-persist-01" وعدم تهيئة هذا الخيار، تكون القيمة الافتراضية "dns,delay".

عند ضبط "challenge" على "dns-persist-01"، يُنفَّذ دائمًا فحص DNS انتهازي أولي قبل تقييم شروط "challenge-ready". وبما أن سجل TXT المسمى "\_validation-persist.`<domain>`" يُعيَّن مرة واحدة ولا يتغير بين التجديدات، يتحقق HAProxy وقت التجديد مما إذا كان السجل موجودًا بالفعل. إذا نجح الفحص لجميع النطاقات، قُدِّم التحدي فورًا دون المرور بخطوات "challenge-ready" (cli و delay و dns). وإذا فشل الفحص، يرتد HAProxy إلى تدفق "challenge-ready" الاعتيادي.

مثال:

```shell
# Wait for CLI confirmation, then verify DNS propagation
challenge-ready cli,dns
```

contact <string>

البريد الإلكتروني للاتصال الذي سيُربط بمفتاح الحساب لدى المرجع المصدق (CA).

<a id="entry-12-8-curves"></a>

**`curves <string>`**

```haproxy
curves <string>
```

عند استخدام نوع المفتاح ECDSA، يهيئ المنحنيات. القيمة الافتراضية هي P-384.

<a id="entry-12-8-directory"></a>

**`directory <string>`**

```haproxy
directory <string>
```

تهيئ هذه الكلمة المفتاحية عنوان URL للدليل الخاص بالمرجع المصدق الذي يستخدمه قسم acme هذا. هذه الكلمة المفتاحية إلزامية إذ لا يوجد عنوان URL افتراضي.

مثال:

```text

```

<a id="entry-12-8-dns-delay"></a>

**`dns-delay <time>`**

```haproxy
dns-delay <time>
```

يهيئ التأخير المستخدم بواسطة شرطي "challenge-ready" المسميين "delay" و "dns". القيمة وقت مُعبَّر عنه بصيغة وقت HAProxy (مثل "5m" و "300s"). القيمة الافتراضية هي 30 ثانية.

يعتمد دورها على شرطي "challenge-ready" المستخدمَين:

```text
delay     - يُقدَّم التحدي بعد انقضاء هذا التأخير، دون أي فحص
            DNS مسبق.

dns       - التأخير بين محاولتَي تحليل DNS متتاليتين.
            تُطلَق أول محاولة فورًا دون أي انتظار أولي.

dns+delay - الانتظار الأولي قبل أول محاولة تحليل DNS، والتأخير
            بين محاولات الإعادة اللاحقة.
```

لاحظ أن التحليل يمر عبر قسم resolvers المضبوط باسم "default"، لا عبر خوادم الأسماء المرجعية. لذا قد تظل النتائج متأثرة بالتخزين المؤقت لـ DNS على مستوى المحلل.

<a id="entry-12-8-dns-timeout"></a>

**`dns-timeout <time>`**

```haproxy
dns-timeout <time>
```

عندما يتضمن "challenge-ready" القيمة "dns"، يهيئ أقصى وقت مسموح به لتحليل سجل TXT بنجاح قبل إحباط التحدي. القيمة وقت مُعبَّر عنه بصيغة وقت HAProxy (مثل "10m" و "600s"). القيمة الافتراضية هي 600 ثانية.

يبدأ المؤقت من لحظة إطلاق أول محاولة تحليل DNS (بعد "dns-delay" الأولي). إذا كانت محاولة التحليل التالية ستُطلَق بعد انقضاء المهلة، أُحبط التحدي مع خطأ. يمنع هذا وقوع حلقة إعادة محاولة لا نهائية عند فشل انتشار DNS.

انظر أيضًا: "dns-delay"

<a id="entry-12-8-keytype"></a>

**`keytype <string>`**

```haproxy
keytype <string>
```

يهيئ نوع المفتاح الذي سيولَّد. يمكن أن تكون القيمة إما "RSA" أو "ECDSA". يمكنك أيضًا تهيئة "curves" لأجل ECDSA وعدد "bits" لأجل RSA. افتراضيًا تُولَّد مفاتيح EC384.

<a id="entry-12-8-map"></a>

**`map <map>`**

```haproxy
map <map>
```

يهيئ الخريطة (map) التي ستُستخدم لتخزين الرمز المميز (مفتاح) والبصمة (قيمة)، وهو أمر مفيد للرد على تحدٍّ عند استخدام حسابات متعددة. ستضيف مهمة ACME إدخالات قبل التحقق من صحة التحدي وستزيل الإدخالات في نهاية المهمة.

<a id="entry-12-8-profile"></a>

**`profile <string>`**

```haproxy
profile <string>
```

يطلب ملف تعريف شهادة محددًا من المرجع المصدق عبر تضمين حقل "profile" في طلب newOrder. ينفذ هذا مسودة draft-ietf-acme-profiles.

أسماء ملفات التعريف معرفات قصيرة خاصة بالمرجع المصدق (مثل "classic" و "shortlived"). عند ضبطها، يُرسَل اسم ملف التعريف كما هو في حمولة JSON لطلب newOrder. للمرجع المصدق حرية تجاهل الطلب أو إرجاع خطأ إذا كان ملف التعريف غير مدعوم. عند عدم الضبط، لا يُضمَّن أي حقل ملف تعريف، ويستخدم المرجع المصدق سياسة الإصدار الافتراضية لديه.

انظر <https://letsencrypt.org/docs/profiles/> لملفات تعريف Let's Encrypt.

مثال:

```shell
# Request short-lived certificates
profile shortlived
```

<a id="entry-12-8-provider-name"></a>

**`provider-name <string>`**

```haproxy
provider-name <string>
```

يعيّن اسم مزود DNS الذي يُمرَّر إلى أداة تزويد DNS الخارجية (مثل dataplaneAPI) عبر وجهة الإخراج المسماة "dpapi". القيم المقبولة خاصة بالأداة؛ راجع وثائق أداة تزويد DNS لديك.

لا تكون هذه الكلمة المفتاحية ذات معنى إلا عندما يكون نوع التحدي "dns-01" أو "dns-persist-01".

انظر أيضًا: "challenge" و "acme-vars"

<a id="entry-12-8-reuse-key"></a>

**`reuse-key { on | off }`**

```haproxy
reuse-key { on | off }
```

إذا ضُبطت على "on"، فلن يولّد HAProxy مفتاحًا خاصًا جديدًا وسيحتفظ بالسابق. يُوصى بتدوير المفاتيح الخاصة؛ لذا عند تمكين هذا الخيار يُوصى بإعادة توليد المفاتيح يدويًا بانتظام.

قد يكون هذا الخيار مفيدًا عند استخدام مفاتيح RSA أكبر من 2048، فقد تستغرق وقتًا لتوليدها وقد تبطئ الخيط الذي يقوم بذلك.

يمكن أن يكون استخدام المفتاح نفسه مفيدًا عند استخدام ذاكرة التخزين المؤقت لخادم ACME لديك، إذ يساعد ذلك على استرجاع شهادة صالحة مقابلة للمفتاح الحالي.

الإعداد الافتراضي هو "off".

مثال:

```text
global
    expose-experimental-directives
    httpclient.resolvers.prefer ipv4

frontend in
    bind *:80
    bind *:443 ssl
    http-request return status 200 content-type text/plain lf-string "%[path,field(-1,/)].%[path,field(-1,/),map(virt@acme)]\n" if { path_beg '/.well-known/acme-challenge/' }
    ssl-f-use crt "foo.example.com.pem.rsa"   acme LE1 domains "foo.example.com.pem,bar.example.com"
    ssl-f-use crt "foo.example.com.pem.ecdsa" acme LE2 domains "foo.example.com.pem,bar.example.com"

acme LE1
    directory https://acme-staging-v02.api.letsencrypt.org/directory
    account-key /etc/haproxy/letsencrypt.account.key
    contact john.doe@example.com
    challenge http-01
    keytype RSA
    bits 2048
    map virt@acme

acme LE2
    directory https://acme-staging-v02.api.letsencrypt.org/directory
    account-key /etc/haproxy/letsencrypt.account.key
    contact john.doe@example.com
    challenge http-01
    keytype ECDSA
    curves P-384
    map virt@acme
```

<a id="entry-12-8-eab-key-id"></a>

**`eab-key-id <filename>`**

```haproxy
eab-key-id <filename>
```

يهيئ المسار إلى ملف معرِّف مفتاح EAB. يوفّر المرجع المصدق بيانات الاعتماد هذه، ويجب وضعها في المسار المحدد قبل بدء HAProxy. تُستخدم أثناء إنشاء الحساب فقط.

يجب أن يحتوي الملف على سلسلة ASCII مجردة.

بيانات اعتماد EAB مطلوبة فقط أثناء إنشاء حساب ACME الأولي ويمكن إزالتها بعد ذلك، إما من الإعداد أو بإفراغ الملفات. يُتجاهَل الملف الفارغ بصمت. لا تُتجاهل محارف المسافات البيضاء، باستثناء السطر الجديد الأخير.

انظر أيضًا: "eab-mac-key" و "eab-mac-alg"

<a id="entry-12-8-eab-mac-key"></a>

**`eab-mac-key <filename>`**

```haproxy
eab-mac-key <filename>
```

يهيئ المسار إلى ملف مفتاح MAC الخاص بـ EAB. يوفّر المرجع المصدق بيانات الاعتماد هذه، ويجب وضعها في المسار المحدد قبل بدء HAProxy. تُستخدم أثناء إنشاء الحساب فقط.

يجب أن يحتوي الملف على مفتاح MAC مرمَّز بصيغة base64url.

بيانات اعتماد EAB مطلوبة فقط أثناء إنشاء حساب ACME الأولي ويمكن إزالتها بعد ذلك، إما من الإعداد أو بإفراغ الملفات. يُتجاهَل الملف الفارغ بصمت. لا تُتجاهل محارف المسافات البيضاء، باستثناء السطر الجديد الأخير.

انظر أيضًا: "eab-key-id" و "eab-mac-alg"

<a id="entry-12-8-eab-mac-alg"></a>

**`eab-mac-alg { HS256 | HS384 | HS512 }`**

```haproxy
eab-mac-alg { HS256 | HS384 | HS512 }
```

يهيئ خوارزمية MAC المستخدمة لتوقيع EAB. القيمة الافتراضية هي HS256. يجب أن يكون مفتاح MAC الخاص بـ EAB كبيرًا بما يكفي لدعم خوارزمية MAC المحددة. لا تدعم جميع المراجع المصدقة خوارزميات غير HS256.

انظر أيضًا: "eab-key-id" و "eab-mac-key"

## 12.9. فحوص الصحة {#section-12-9}

من الممكن التصريح على مستوى عام بعدة فحوص صحة يمكن أن تستخدمها الخوادم عبر كامل الإعداد، متجاوزةً تهيئة الوكيل المحلية.

<a id="entry-12-9-healthcheck"></a>

**`healthcheck <name>`**

```haproxy
healthcheck <name>
```

ينشئ فحص صحة جديدًا بالاسم `<name>`. يجب أن يكون هذا الاسم فريدًا. ينبغي استخدامه على سطر server للإشارة إلى قسم فحص صحة محدد.

<a id="entry-12-9-type"></a>

**`type <type>`**

```haproxy
type <type>
```

يحدد نوع فحص الصحة. هذا المعامل إلزامي. أنواع فحوص الصحة التالية مدعومة:

    * tcp-check
    * httpchk
    * ssl-hello-chk
    * smtpchk
    * pgsql-check
    * redis-check
    * mysql-check
    * ldap-check
    * spop-check

يستخدم كل نوع المعاملات نفسها، إن وُجدت، التي تستخدمها الخاصية المقابلة في الوكيل. فعلى سبيل المثال، يمكن تحديد طريقة الطلب و uri... للنوع "httpchk":

أمثلة:

```text
   healthcheck my-http-check
type httpchk GET /health HTTP/1.1 %[srv_name]
```

انظر أيضًا: "option tcp-check" و "option httpchk" و "option ssl-hello-chk" و "option smtpchk" و "option mysql-check" و "option pgsql-check" و "option redis-check" و "option ldap-check" و "option spop-check"

<a id="entry-12-9-http-check-comment"></a>

**`http-check comment <string>`**

```haproxy
http-check comment <string>
http-check connect [default] [port <expr>] [addr <ip>] [send-proxy]
                   [via-socks4] [ssl] [sni <sni>] [alpn <alpn>] [linger]
                   [proto <name>] [comment <msg>]
http-check disable-on-404
http-check expect [min-recv <int>] [comment <msg>]
                  [ok-status <st>] [error-status <st>] [tout-status <st>]
                  [on-success <fmt>] [on-error <fmt>] [status-code <expr>]
                  [!] <match> <pattern>
http-check send [meth <method>] [{ uri <uri> | uri-lf <fmt> }>] [ver <version>]
                [hdr <name> <fmt>]* [{ body <string> | body-lf <fmt> }]
                [comment <msg>]
http-check send-state
http-check set-var(<var-name>[,<cond>...]) <expr>
http-check set-var-fmt(<var-name>[,<cond>...]) <fmt>
http-check unset-var(<var-name>)
```

يضيف قاعدة http-check محددة لفحص صحة من نوع "httpchk". تُستخدم الصياغة نفسها الخاصة بتوجيهات الوكيل المقابل. راجع وثائق الوكيل المقابل للتفاصيل.

<a id="entry-12-9-tcp-check-comment"></a>

**`tcp-check comment <string>`**

```haproxy
tcp-check comment <string>
tcp-check connect [default] [port <expr>] [addr <ip>] [send-proxy] [via-socks4]
                  [ssl] [sni <sni>] [alpn <alpn>] [linger]
                  [proto <name>] [comment <msg>]
tcp-check expect [min-recv <int>] [comment <msg>]
                 [ok-status <st>] [error-status <st>] [tout-status <st>]
                 [on-success <fmt>] [on-error <fmt>] [status-code <expr>]
                 [!] <match> <pattern>
tcp-check send <data> [comment <msg>]
tcp-check send-lf <fmt> [comment <msg>]
tcp-check send-binary <hexstring> [comment <msg>]
tcp-check send-binary-lf <hexfmt> [comment <msg>]
tcp-check set-var(<var-name>[,<cond>...]) <expr>
tcp-check set-var-fmt(<var-name>[,<cond>...]) <fmt>
tcp-check unset-var(<var-name>)
```

يضيف قاعدة tcp-check محددة لفحص صحة من نوع "tcp-check". تُستخدم الصياغة نفسها الخاصة بتوجيهات الوكيل المقابل. راجع وثائق الوكيل المقابل للتفاصيل.
