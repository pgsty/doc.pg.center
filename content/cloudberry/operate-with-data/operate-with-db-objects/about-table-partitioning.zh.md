## 为何使用表分区 {#why-use-table-partitioning}

分区有多方面的优势，对于非常大的表（例如，大小超过数据库服务器物理内存的表）尤其如此：

- **提高查询性能**：如果大部分频繁访问的行都位于单个分区或少量分区中，查询速度可以大幅提高。分区的作用类似于索引的上层结构，使索引的关键部分更有可能容纳在内存中。
- **高效扫描**：当查询或更新访问单个分区中较大比例的数据时，顺序扫描该分区可能比使用索引更高效，因为后者需要在整张表中进行随机访问读取。
- **加快数据管理**：通过添加或删除分区，可以快速完成批量加载和删除。对分区执行 `DROP TABLE` 或 `ALTER TABLE DETACH PARTITION` 等操作，比批量 `DELETE` 操作快得多，还能避免 `VACUUM` 开销。
- **数据分层**：通过管理分区，可以将很少使用的数据迁移到更便宜、速度较慢的存储介质上。

## 分区方法 {#partitioning-methods}

Apache Cloudberry 支持以下表分区方法：

- **范围分区**：根据一个或多个键列定义的“范围”对表进行分区。分配给不同分区的值范围互不重叠。例如，可以按日期范围或业务对象标识符范围分区。每个范围包含下界，但不包含上界。
- **列表分区**：通过明确列出每个分区中包含的键值来对表进行分区。例如，按销售区域或产品线分区。
- **哈希分区**：通过为每个分区指定模数和余数来对表进行分区。每个分区存储的行满足以下条件：分区键的哈希值除以模数后，得到指定的余数。

这些方法可以组合为多级分区设计，例如，在第一级使用日期范围分区，在下一级使用列表分区。（源文档中的示意图展示了结合日期范围分区和列表分区的多级设计。）

## 分区表结构 {#partitioned-table-structure}

在 Apache Cloudberry 中对表进行分区时：

- 定义的主表（*分区表*）是一个“虚拟”表，本身不存储数据。
- 实际数据存储在各个*分区*中；除此之外，分区就是与分区表关联的普通表。每个分区存储由其*分区边界*定义的数据子集。
- 插入分区表的行会根据分区键列自动路由到正确的分区。如果某行的分区键更新后不再符合原分区的边界，Apache Cloudberry 会尝试将其移动到正确的分区。
- 创建表时，通过 `CREATE TABLE` 命令中的 `PARTITION BY` 子句定义分区。这会创建一个顶层的*根分区表*，它可以包含一级或多级*子表*（分区）。子表的直接上级表是其*父表*。*叶子分区*位于层次结构的最底端，负责存储数据；同一层次结构中的叶子分区可以位于不同深度。
- Apache Cloudberry 会自动为每个分区创建各自的分区约束，限制它可以包含的数据。查询优化器利用这些约束来确定给定查询需要扫描哪些分区。
- 分区本身也可以定义为分区表，形成*子分区*。
- 所有分区必须与其父表具有相同的列，但可以有各自独立的索引、约束和默认值。
- 分区也可以是外部表或外表，但必须确保其内容满足分区规则。外表还存在其他限制。

## 确定分区策略 {#decide-on-a-partitioning-strategy}

考虑以下问题，以确定分区是否可行：

- **表是否足够大？** 分区有利于包含数百万或数十亿条记录的大型事实表。对于小表，管理开销可能超过收益。
- **性能是否未达预期？** 如果查询速度达不到要求，可以考虑分区。
- **查询谓词是否具有可识别的访问模式？** 查找经常出现在 `WHERE` 子句中的列。例如，如果查询经常按日期筛选，按日期分区可能有益。如果按区域访问，可以考虑列表分区。
- **数据仓库是否维护一个历史数据窗口？** 如果需要保留特定时间段内的数据（例如，最近十二个月），分区（例如，按月分区）可以让你轻松删除最旧的分区并添加新分区。
- **数据能否划分为大致相等的部分？** 选择尽可能均匀划分数据的条件。如果各分区的记录数大致相同，查询性能的提升幅度可以与分区数成正比（前提是该设计支持查询条件）。

> [!TIP]
> - **避免过度分区**：创建过多分区会拖慢清理、Segment 恢复和集群扩容等管理维护任务。
> - **确保能够排除分区**：只有查询优化器能够根据查询谓词排除分区时，分区才能提高查询性能。扫描所有分区的查询反而会更慢。务必检查 `EXPLAIN` 计划。
> - **谨慎使用多级分区**：多级分区的分区文件数可能急剧增长，影响系统的可管理性，需要谨慎使用。例如，按 1000 天和 1000 个城市分区会产生一百万个分区。如果表有 100 列且采用列式存储，每个 Segment 上可能就有一亿个文件。可以考虑以带位图索引的单级分区作为替代方案，并且务必测试性能。

### 分区设计的最佳实践 {#best-practices-for-partitioning-design}

精心设计至关重要，因为不当的选择会损害查询规划和执行性能。

- **选择分区键**：

    * 选择最常出现在查询 `WHERE` 子句中的列，以便进行分区剪枝。
    * 考虑 `PRIMARY KEY` 或 `UNIQUE` 约束的要求，这些要求可能影响键的选择。
    * 考虑数据删除需求；设计分区时，将需要一起删除的数据放在同一个分区中，以便快速分离。

- **分区数量**：

    * **分区过少**：可能导致索引仍然过大、数据局部性差、缓存命中率低。
    * **分区过多**：可能导致查询规划时间更长，规划和执行期间的内存消耗更高。

- **未来增长**：

    * 考虑数据可能发生的变化。如果按客户进行 `LIST` 分区，客户数量大幅增长时会怎样？使用合理数量的分区进行 `HASH` 分区可能更加稳妥。

- **子分区**：

    * 适合进一步划分预计会比其他分区更大的分区。
    * 另一种选择是在分区键中使用多个列进行范围分区。
    * 这两种方法都容易导致分区过多，因此应适度使用。

- **开销**：

    * 只要典型查询能够通过剪枝将分区缩减到少数几个，查询规划器通常可以很好地处理包含几千个分区的层次结构。
    * 剪枝后剩余的分区越多，规划时间和内存用量就越高，尤其是对于 `UPDATE` 和 `DELETE` 命令。
    * 如果许多会话访问许多分区，服务器内存消耗可能显著增加，因为每个会话都需要将各分区的元数据加载到本地内存中。

- **工作负载类型**：

    * 与 OLTP 类型的工作负载相比，数据仓库任务可能更适合使用较多分区。在数据仓库中，相较于执行时间，规划时间往往没有那么关键。

- **充分测试**：

    * 尽早作出决定，因为对大表重新分区很慢。
    * 模拟预期工作负载以优化分区策略。不要假设分区越多越好，也不要假设越少越好。

## 限制 {#limitations}

请注意 Apache Cloudberry 分区表的以下限制：

- 分区表的每一级最多可以有 32,767 个分区。
- 不支持对复制表（使用 `DISTRIBUTED REPLICATED` 创建的表）进行分区。
- Cloudberry 查询优化器（默认使用的 GPORCA）不支持结构一致的多级分区表。对此类表的查询会使用基于 Postgres 的规划器。
- 如果叶子分区是外部表或外表，`gpbackup` 工具不会备份其中的数据。
- 要在分区表上创建唯一约束或主键约束：
    - 分区键不能包含任何表达式或函数调用。
    - 约束列必须包含所有分区键列。这是因为各个索引只能在各自分区内强制保证唯一性，而分区结构本身必须保证不同分区之间没有重复值。
- 无法创建跨越整个分区表的排他约束；此类约束只能放在各个叶子分区上。
- 不允许在同一个分区层次结构中混用临时关系和永久关系。如果分区表是永久表，其所有分区也必须是永久表；临时表同理（所有成员还必须属于同一会话）。
- **与继承的差异**：
    - 分区不能包含父表中不存在的列。不能在创建分区后为其添加列，也不能挂接列结构不同的表。
    - 分区表的 `CHECK` 和 `NOT NULL` 约束总是由所有分区继承。不能在分区表上创建标记为 `NO INHERIT` 的 `CHECK` 约束。如果父表中存在相同的约束，就不能删除分区列上的 `NOT NULL` 约束。
    - 只有在尚无分区时，才支持使用 `ONLY` 仅为分区表添加或删除约束（例如 `ALTER TABLE ONLY ...`）。一旦存在分区，对约束使用 `ONLY` 就会报错。
    - 尝试对分区表使用 `TRUNCATE ONLY` 总会报错，因为分区表本身不包含数据。
- **外部表或外表叶子分区**：
    - 在不可写的外部表／外表分区中修改数据（`INSERT`、`DELETE`、`UPDATE`、`TRUNCATE`），或者没有相应权限时修改数据，都会报错。
    - 如果涉及更新外部表／外表分区，`COPY` 就不能将数据复制*到*分区表。
    - 从外部表／外表分区执行 `COPY` 会报错，除非指定 `IGNORE EXTERNAL PARTITIONS`（将跳过这些分区）。要从包含外部表／外表叶子分区的分区表执行 `COPY`，请使用 SQL 表达式（例如 `COPY (SELECT * from my_table) TO stdout`）。
    - `VACUUM` 命令会跳过外部表和外表分区。
    - 在不可写的外部表／外表分区上执行添加或删除列、更改列的数据类型等 DDL 操作（或者没有相应权限时执行），都会报错。
