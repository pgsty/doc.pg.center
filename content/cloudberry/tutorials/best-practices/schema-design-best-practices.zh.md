Apache Cloudberry 是一个采用无共享架构的分析型数据库，与高度规范化的事务型 SMP 数据库有很大差异。Apache Cloudberry 最适合采用面向 MPP 分析处理的非规范化模式设计，例如星型模式或雪花模式：使用大型中心事实表连接多个较小的维度表。

## 数据类型 {#data-types}

### 统一使用类型 {#use-types-consistently}

表之间执行连接时，连接列应使用相同的数据类型。如果数据类型不同，Apache Cloudberry 必须动态转换其中一列的数据类型，才能正确比较数据值。考虑到这一点，可能需要增大数据类型的大小，以便与其他常用对象执行连接。

### 选择占用空间最少的数据类型 {#choose-data-types-that-use-the-least-space}

选择最高效的数据类型存储数据，可以增加数据库容量并改善查询执行。

使用 `TEXT` 或 `VARCHAR`，而不是 `CHAR`。各种字符数据类型之间没有性能差异，但使用 `TEXT` 或 `VARCHAR` 可以减少占用的存储空间。

使用能够容纳数据的最小数值数据类型。对于适合 `INT` 或 `SMALLINT` 的数据使用 `BIGINT`，会浪费存储空间。

## 存储模型 {#storage-model}

Apache Cloudberry 创建表时提供多种存储选项。必须了解何时使用堆存储与 AO 存储，以及何时使用行存储与列存储。对于大型事实表，正确选择堆存储或 AO 存储、行存储或列存储非常重要；对于小型维度表，这种选择的重要性较低。

确定存储模型时的最佳实践如下：

1. 设计并构建仅插入模型，在加载前截断每日分区。
2. 对大型分区事实表，评估并为不同分区选择最佳存储选项。整个分区表不一定适合使用同一种存储选项。例如，某些分区可以使用行存储，其他分区可以使用列存储。
3. 使用列存储时，Apache Cloudberry 的*每个* Segment 上每一列都是一个独立文件。对于列数较多的表，常访问（热）数据可以考虑列存储，不常访问（冷）数据使用行存储。
4. 应在分区级别设置存储选项。
5. 压缩大型表，以改善 I/O 性能并为集群释放空间。

### 堆存储或 AO 存储 {#heap-storage-or-append-optimized-storage}

堆存储是默认模型，也是 PostgreSQL 用于所有数据库表的模型。对于需要反复执行 `UPDATE`、`DELETE` 和单行 `INSERT` 操作的表和分区，使用堆存储。对于需要并发执行 `UPDATE`、`DELETE` 和 `INSERT` 操作的表和分区，也使用堆存储。

对于初始加载后很少更新、后续仅以批量方式插入数据的表和分区，使用 AO 存储。避免对 AO 表执行单行 `INSERT`、`UPDATE` 或 `DELETE` 操作。并发批量 `INSERT` 操作可以接受，但*绝不要*并发执行批量 `UPDATE` 或 `DELETE` 操作。

AO 存储模型不适合频繁更新的表，因为 AO 表中已更新和删除行占用的空间，无法像堆表那样高效地回收和重新使用。AO 存储适合只加载一次、很少更新、但经常查询以执行分析处理的大型表。

### 行存储或列存储 {#row-or-column-orientation}

行存储是保存数据库元组的传统方式。组成一行的各列会连续存储在磁盘上，因此一次磁盘 I/O 就能读取整行。

列存储会将列值集中存储在磁盘上。每一列都会创建一个独立文件。如果表已分区，则每个分区中的每一列都会创建一个独立文件。当查询只访问列数很多的列存储表中的少量列时，与行存储相比，I/O 成本会显著降低；查询未引用的列不需要从磁盘读取。

对于需要反复执行事务、需要更新并频繁插入数据的事务型工作负载，建议使用行存储。当表查询需要读取大量列、查询需要一行中的很多列时，使用行存储。如果查询中 `SELECT` 列表或 `WHERE` 子句选中了大多数列，使用行存储。对于通用或混合型工作负载，使用行存储，因为它能够在灵活性和性能之间取得最佳平衡。

列存储针对读操作进行了优化，但没有针对写操作进行优化；一行中的列值必须写入磁盘上的不同位置。对于列数很多、查询只访问少量列的大表，列存储可以提供最佳查询性能。

列存储的另一个优点是，同一数据类型的一组值可以比混合类型值占用更少空间，因此列存储表比行存储表占用更少的磁盘空间（相应地也需要更少的磁盘 I/O）。列存储表的压缩效果也优于行存储表。

对于查询读取少量列或在少数列上计算数据聚合的数据仓库分析型工作负载，使用列存储。对于经常单独更新、而不会修改行中其他列的列，使用列存储。宽列存储表读取完整一行所需的时间，比从行存储表读取同一行更长。必须了解，Apache Cloudberry 的*每个* Segment 上每一列都是一个独立物理文件。

## 压缩 {#compression}

Apache Cloudberry 提供多种压缩 AO 表和分区的选项。使用压缩，可以在每次磁盘读取时读取更多数据，从而改善整个系统的 I/O。最佳实践是在分区级别设置列压缩选项。

注意，添加到分区表的新分区不会自动继承表级别定义的压缩设置；添加新分区时必须*明确*定义压缩。

游程编码（RLE）压缩可以提供最高的压缩率。更高的压缩级别通常会使磁盘上的存储更紧凑，但压缩写入数据和解压读取数据时需要额外的时间和 CPU 周期。数据排序结合各种压缩选项，可以达到最高的压缩率。

绝不要对存储在压缩文件系统中的数据使用数据压缩。

测试不同的压缩类型和排序方式，为特定数据确定最佳压缩方案。例如，可以从 8 或 9 级 zstd 压缩开始，再根据结果进行调整。RLE 压缩最适合包含重复数据的文件。

## 数据分布 {#distributions}

能够使数据均匀分布的最佳分布，是 Apache Cloudberry 中最重要的因素。在 MPP 无共享架构环境中，查询的总体响应时间由所有 Segment 的完成时间决定。系统的速度取决于最慢的 Segment。如果数据存在倾斜，数据较多的 Segment 完成任务需要更长时间，因此每个 Segment 必须拥有大致相同数量的行，并执行大致相同量的处理。如果某个 Segment 要处理的数据明显多于其他 Segment，可能出现性能不佳和内存不足情况。

选择分布策略时，请考虑以下最佳实践：

- 为所有表显式定义列分布或随机分布。不要使用默认值。
- 理想情况下，使用单个列，让数据在所有 Segment 之间均匀分布。
- 不要按查询 `WHERE` 子句中使用的列进行分布。
- 不要按日期或时间戳分布。
- 分布键列的数据应包含唯一值或基数非常高的值。
- 如果单个列无法实现均匀分布，则使用最多包含两列的多列分布键。增加列通常不会使分布更均匀，还会增加哈希处理时间。
- 如果两列分布键无法实现数据均匀分布，则使用随机分布。多列分布键在多数情况下需要通过数据移动来连接表，因此相比随机分布没有优势。

Apache Cloudberry 的随机分布不是轮询分布，因此无法保证每个 Segment 上的记录数量相等。随机分布通常会落在小于百分之十的差异范围内。

连接大表时，最佳分布至关重要。执行连接时，匹配的行必须位于同一 Segment 上。如果数据没有按相同的连接列分布，就会将其中一个表所需的行动态重分布到其他 Segment。在某些情况下，会执行广播移动：每个 Segment 将自己的行发送给其他所有 Segment，而不是执行重分布移动；在重分布移动中，每个 Segment 会重新计算数据哈希，并根据哈希键将行发送到适当的 Segment。

### 本地（共置）连接 {#local-co-located-joins}

使用哈希分布将表行均匀分布到所有 Segment，并实现本地连接，可以带来显著的性能提升。当连接行位于同一 Segment 时，大部分处理可以在 Segment 实例内部完成。这种连接称为*本地*连接或*共置*连接。本地连接可以最大限度地减少数据移动；每个 Segment 独立于其他 Segment 运行，无需 Segment 之间的网络流量或通信。

要为经常连接的大表实现本地连接，应按同一列分布这些表。本地连接要求连接两边按相同的列（并且顺序相同）进行分布，*并且*连接表时使用分布子句中的所有列。分布列还必须使用相同的数据类型——尽管某些不同数据类型的值看起来可能具有相同表示形式，但它们的存储方式不同，哈希值也不同，因此会存储在不同的 Segment 上。

### 数据倾斜 {#data-skew}

数据倾斜通常是查询性能不佳和内存不足的根本原因。数据倾斜会影响扫描（读取）性能，也会影响其他所有查询执行操作，例如连接和分组操作。

初始加载后，必须*验证*分布，*确保*数据均匀分布。增量加载后，继续*验证*分布同样重要。

以下查询显示每个 Segment 上的行数，以及与最小和最大行数的差异：

```sql
SELECT 'Example Table' AS "Table Name", 
    max(c) AS "Max Seg Rows", min(c) AS "Min Seg Rows", 
    (max(c)-min(c))*100.0/max(c) AS "Percentage Difference Between Max & Min" 
FROM (SELECT count(*) c, gp_segment_id FROM facts GROUP BY 2) AS a;
```

`gp_toolkit` 模式提供两个可用于检查数据倾斜的视图。

- `gp_toolkit.gp_skew_coefficients` 视图通过计算每个 Segment 上存储数据的变异系数（CV），显示数据分布倾斜。`skccoeff` 列显示变异系数（CV），其计算方式是标准差除以平均值。它同时考虑数据序列的平均值和围绕平均值的变化。值越低越好。值越高表示数据倾斜越严重。
- `gp_toolkit.gp_skew_idle_fractions` 视图通过计算表扫描期间系统处于空闲状态的百分比，显示数据分布倾斜；该百分比是计算倾斜的指标。`siffraction` 列显示表扫描期间系统处于空闲状态的百分比，用于指示数据分布不均或查询处理倾斜。例如，值 0.1 表示 10% 的倾斜，值 0.5 表示 50% 的倾斜，依此类推。倾斜超过 10% 的表应重新评估其分布策略。

### 处理倾斜 {#processing-skew}

当不成比例的数据流向一个或少数几个 Segment 并由其处理时，就会产生处理倾斜。它通常是 Apache Cloudberry 性能和稳定性问题的根源。连接、排序、聚合和各种 OLAP 操作都可能出现处理倾斜。处理倾斜会在查询运行过程中发生，不像数据倾斜那样容易检测；数据倾斜是由于错误选择分布键导致数据分布不均，在表级别就存在，因此容易检测，也可以通过选择最佳分布键来避免。

如果只有单个 Segment 发生故障，即同一主机上的其他 Segment 没有故障，可能是处理倾斜问题。当前识别处理倾斜需要手动完成。首先查找溢出文件。如果存在倾斜，但倾斜程度不足以导致溢出，就不会成为性能问题。如果确定存在倾斜，就要找出导致倾斜的查询。

几乎所有情况下，处理倾斜的解决方法都是重写查询。创建临时表可以消除倾斜。临时表可以随机分布，从而强制执行两阶段聚合。

## 分区 {#partitioning}

良好的分区策略只读取满足查询所需的分区，从而减少需要扫描的数据量。

每个分区在*每个* Segment 上都是一个独立的物理文件或文件集合（对于列存储表）。正如读取宽列存储表的完整行比从堆表读取同一行需要更长时间一样，读取分区表中的所有分区也比从非分区表读取相同数据需要更长时间。

以下是分区最佳实践：

- 只对大型表进行分区，不要对小表分区。
- 只有在可以根据查询条件实现分区消除（分区剪枝）时，才对大型表使用分区；实现方式是根据查询谓词对表进行分区。只要可能，就使用范围分区，而不是列表分区。
- 只有当查询使用不可变操作符（例如 `=`、`<`、`<=`、`>`、`>=` 和 `<>`）对表进行直接、简单的限制时，查询规划器才能有选择地扫描分区表。
- 有选择的扫描会识别 `STABLE` 和 `IMMUTABLE` 函数，但不会识别查询中的 `VOLATILE` 函数。例如，以下 `WHERE` 子句

    ```sql
    date > CURRENT_DATE
    ```

    会使查询规划器有选择地扫描分区表，而以下 `WHERE` 子句

    ```sql
    time > TIMEOFDAY
    ```

    不会。必须检查查询的 `EXPLAIN` 计划，验证查询是否在有选择地扫描分区表（是否消除了分区）。

- 不要使用默认分区。默认分区始终会被扫描；更重要的是，在许多环境中默认分区容易过度填充，导致性能不佳。
- *绝不要*使用同一列进行表分区和分布。
- 不要使用多级分区。虽然支持子分区，但不建议使用，因为子分区通常包含很少或不包含数据。分区或子分区数量增加就会提升性能，这是一个误解；维护大量分区和子分区的管理开销会超过任何性能收益。为了兼顾性能、可扩展性和可管理性，应在分区扫描性能与分区总数之间取得平衡。
- 谨慎使用过多的列存储分区。
- 考虑并发工作负载，以及所有并发查询打开和扫描的平均分区数量。

### 分区数量与列存储文件 {#number-of-partition-and-columnar-storage-files}

Apache Cloudberry 支持的文件数量唯一硬限制是操作系统打开文件的限制。但是，还必须考虑集群中的文件总数、每个 Segment 上的文件数，以及一台主机上的文件总数。在 MPP 无共享架构环境中，每个节点独立于其他节点运行。每个节点都受其磁盘、CPU 和内存限制。Apache Cloudberry 中 CPU 和 I/O 限制并不常见，但内存通常是限制因素，因为查询执行模型会在内存中优化查询性能。

每个 Segment 的最佳文件数还取决于节点上的 Segment 数量、集群大小、SQL 访问、并发性、工作负载和数据倾斜。每台主机通常有 6 到 8 个 Segment，但大型集群每台主机应运行更少的 Segment。使用分区和列存储时，平衡集群中的文件总数很重要，但考虑每个 Segment 上的文件数和节点上的文件总数*更加*重要。

每个节点 64GB 内存的示例

- 节点数：16
- 每个节点的 Segment 数量：8
- 每个 Segment 的平均文件数：10,000

每个节点的文件总数为 `8*10,000 = 80,000`，集群的文件总数为 `8*16*10,000 = 1,280,000`。分区数量和列数增加时，文件数量会快速增长。

一般最佳实践是将每个节点的文件总数限制在 100,000 以下。如前面的示例所示，每个 Segment 的最佳文件数和每个节点的文件总数取决于节点的硬件配置（主要是内存）、集群大小、SQL 访问、并发性、工作负载和数据倾斜。

## 索引 {#indexes}

Apache Cloudberry 通常不需要索引。大多数分析型查询处理大量数据，而索引用于定位单行或少量数据行。在 Apache Cloudberry 中，顺序扫描是一种高效的数据读取方法，因为每个 Segment 包含相等部分的数据，所有 Segment 会并行读取数据。

如果添加索引没有带来性能收益，就删除索引。验证创建的每个索引都被优化器使用。

对于高选择性查询，索引可能改善查询性能。对于需要执行高选择性查询的高基数列，可以为列存储表的单个列创建索引，以支持深入查询。

不要为经常更新的列创建索引。为经常更新的列创建索引，会增加更新所需的写入次数。

只有在查询中经常使用表达式时，才应对表达式建立索引。

带谓词的索引会创建部分索引，可用于从大表中选择少量行。

避免创建重叠索引。具有相同前导列的索引是冗余的。

对于返回目标行集合的查询，索引可以改善压缩 AO 表的性能。对于压缩数据，使用索引访问方法意味着只需解压必要的数据页。

创建选择性较高的 B-树索引。索引选择性是列中不同值数量除以表中行数的比率。例如，如果表有 1000 行，某列有 800 个不同值，则索引选择性为 0.8，这被认为是良好的选择性。

一般规则是，在向表加载数据前删除索引。与向带索引的表加载数据相比，这样加载速度会快一个数量级。加载完成后，重新创建索引。

位图索引适合查询，不适合更新。列具有低基数（100 到 100,000 个不同值）时，位图索引的效果最佳。不要对唯一列、基数非常高或非常低的数据使用位图索引。不要将位图索引用于事务型工作负载。

如果分区表需要索引，索引列必须不同于分区列。为分区表建立索引的一个优点是，随着 B-树规模增长，其性能会呈指数下降；在分区表上创建索引可以得到更小的 B-树，其性能优于非分区表上的 B-树。

## 列顺序与字节对齐 {#column-sequence-and-byte-alignment}

为了获得最佳性能，应排列表列，使数据类型按字节对齐。堆表中的列应按以下顺序排列：

1. 分布列和分区列
2. 固定长度数值类型
3. 可变长度数据类型

按照从大到小的顺序排列数据类型，使 `BIGINT` 和 `TIMESTAMP` 位于 `INT` 和 `DATE` 之前，而所有这些类型都位于 `TEXT`、`VARCHAR` 或 `NUMERIC(x,y)` 之前。例如，先放置 8 字节类型（`BIGINT`、`TIMESTAMP`），再放置 4 字节类型（`INT`、`DATE`），然后是 2 字节类型（`SMALLINT`），最后是可变长度数据类型（`VARCHAR`）。

不要按以下顺序定义列：

`Int`, `Bigint`, `Timestamp`, `Bigint`, `Timestamp`, `Int` (分布键), `Date` (分区键), `Bigint`, `Smallint`

应按以下顺序定义列：

`Int` (分布键), `Date` (分区键), `Bigint`, `Bigint`, `Timestamp`, `Bigint`, `Timestamp`, `Int`, `Smallint`
