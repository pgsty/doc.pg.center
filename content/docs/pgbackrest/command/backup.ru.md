Если настроено несколько репозиториев, pgBackRest создаёт резервную копию в репозитории с наивысшим приоритетом (например, `repo1`), если не указан параметр `--repo`.

В pgBackRest нет встроенного планировщика, поэтому лучше запускать его через cron или другой механизм планирования.

Подробности и примеры приведены в разделе [Создание резервной копии](/ru/docs/pgbackrest/user-guide/#perform-a-backup).

## Параметры команды {#command-options}

### Параметр аннотации резервной копии (`--annotation`) {#backup-annotation-option---annotation}

Добавление к резервной копии пользовательских пар «ключ — значение».

Пользователи могут добавлять к резервной копии информационные пары «ключ — значение». Этот параметр можно указывать несколько раз для добавления нескольких аннотаций.

Аннотации включаются в текстовый вывод команды `info`, если резервная копия указана через `--set`, и всегда присутствуют в выводе JSON.

```yaml
example: --annotation=source="Sunday backup for website database"
```

### Параметр проверки архива (`--archive-check`) {#check-archive-option---archive-check}

Проверка наличия сегментов WAL в архиве перед завершением резервного копирования.

Проверяет, что все сегменты WAL, необходимые для согласованности резервной копии, присутствуют в архиве WAL. Рекомендуется оставить значение по умолчанию, если не используется другой способ архивирования.

Этот параметр должен быть включён, если включён `archive-copy`.

```yaml
default: y
example: --no-archive-check
```

### Параметр копирования архива (`--archive-copy`) {#copy-archive-option---archive-copy}

Копирование в резервную копию сегментов WAL, необходимых для согласованности.

Этот параметр обеспечивает дополнительную предосторожность: он защищает от повреждения архива сегментов WAL, сохраняя сегменты, необходимые для согласованности, непосредственно в резервной копии. Сегменты WAL по-прежнему сохраняются и в архиве, поэтому параметр увеличивает расход места.

При использовании этого параметра желательно, чтобы команды `archive-push` и `backup` имели одинаковый `compress-type` (например, `lz4`). Иначе сегменты WAL потребуется повторно сжать с `compress-type`, используемым резервной копией, что может потребовать значительных ресурсов в зависимости от объёма WAL, созданного во время резервного копирования.

При восстановлении сегменты WAL будут находиться в `pg_xlog/pg_wal`, и PostgreSQL предпочтёт использовать их, а не вызывать `restore_command`.

Параметр `archive-check` должен быть включён, если включён `archive-copy`.

```yaml
default: n
example: --archive-copy
```

### Параметр проверки режима архивирования (`--archive-mode-check`) {#check-archive-mode-option---archive-mode-check}

Проверка настройки PostgreSQL `archive_mode`.

Этот параметр включён по умолчанию и запрещает использовать в PostgreSQL `archive_mode=always`.

Сегменты WAL, отправляемые с резервного сервера, могут логически совпадать с сегментами WAL с первичного сервера, но иметь другие контрольные суммы. Во избежание конфликтов рекомендуется отключить архивирование из нескольких источников.

ОСТОРОЖНО:

Если этот параметр отключён, крайне важно обеспечить, чтобы в репозиторий через команду `archive-push` писал только один процесс архивирования.

```yaml
default: y
example: --no-archive-mode-check
```

### Параметр тайм-аута архивирования (`--archive-timeout`) {#archive-timeout-option---archive-timeout}

Тайм-аут архивирования.

Задаёт максимальное время в секундах, в течение которого ожидается поступление каждого сегмента WAL в архивный репозиторий pgBackRest. Тайм-аут применяется к командам `check` и `backup`, когда они ожидают архивирования сегментов WAL, необходимых для согласованности резервной копии.

```yaml
default: 1m
allowed: [100ms, 1d]
example: --archive-timeout=30
```

### Параметр резервного копирования с резервного сервера (`--backup-standby`) {#backup-from-standby-option---backup-standby}

Резервное копирование с резервного кластера.

Включает резервное копирование с резервного сервера для снижения нагрузки на первичный кластер. Этот параметр требует настройки как первичного, так и резервного сервера.

Поддерживаются следующие режимы:

- `y` - Для резервного копирования необходим резервный сервер.
- `prefer` - Копирование с резервного сервера, если он доступен; иначе с первичного.
- `n` - Копирование только с первичного сервера.

```yaml
default: n
example: --backup-standby=y
```

### Параметр контрольных сумм страниц (`--checksum-page`) {#page-checksums-option---checksum-page}

Проверка контрольных сумм страниц данных.

Указывает pgBackRest проверять контрольные суммы всех страниц данных при резервном копировании кластера. Этот параметр включается автоматически, если в кластере включены контрольные суммы страниц данных.

Ошибки проверки контрольных сумм не прерывают резервное копирование. Вместо этого в журнал выводятся предупреждения (а при настройках по умолчанию — и в консоль), а список некорректных страниц сохраняется в манифесте резервной копии.

```yaml
example: --no-checksum-page
```

### Параметр исключения путей и файлов (`--exclude`) {#pathfile-exclusions-option---exclude}

Исключение путей и файлов из резервной копии.

Все исключения задаются относительно `$PGDATA`. Если исключение заканчивается на /, исключаются только файлы в указанном каталоге: например, `--exclude=junk/` исключит все файлы в каталоге `$PGDATA/junk`, но сохранит сам каталог. Если исключение не заканчивается на /, файл может либо точно совпадать с исключением, либо соответствовать исключению с добавленным /: например, `--exclude=junk` исключит каталог `$PGDATA/junk` и все содержащиеся в нём файлы.

**Используйте эту возможность осторожно: очень легко исключить важные данные и нарушить согласованность резервной копии. Обязательно проверяйте восстановление!**

Все исключённые файлы записываются в журнал на уровне `info` вместе с правилом исключения. Обязательно проверяйте список исключённых файлов, чтобы убедиться, что ничего не исключено случайно.

> **ПРИМЕЧАНИЕ:** при дельта-восстановлении исключения не учитываются. Все файлы и каталоги, исключённые при резервном копировании, будут *удалены* при дельта-восстановлении.

Этот параметр не следует использовать для исключения журналов PostgreSQL из резервной копии. Журналы можно вынести за пределы каталога `PGDATA` с помощью настройки PostgreSQL `log_directory`; при этом они также сохранятся после восстановления.

В командной строке или файле конфигурации можно задать несколько исключений.

```yaml
example: --exclude=junk/
```

### Параметр автоматического удаления устаревших копий (`--expire-auto`) {#expire-auto-option---expire-auto}

Автоматический запуск команды `expire` после успешного резервного копирования.

Этот параметр включён по умолчанию. Отключать его следует с осторожностью: в этом случае все резервные копии и архивы будут храниться бессрочно, что может привести к исчерпанию места в репозитории. Чтобы избежать этого, необходимо регулярно запускать команду `expire`.

При автоматическом запуске после успешного резервного копирования `expire` использует конфигурацию команды `backup`, поэтому параметры, заданные только в секции команды `expire` (например, `[global:expire]`), не применяются. Чтобы применялась конфигурация, специфичная для `expire`, отключите этот параметр и запускайте команду `expire` отдельно.

```yaml
default: y
example: --expire-auto
```

### Параметр принудительного выполнения (`--force`) {#force-option---force}

Принудительное резервное копирование остановленного кластера.

При использовании с `--no-start-stop` резервное копирование выполняется, даже если pgBackRest считает PostgreSQL работающим. **Этот параметр следует использовать крайне осторожно, поскольку он, скорее всего, приведёт к созданию непригодной резервной копии.**

В некоторых ситуациях резервное копирование может быть желательно и при таких условиях. Например, если сервер аварийно завершил работу, а том кластера базы данных можно смонтировать только для чтения, имеет смысл создать резервную копию, даже если присутствует `postmaster.pid`. В таком случае лучше было бы вернуться к предыдущей копии и воспроизвести WAL, но в сегменте WAL, не попавшем в архив, может находиться очень важная транзакция.

```yaml
default: n
example: --force
```

### Параметр порога сохранения манифеста (`--manifest-save-threshold`) {#manifest-save-threshold-option---manifest-save-threshold}

Порог сохранения манифеста при резервном копировании.

Определяет, как часто манифест сохраняется во время резервного копирования. Сохранять его важно, поскольку он содержит контрольные суммы и обеспечивает эффективное возобновление. Фактический порог равен большему из двух значений: 1% размера резервной копии или `manifest-save-threshold`.

```yaml
default: 1GiB
allowed: [1B, 1TiB]
example: --manifest-save-threshold=8GiB
```

### Параметр копирования работающего кластера (`--online`) {#online-option---online}

Резервное копирование работающего кластера.

Параметр --no-online запрещает pgBackRest вызывать функции начала и завершения резервного копирования на кластере базы данных. Для этого PostgreSQL следует остановить; если он работает, pgBackRest выдаст ошибку.

Этот параметр позволяет создавать резервные копии остановленного кластера. Каталог `pg_xlog`/`pg_wal` копируется как есть, а `archive-check` автоматически отключается для этой копии.

```yaml
default: y
example: --no-online
```

### Параметр возобновления (`--resume`) {#resume-option---resume}

Разрешение возобновления неудавшегося резервного копирования.

Определяет, включена ли возможность возобновления. Она может значительно сократить время резервного копирования после сбоя предыдущей попытки того же типа. Однако она усложняет работу, поэтому в средах, где она не нужна, может быть желательно её отключить.

```yaml
default: y
example: --no-resume
```

### Параметр быстрого запуска (`--start-fast`) {#start-fast-option---start-fast}

Принудительная контрольная точка для быстрого начала резервного копирования.

Принудительно выполняет контрольную точку, передавая `y` в параметр `fast` функции начала резервного копирования, чтобы копирование началось немедленно. Иначе резервное копирование начнётся после следующей плановой контрольной точки.

```yaml
default: n
example: --start-fast
```

### Параметр типа (`--type`) {#type-option---type}

Тип резервной копии.

Поддерживаются следующие типы резервных копий:

- `full` - Копируются все файлы кластера базы данных; зависимостей от предыдущих копий нет.
- `incr` - Инкрементная копия относительно последней успешной резервной копии.
- `diff` - Аналогична инкрементной копии, но всегда основана на последней полной копии.

```yaml
default: incr
example: --type=full
```

## Общие параметры {#general-options}

### Параметр разрешения запуска от root (`--allow-root`) {#allow-run-as-root-option---allow-root}

Разрешение запуска команды от пользователя root.

По умолчанию только команда `restore` может выполняться от пользователя root, поскольку она предназначена для тщательного управления принадлежностью файлов. Выполнение других команд от пользователя root может привести к созданию файлов (например, в репозитории), принадлежащих root, и, как следствие, недоступных для пользователя PostgreSQL, что вызовет сбой последующих команд.

Включите этот параметр, чтобы запустить команду от имени root. Однако гораздо лучше запускать pgBackRest от пользователя, владеющего репозиторием и кластером PostgreSQL.

```yaml
default: n
example: --allow-root
```

### Параметр размера буфера (`--buffer-size`) {#buffer-size-option---buffer-size}

Размер буфера для операций ввода-вывода.

Размер буфера, используемый для копирования, сжатия, шифрования и других операций. Количество используемых буферов зависит от параметров, и каждая операция может использовать дополнительную память, например, сжатие `gz` может потребовать дополнительно 256KiB памяти.

Допустимые значения: `16KiB`, `32KiB`, `64KiB`, `128KiB`, `256KiB`, `512KiB`, `1MiB`, `2MiB`, `4MiB`, `8MiB` и `16MiB`.

```yaml
default: 1MiB
example: --buffer-size=2MiB
```

### Параметр команды pgBackRest (`--cmd`) {#pgbackrest-command-option---cmd}

Команда pgBackRest.

pgBackRest может формировать командную строку, например когда команда `restore` создаёт настройку restore_command. В этом случае используется команда, которой был запущен процесс pgBackRest, если не задан параметр `cmd`.

ОСТОРОЖНО:

Использование обёртки для команды pgBackRest может привести к непредсказуемому поведению и не рекомендуется.

```yaml
default: [path of executed pgbackrest binary]
example: --cmd=/var/lib/pgsql/bin/pgbackrest_wrapper.sh
```

### Параметр команды SSH-клиента (`--cmd-ssh`) {#ssh-client-command-option---cmd-ssh}

Команда SSH-клиента.

Позволяет задать конкретную команду SSH-клиента, если нужен другой клиент или команда `ssh` отсутствует в $PATH.

```yaml
default: ssh
example: --cmd-ssh=/usr/bin/ssh
```

### Параметр сжатия (`--compress`) {#compress-option---compress}

Сжатие файлов.

Файлы резервных копий совместимы с утилитами сжатия командной строки.

Этот параметр устарел. Вместо него следует использовать `compress-type`.

```yaml
default: y
example: --no-compress
```

### Параметр уровня сжатия (`--compress-level`) {#compress-level-option---compress-level}

Уровень сжатия файлов.

Задаёт уровень сжатия файлов, когда `compress-type` не равен `none` или задано `compress=y` (устаревший вариант).

```yaml
default (depending on compress-type):
    bz2 - 9
    gz - 6
    lz4 - 1
    zst - 3

allow range (depending on compress-type):
    bz2 - [1, 9]
    gz - [-1, 9]
    lz4 - [-5, 12]
    zst - [-7, 22]

example: --compress-level=9
```

### Параметр уровня сжатия для сети (`--compress-level-network`) {#network-compress-level-option---compress-level-network}

Уровень сжатия для передачи по сети.

Задаёт уровень сетевого сжатия, когда `compress-type=none` и команда выполняется на другом сервере, чем репозиторий. Сжатие уменьшает сетевой трафик. Когда `compress-type` не равен `none`, настройка `compress-level-network` игнорируется и вместо неё используется `compress-level`, чтобы файл сжимался только один раз.

```yaml
default: 1
allowed: [-5, 12]
example: --compress-level-network=1
```

### Параметр типа сжатия (`--compress-type`) {#compress-type-option---compress-type}

Тип сжатия файлов.

Поддерживаются следующие типы сжатия:

- `none` - без сжатия
- `bz2` - формат сжатия bzip2
- `gz` - формат сжатия gzip
- `lz4` - формат сжатия lz4 (доступен не на всех платформах)
- `zst` - формат сжатия Zstandard (доступен не на всех платформах)

```yaml
default: gz
example: --compress-type=none
```

### Параметр файла конфигурации (`--config`) {#config-option---config}

Конфигурационный файл pgBackRest.

Используйте этот параметр для указания другого файла конфигурации, отличного от файла по умолчанию.

```yaml
default: CFGOPTDEF_CONFIG_PATH "/" PROJECT_CONFIG_FILE
example: --config=/conf/pgbackrest/pgbackrest.conf
```

### Параметр каталога включаемых конфигураций (`--config-include-path`) {#config-include-path-option---config-include-path}

Путь к дополнительным файлам конфигурации pgBackRest.

Файлы конфигурации с расширением `.conf`, находящиеся в указанном каталоге, объединяются с файлом конфигурации pgBackRest в единый файл конфигурации.

```yaml
default: CFGOPTDEF_CONFIG_PATH "/" PROJECT_CONFIG_INCLUDE_PATH
example: --config-include-path=/conf/pgbackrest/conf.d
```

### Параметр каталога конфигурации (`--config-path`) {#config-path-option---config-path}

Базовый путь файлов конфигурации pgBackRest.

Эта настройка переопределяет базовый каталог по умолчанию для параметров `--config` и `--config-include-path`, если они не заданы явно в командной строке.

Например, передача только `--config-path=/conf/pgbackrest` приводит к установке значения по умолчанию для `--config` в `/conf/pgbackrest/pgbackrest.conf` и значения по умолчанию для `--config-include-path` в `/conf/pgbackrest/conf.d`.

```yaml
default: CFGOPTDEF_CONFIG_PATH
example: --config-path=/conf/pgbackrest
```

### Параметр тайм-аута базы данных (`--db-timeout`) {#database-timeout-option---db-timeout}

Тайм-аут запроса к базе данных.

Задаёт тайм-аут запросов к базе данных в секундах. Он распространяется и на функции начала и завершения резервного копирования, каждая из которых может выполняться довольно долго. Поэтому следует задавать большой тайм-аут, если нет уверенности, что эти функции завершатся быстро (то есть если задано `start-fast=y` и известно, что кластер базы данных не создаст много сегментов WAL во время резервного копирования).

> **ПРИМЕЧАНИЕ:** параметр `db-timeout` должен быть меньше `protocol-timeout`.

```yaml
default: 30m
allowed: [100ms, 7d]
example: --db-timeout=600
```

### Параметр дельта-восстановления и копирования (`--delta`) {#delta-option---delta}

Восстановление или резервное копирование с использованием контрольных сумм.

При восстановлении по умолчанию предполагается, что каталоги данных и табличных пространств PostgreSQL существуют, но пусты. Этот параметр выполняет дельта-восстановление с использованием контрольных сумм.

При резервном копировании этот параметр использует контрольные суммы вместо временных меток, чтобы определить, нужно ли копировать файлы.

```yaml
default: n
example: --delta
```

### Параметр тайм-аута ввода-вывода (`--io-timeout`) {#io-timeout-option---io-timeout}

Тайм-аут ввода-вывода.

Тайм-аут, в секундах, используемый для соединений и операций чтения/записи.

Операция чтения или записи не обязана полностью завершиться за это время, но *какое-то* продвижение должно произойти, хотя бы на один байт.

```yaml
default: 1m
allowed: [100ms, 1h]
example: --io-timeout=120
```

Путь для хранения файлов блокировок.

### Параметр нейтральной маски umask (`--neutral-umask`) {#neutral-umask-option---neutral-umask}

Использование нейтральной маски umask.

Устанавливает umask в 0000, чтобы объекты в репозитории создавались с подходящими правами. По умолчанию права каталогов — 0750, файлов — 0640.

Чтобы вместо этого использовать umask пользователя, выполняющего команду, укажите `neutral-umask=n` в файле конфигурации или `--no-neutral-umask` в командной строке.

```yaml
default: y
```

### Параметр приоритета процесса (`--priority`) {#set-process-priority-option---priority}

Установка приоритета процесса.

Определяет приоритет процесса (то есть значение nice) для планировщика ядра. Положительные значения понижают приоритет, отрицательные — повышают. В большинстве случаев процессы не имеют права повышать свой приоритет.

### Параметр максимального числа процессов (`--process-max`) {#process-maximum-option---process-max}

Максимальное число процессов для сжатия и передачи данных.

Каждый процесс выполняет сжатие и передачу, ускоряя выполнение команды, однако не следует задавать `process-max` настолько большим, чтобы это ухудшало производительность базы данных.

```yaml
default: 1
```

### Параметр тайм-аута протокола (`--protocol-timeout`) {#protocol-timeout-option---protocol-timeout}

Тайм-аут протокола.

Задаёт тайм-аут, в секундах, на который локальный или удалённый процесс будет ждать получения нового сообщения на уровне протокола. Это предотвращает бесконечное ожидание сообщения процессами.

> **ПРИМЕЧАНИЕ:** параметр `protocol-timeout` должен быть больше `db-timeout`.

```yaml
default: 31m
allowed: [100ms, 7d]
example: --protocol-timeout=630
```

### Параметр stanza (`--stanza`) {#stanza-option---stanza}

Определение stanza.

Stanza — конфигурация кластера баз данных PostgreSQL, которая определяет его расположение, способ резервного копирования, параметры архивирования и т. п. Большинство серверов баз данных содержат только один кластер PostgreSQL и, соответственно, одну stanza, тогда как на серверах резервного копирования есть stanza для каждого кластера, требующего резервного копирования.

Может возникнуть желание назвать stanza по имени первичного кластера, но лучше выбрать имя, описывающее базы данных в нём. Поскольку имя stanza используется для первичного сервера и всех реплик, уместнее выбрать имя, отражающее назначение кластера, например app или dw, а не локальное имя кластера, такое как main или prod.

```yaml
example: --stanza=main
```

Число сообщений keep-alive.

Время простоя перед отправкой keep-alive.

Задаёт время отсутствия сетевой активности в секундах, по истечении которого операционной системе следует отправить сообщение TCP keep-alive.

Этот параметр доступен на системах, которые поддерживают опцию сокета `TCP_KEEPIDLE`.


### Параметр интервала keep-alive (`--tcp-keep-alive-interval`) {#keep-alive-interval-option---tcp-keep-alive-interval}

Интервал сообщений keep-alive.

Задаёт время в секундах, после которого следует повторно отправить сообщение TCP keep-alive, не получившее подтверждения.

Этот параметр доступен на системах, которые поддерживают опцию сокета `TCP_KEEPINTVL`.

### Параметр наборов шифров TLSv1.2 (`--tls-cipher-12`) {#tlsv12-cipher-suites-option---tls-cipher-12}

Допустимые наборы шифров TLSv1.2.

Все соединения TLS между клиентом pgBackRest и сервером зашифрованы. По умолчанию также зашифрованы соединения с объектными хранилищами (например, S3).

```yaml
example: --tls-cipher-12=HIGH:MEDIUM:+3DES:!aNULL
```

### Параметр наборов шифров TLSv1.3 (`--tls-cipher-13`) {#tlsv13-cipher-suites-option---tls-cipher-13}

Допустимые наборы шифров TLSv1.3.

```yaml
example: --tls-cipher-13=TLS_AES_256_GCM_SHA384:TLS_CHACHA20_POLY1305_SHA256
```

## Параметры для сопровождающих {#maintainer-options}

### Параметр проверки заголовков страниц (`--page-header-check`) {#page-header-check-option---page-header-check}

Проверка заголовков страниц PostgreSQL.

Этот параметр включён по умолчанию и добавляет проверки заголовков страниц.

Следует избегать отключения этого параметра, кроме случаев, когда оно необходимо, например если страницы зашифрованы.

```yaml
default: y

```

### Параметр принудительного задания версии PostgreSQL (`--pg-version-force`) {#force-postgresql-version-option---pg-version-force}

Принудительное задание версии PostgreSQL.

Указанная версия PostgreSQL будет использоваться вместо версии, автоматически определённой по `pg_control` или заголовкам WAL. Это полезно главным образом для форков PostgreSQL или версий в разработке, в которых эти значения отличаются от версии выпуска. Версия, которую PostgreSQL сообщает через `server_version_num`, должна совпадать с принудительно заданной.

ПРЕДУПРЕЖДЕНИЕ:

Используйте этот параметр осторожно: `pg_control` и заголовки WAL всё равно будут читаться в формате, ожидаемом для указанной версии, то есть в формате официальной версии PostgreSQL с открытым исходным кодом. Если форк или версия в разработке меняет формат полей, от которых зависит pgBackRest, это приведёт к неожиданному поведению. В общем случае параметр будет работать как ожидается только тогда, когда форк добавляет все собственные поля структур *после* стандартных полей PostgreSQL.

```yaml
example: --pg-version-force=15
```

### Параметр поблочного инкрементного резервного копирования (`--repo-block`) {#block-incremental-backup-option---repo-block}

Включение поблочного инкрементного резервного копирования.

Поблочное инкрементное копирование позволяет создавать более детальные резервные копии, разбивая файлы на блоки, которые можно копировать независимо. Это экономит место в репозитории и может ускорить дельта-восстановление, поскольку отдельные блоки можно получать без чтения всего файла из репозитория.

> **ПРИМЕЧАНИЕ:** прежде чем включить `repo-block`, необходимо включить параметр `repo-bundle`.

Размер блока определяется размером и возрастом файла. Как правило, для более старых или крупных файлов выбираются более крупные блоки. Если файл достаточно старый, поблочное инкрементное копирование для него не используется.

Поблочное инкрементное копирование наиболее эффективно, когда включено для всех типов резервных копий, в том числе полных. Полная копия при этом становится немного больше, зато последующие дифференциальные и инкрементные копии могут использовать созданные ею карты блоков для экономии места.

```yaml
default: n
example: --repo1-block
```

### Параметр пакетирования файлов в репозитории (`--repo-bundle`) {#repository-bundles-option---repo-bundle}

Пакетирование файлов в репозитории.

Объединяет небольшие файлы в пакеты, уменьшая общее число файлов, записываемых в репозиторий. Записывать меньше файлов обычно эффективнее, особенно в объектные хранилища, такие как S3. Кроме того, файлы нулевого размера не сохраняются (кроме записей в манифесте), что экономит время и место.

```yaml
default: n
example: --repo1-bundle
```

### Параметр предельного размера файла в пакете репозитория (`--repo-bundle-limit`) {#repository-bundle-limit-option---repo-bundle-limit}

Предельный размер файлов для пакетирования.

Максимальный размер файлов, включаемых в пакеты. Файлы большего размера хранятся отдельно.

Файлы в пакетах нельзя использовать повторно при возобновлении резервного копирования, поэтому этот параметр определяет, какие файлы можно использовать при возобновлении: чем больше значение, тем меньше таких файлов.

```yaml
default: 2MiB
allowed: [8KiB, 1PiB]
example: --repo1-bundle-limit=10MiB
```

### Параметр размера пакета репозитория (`--repo-bundle-size`) {#repository-bundle-size-option---repo-bundle-size}

Целевой размер пакета файлов.

Определяет целевой суммарный размер файлов, добавляемых в один пакет. Несжатый пакет может достигать размера `repo-bundle-size` + `repo-bundle-limit`, поэтому не следует задавать этому параметру максимальный размер, допустимый файловой системой.

Как правило, слишком большое значение нежелательно: при повторной попытке потребуется заново обработать весь пакет.

```yaml
default: 20MiB
allowed: [1MiB, 1PiB]
example: --repo1-bundle-size=10MiB
```

### Параметр типа шифрования репозитория (`--repo-cipher-type`) {#repository-cipher-type-option---repo-cipher-type}

Шифр для шифрования репозитория.

Поддерживаются следующие типы шифрования:

- `none` - Репозиторий не зашифрован

```yaml
default: none
example: --repo1-cipher-type=aes-256-cbc
```

### Параметр типа ключа репозитория GCS (`--repo-gcs-key-type`) {#gcs-repository-key-type-option---repo-gcs-key-type}

Тип ключа репозитория GCS.

Для авторизации поддерживаются следующие типы:

- `auto` - Авторизация с помощью служебной учётной записи экземпляра.

При `repo-gcs-key-type=service` учётные данные повторно загружаются при обновлении токена аутентификации.

### Параметр хранения архива (`--repo-retention-archive`) {#archive-retention-option---repo-retention-archive}

Число резервных копий, для которых сохраняется непрерывный WAL.

> **ПРИМЕЧАНИЕ:** сегменты WAL, необходимые для согласованности резервной копии, всегда сохраняются до удаления этой копии независимо от настройки данного параметра.

Если значение не задано, а `repo-retention-full-type` равен `count` (по умолчанию), то для удаления архива по умолчанию используется значение `repo-retention-full` (или `repo-retention-diff`), соответствующее `repo-retention-archive-type`, заданному как `full` (или `diff`). Это гарантирует, что WAL удаляется только для уже удалённых резервных копий. Если `repo-retention-full-type` равен `time`, по умолчанию удаляются архивы, предшествующие самой старой полной копии, оставшейся после применения настройки `repo-retention-full`.

Этот параметр должен быть задан, если `repo-retention-archive-type` равен `incr`. При острой нехватке дискового пространства он вместе с `repo-retention-archive-type` позволяет агрессивнее удалять сегменты WAL. Однако это исключает возможность PITR из копий с удалённым WAL и потому **не** рекомендуется.

```yaml
allowed: [1, 9999999]
example: --repo1-retention-archive=2
```

Устаревшее имя: retention-archive

### Параметр типа хранения архива (`--repo-retention-archive-type`) {#archive-retention-type-option---repo-retention-archive-type}

Тип резервных копий для хранения WAL.

При значении `full` pgBackRest сохраняет архивные журналы для числа полных резервных копий, заданного `repo-retention-archive`. При значении `diff` (дифференциальные) pgBackRest сохраняет архивные журналы для числа полных и дифференциальных копий, заданного `repo-retention-archive`: если последняя копия полная, для целей хранения в репозитории она учитывается как дифференциальная. При значении `incr` (инкрементные) pgBackRest сохраняет архивные журналы для числа полных, дифференциальных и инкрементных копий, заданного `repo-retention-archive`. Рекомендуется оставить значение по умолчанию, при котором WAL удаляется только вместе с полными резервными копиями.

```yaml
default: full
example: --repo1-retention-archive-type=diff
```

Устаревшее имя: retention-archive-type

### Параметр хранения дифференциальных копий (`--repo-retention-diff`) {#differential-retention-option---repo-retention-diff}

Число сохраняемых дифференциальных резервных копий.

При удалении дифференциальной копии также удаляются все связанные с ней инкрементные копии. Если параметр не задан, все дифференциальные копии сохраняются до удаления полных копий, от которых они зависят.

При определении копий для удаления полные копии учитываются в числе дифференциальных. В большинстве случаев это немного уменьшает число дифференциальных копий, которые необходимо хранить.

```yaml
allowed: [1, 9999999]
example: --repo1-retention-diff=3
```

Устаревшее имя: retention-diff

### Параметр хранения полных копий (`--repo-retention-full`) {#full-retention-option---repo-retention-full}

Число или срок хранения полных резервных копий.

При удалении полной копии также удаляются все связанные с ней дифференциальные и инкрементные копии. Если параметр не задан, выводится предупреждение. Для бессрочного хранения задайте максимальное значение.

```yaml
allowed: [1, 9999999]
example: --repo1-retention-full=2
```

Устаревшее имя: retention-full

### Параметр типа хранения полных копий (`--repo-retention-full-type`) {#full-retention-type-option---repo-retention-full-type}

Тип срока хранения полных резервных копий.

Определяет, означает ли настройка `repo-retention-full` период времени (в днях) или число полных копий, которые нужно сохранять.

При значении `time` полные копии старше `repo-retention-full` удаляются из репозитория, если существует хотя бы ещё одна копия, возраст которой не меньше значения `repo-retention-full`. Например, если `repo-retention-full` равен 30 (дней) и есть 2 полные копии возрастом 25 и 35 дней, ни одна не будет удалена: после удаления копии возрастом 35 дней останется только копия возрастом 25 дней, что нарушит политику хранения за 30 дней. Эта политика требует наличия хотя бы одной копии возрастом 30 дней перед удалением более старой. Архивный WAL, предшествующий самой старой оставшейся полной копии, удаляется автоматически, если `repo-retention-archive-type` и `repo-retention-archive` не заданы явно.

При значении `count` полные копии сверх числа `repo-retention-full` удаляются. Например, если `repo-retention-full` равен `4` и завершается пятая полная копия, самая старая полная копия будет удалена, чтобы их число осталось равным 4.

Резервная копия учитывается при применении политики хранения только после успешного завершения. Например, если `repo-retention-full-type` равен `count`, а `repo-retention-full` равен `2`, для удаления самой старой копии должны существовать 3 завершённые полные копии.

```yaml
default: count
example: --repo1-retention-full-type=time
```

### Параметр хранения истории резервных копий (`--repo-retention-history`) {#backup-history-retention-option---repo-retention-history}

Число дней хранения манифестов истории резервных копий.

После завершения резервного копирования копия манифеста сохраняется в каталоге `backup.history`. По умолчанию эти файлы никогда не удаляются, поскольку полезны для анализа данных, например для измерения роста резервных копий и WAL со временем.

Параметр `repo-retention-history` задаёт число дней хранения манифестов истории резервных копий. Неудалённые резервные копии всегда сохраняются в истории. Укажите `repo-retention-history=0`, чтобы хранить историю только для неудалённых резервных копий.

При удалении манифеста истории полной резервной копии также удаляются манифесты истории всех связанных с ней дифференциальных и инкрементных копий.

Способ формирования отпечатка сервера репозитория SFTP следует выбирать в соответствии с `repo-sftp-host-key-hash-type`. Отпечаток можно получить командой `awk '{print $2}' ssh_host_xxx_key.pub | base64 -d | (md5sum or sha1sum) -b`. Ключи сервера ssh обычно находятся в каталоге `/etc/ssh`.

```yaml
example: --repo1-sftp-host-fingerprint=f84e172dfead7aeeeae6c1fdfb5aa8cf
```

### Параметр типа проверки ключа сервера SFTP (`--repo-sftp-host-key-check-type`) {#sftp-host-key-check-type-option---repo-sftp-host-key-check-type}

Тип проверки ключа сервера SFTP.

Поддерживаются следующие типы проверки ключа сервера SFTP:

- `strict` - pgBackRest никогда не добавляет ключи серверов в файл ~/.ssh/known_hosts автоматически и отказывается соединяться с серверами, ключ которых изменился или отсутствует в файлах известных серверов. При этом пользователь должен вручную добавлять все новые серверы.
- `accept-new` - pgBackRest автоматически добавляет новые ключи серверов в пользовательский файл известных серверов, но не разрешает соединения с серверами, ключи которых изменились.
- `fingerprint` - pgBackRest сравнивает ключ сервера с отпечатком, заданным параметром `repo-sftp-host-fingerprint`.
- `none` - Ключ сервера не проверяется.

```yaml
default: strict
example: --repo1-sftp-host-key-check-type=accept-new
```

### Параметр типа хеша ключа сервера репозитория SFTP (`--repo-sftp-host-key-hash-type`) {#sftp-repository-host-key-hash-type-option---repo-sftp-host-key-hash-type}

Тип хеша ключа сервера репозитория SFTP.

Тип хеша ключа сервера репозитория SFTP. Задаёт тип хеша для вычисления дайджеста ключа удалённой системы при установлении SSH-соединения. Новые версии `libssh2` поддерживают `sha256` в дополнение к md5 и sha1.

```yaml
example: --repo1-sftp-host-key-hash-type=sha256
```

Порт сервера репозитория SFTP.

Порт сервера репозитория SFTP.

```yaml
default: 22
allowed: [1, 65535]
```


### Параметр файла известных серверов SFTP (`--repo-sftp-known-host`) {#sftp-known-hosts-file-option---repo-sftp-known-host}

Файл известных серверов SFTP.

Файл известных серверов, в котором при аутентификации ищется совпадение с сервером SFTP. Если параметр не задан, pgBackRest по умолчанию проверяет `~/.ssh/known_hosts`, `~/.ssh/known_hosts2`, `/etc/ssh/ssh_known_hosts` и `/etc/ssh/ssh_known_hosts2`. Если заданы один или несколько путей к файлам, поиск выполняется в них. Пути должны быть абсолютными или начинаться с тильды. Параметр `repo-sftp-known-host` можно указывать несколько раз для поиска в нескольких файлах известных серверов. Чтобы использовать проверку по этим файлам, `repo-sftp-host-fingerprint` не должен быть задан. См. также параметр `repo-sftp-host-check-type`.

```yaml
example: --repo1-sftp-known-host=/home/postgres/.ssh/known_hosts
```

### Параметр тегов хранилища репозитория (`--repo-storage-tag`) {#repository-storage-tag-option---repo-storage-tag}

Теги хранилища репозитория.

Задаёт теги, добавляемые к объектам, если репозиторий расположен в объектном хранилище (например, S3). Параметр можно повторять для добавления нескольких тегов.

В pgBackRest нет возможности изменять эти теги, поэтому их следует правильно задать до запуска `stanza-create`, чтобы теги были одинаковыми во всём репозитории.

### Параметр размера части загрузки в хранилище репозитория (`--repo-storage-upload-chunk-size`) {#repository-storage-upload-chunk-size-option---repo-storage-upload-chunk-size}

Размер части загрузки в хранилище репозитория.

Объектные хранилища, такие как S3, позволяют загружать файлы частями, если файл слишком велик для размещения в памяти. Даже если он помещается в память, ограничение объёма памяти для загрузок позволяет использовать её экономнее.

Больший размер части обычно повышает производительность, поскольку уменьшает число запросов загрузки и позволяет загружать больше файлов одним запросом, а не частями. Недостаток — повышенное потребление памяти. Поскольку буфер части выделяется каждому процессу, большие значения `process-max` увеличивают общий расход памяти.

Допустимые размеры частей зависят от типа хранилища и платформы. Например, минимальный размер части в AWS S3 — 5MiB. Терминология также различается: при поиске минимальных и максимальных значений используйте «part size» для AWS S3, «chunk size» для GCS и «block size» для Azure.

Если файл больше 1GiB (максимального размера, который PostgreSQL создаёт по умолчанию), размер части постепенно увеличивается вплоть до максимально допустимого, чтобы завершить загрузку файла.

```yaml
default (depending on repo-type):
    azure - 4MiB
    gcs - 4MiB
    s3 - 5MiB

allow range (depending on repo-type):
    azure - [4MiB, 1GiB]
    gcs - [4MiB, 1GiB]
    s3 - [5MiB, 1GiB]

example: --repo1-storage-upload-chunk-size=16MiB
```

### Параметр проверки сертификата хранилища репозитория (`--repo-storage-verify-tls`) {#repository-storage-certificate-verify-option---repo-storage-verify-tls}

Проверка сертификата хранилища репозитория.

Позволяет включать и отключать проверку TLS-сертификата сервера хранилища (например, S3 или Azure). Отключать проверку следует только при тестировании или в других случаях использования самоподписанного сертификата.

```yaml
default: y
example: --no-repo1-storage-verify-tls
```

Устаревшие имена: repo-azure-verify-tls, repo-s3-verify-ssl, repo-s3-verify-tls

### Параметр символических ссылок в репозитории (`--repo-symlink`) {#repository-symlink-option---repo-symlink}

Создание символических ссылок внутри репозитория.

Включает создание символических ссылок `latest` и ссылок табличных пространств. Эти ссылки наиболее полезны при использовании снимков для восстановления непосредственно в репозитории, что встречается редко.

Хотя подавляющему большинству пользователей эта возможность, вероятно, не нужна, она остаётся включённой по умолчанию ради совместимости. Однако для Posix-подобных хранилищ, не поддерживающих символические ссылки, может быть полезно отключить их.

```yaml
default: y
example: --no-repo1-symlink
```

### Параметр типа репозитория (`--repo-type`) {#repository-type-option---repo-type}

Тип хранилища репозитория.

Поддерживаются следующие типы репозиториев:

- `azure` - Azure Blob Storage Service
- `cifs` - Аналогичен `posix`, но отключает ссылки и fsync каталогов
- `gcs` - Google Cloud Storage
- `posix` - Файловые системы, совместимые с Posix
- `s3` - AWS Simple Storage Service
- `sftp` - Secure File Transfer Protocol

При использовании смонтированной NFS в качестве репозитория `posix` к pgBackRest применяются те же правила, что описаны в документации PostgreSQL: [Создание кластера баз данных — файловые системы](https://www.postgresql.org/docs/current/creating-cluster.html#CREATING-CLUSTER-FILESYSTEM).

```yaml
default: posix
example: --repo1-type=cifs
```
