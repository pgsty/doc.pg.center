По умолчанию команда восстановления автоматически выбирает последнюю резервную копию из первого репозитория, где есть копии (см. [Быстрый старт — восстановление резервной копии](/ru/docs/pgbackrest/user-guide/#restore-a-backup)). Порядок проверки репозиториев задаётся в `pgbackrest.conf` (например, repo1 проверяется раньше repo2). Для выбора конкретного репозитория можно передать `--repo` (например, `--repo=1`). Если требуется не последняя копия, можно передать `--set`.

При PITR с `--type=time` или `--type=lsn` целевое время или LSN необходимо указать с помощью параметра `--target`. Если `--set` не задан, настроенные репозитории проверяются по порядку: выбирается резервная копия, время завершения которой предшествует целевому времени или LSN завершения которой меньше либо равен целевому LSN. Если подходящая копия не найдена, pgBackRest выдаёт ошибку как для `--type=time`, так и для `--type=lsn`; перехода к последней резервной копии не происходит. Для других типов PITR, например `xid`, необходимо указать параметр `--set`, если цель предшествует последней резервной копии. Подробнее и с примерами см. [Восстановление на заданный момент времени](/ru/docs/pgbackrest/user-guide/#point-in-time-recovery).

Слоты репликации не включаются согласно рекомендации PostgreSQL. Дополнительные сведения приведены в разделе [Резервное копирование каталога данных](https://www.postgresql.org/docs/current/continuous-archiving.html#BACKUP-LOWLEVEL-BASE-BACKUP-DATA) документации PostgreSQL.

## Параметры команды {#command-options}

### Параметр режима архивирования (`--archive-mode`) {#archive-mode-option---archive-mode}

Сохранение или отключение архивирования на восстановленном кластере.

Позволяет сохранить или отключить архивирование на восстановленном кластере. Это полезно, когда для выполнения определённой работы кластер необходимо повысить до первичного, но использовать его как новый первичный сервер не планируется. В таком случае отправлять WAL этого кластера в репозиторий нежелательно.

Поддерживаются следующие режимы:

- `off` - Отключает архивирование, задавая `archive_mode=off`.
- `preserve` - Сохраняет текущее значение `archive_mode`.

**ПРИМЕЧАНИЕ**: этот параметр недоступен в PostgreSQL < 12.

```yaml
default: preserve
example: --archive-mode=off
```

### Параметр исключения баз данных (`--db-exclude`) {#exclude-database-option---db-exclude}

Восстановление с исключением указанных баз данных.

Исключённые базы данных восстанавливаются в виде разреженных файлов, заполненных нулями: это экономит место, сохраняя возможность восстановления PostgreSQL. После восстановления эти базы будут недоступны, но их можно удалить командой `drop database`. Параметр `--db-exclude` можно передать несколько раз, чтобы исключить несколько баз данных.

В сочетании с параметром `--db-include` параметр `--db-exclude` применяется только к стандартным системным базам данных (`template0`, `template1` и `postgres`).

```yaml
example: --db-exclude=db_main
```

### Параметр включения баз данных (`--db-include`) {#include-database-option---db-include}

Восстановление только указанных баз данных.

Эта возможность позволяет восстановить только выбранные базы данных. Базы, не включённые явно, восстанавливаются в виде разреженных файлов, заполненных нулями: это экономит место, сохраняя возможность восстановления PostgreSQL. После восстановления базы, которые не были включены, будут недоступны, но их можно удалить командой `drop database`.

> **ПРИМЕЧАНИЕ:** встроенные базы данных (`template0`, `template1` и `postgres`) всегда восстанавливаются, если они не исключены явно.

Параметр `--db-include` можно передать несколько раз, чтобы включить несколько баз данных.

Дополнительные сведения и ограничения приведены в разделе [Восстановление выбранных баз данных](/ru/docs/pgbackrest/user-guide/#restore-selected-databases).

```yaml
example: --db-include=db_main
```

### Параметр принудительного выполнения (`--force`) {#force-option---force}

Принудительное восстановление.

Сам по себе этот параметр принудительно полностью перезаписывает каталоги данных и табличных пространств PostgreSQL. В сочетании с `--delta` выполняется дельта-восстановление по временным меткам и размерам вместо контрольных сумм.

```yaml
default: n
example: --force
```

### Параметр восстановления всех ссылок (`--link-all`) {#link-all-option---link-all}

Восстановление всех символических ссылок.

По умолчанию каталоги и файлы, на которые указывают символические ссылки, восстанавливаются как обычные каталоги и файлы в $PGDATA. Причина в том, что восстанавливать ссылки на исходные цели в другой системе, отличной от той, где выполнялось резервное копирование, может быть небезопасно. Этот параметр восстанавливает все символические ссылки в том виде, в каком они были в исходной системе при резервном копировании.

```yaml
default: n
example: --link-all
```

### Параметр переназначения ссылок (`--link-map`) {#link-map-option---link-map}

Изменение цели символической ссылки.

Позволяет при восстановлении изменить целевой файл или путь символической ссылки. Это полезно при восстановлении в системах, где организация хранилища отличается от исходной системы, в которой была создана резервная копия.

```yaml
example: --link-map=pg_xlog=/data/xlog
```

### Параметр настройки восстановления (`--recovery-option`) {#recovery-option---recovery-option}

Установка параметра в `postgresql.auto.conf` или `recovery.conf`.

Сведения о параметрах `postgresql.auto.conf` и `recovery.conf` приведены в разделе [Конфигурация сервера](https://www.postgresql.org/docs/current/runtime-config.html) (обязательно выберите свою версию PostgreSQL). Этот параметр можно указывать несколько раз.

Для PostgreSQL >= 12 параметры записываются в `postgresql.auto.conf`. Для всех остальных версий — в `recovery.conf`.

> **ПРИМЕЧАНИЕ:** параметр `restore_command` создаётся автоматически, но его можно переопределить этим параметром. Собственный `restore_command` следует задавать осторожно, поскольку pgBackRest рассчитан на автоматическое управление им. Параметры цели восстановления (recovery_target_name, recovery_target_time и т. п.) pgBackRest формирует автоматически, и их не следует задавать таким способом.

Поскольку после записи файла `postgresql.auto.conf` или `recovery.conf` pgBackRest не запускает PostgreSQL, перед ручным перезапуском всегда можно проверить или отредактировать `postgresql.auto.conf` или `recovery.conf`.

```yaml
example: --recovery-option=primary_conninfo=db.mydomain.com
```

### Параметр набора резервной копии (`--set`) {#set-option---set}

Набор резервной копии для восстановления.

Набор резервной копии, который требуется восстановить. Значение `latest` восстанавливает последнюю копию; иначе следует указать имя нужной копии.

```yaml
default: latest
example: --set=20150131-153358F_20150131-153401I
```

### Параметр переназначения табличного пространства (`--tablespace-map`) {#tablespace-map-option---tablespace-map}

Восстановление табличного пространства в указанный каталог.

Перемещает табличное пространство в новое расположение при восстановлении. Это полезно, когда расположения табличных пространств на реплике отличаются или после обновления системы изменились точки монтирования.

Расположения табличных пространств не хранятся в pg_tablespace, поэтому их можно свободно перемещать. Однако переносить табличное пространство в `data_directory` не рекомендуется: это может вызвать проблемы. Дополнительные сведения о перемещении табличных пространств приведены на http://www.databasesoup.com/2013/11/moving-tablespaces.html.

```yaml
example: --tablespace-map=ts_01=/db/ts_01
```

### Параметр переназначения всех табличных пространств (`--tablespace-map-all`) {#map-all-tablespaces-option---tablespace-map-all}

Восстановление всех табличных пространств в указанный каталог.

По умолчанию табличные пространства восстанавливаются в исходные расположения. Для каждого пространства это можно изменить параметром `tablespace-map`, но иногда удобнее сразу переназначить все пространства в новый каталог. Это особенно полезно в системах разработки или предварительного тестирования, где организация хранилища может отличаться от исходной системы, в которой была создана резервная копия.

Указанный путь будет родительским каталогом, в котором создаются все табличные пространства из резервной копии.

ОСТОРОЖНО:

Табличные пространства, созданные после начала резервного копирования, не переназначаются. Если требуется переназначение, после создания табличного пространства следует сделать новую резервную копию.

```yaml
example: --tablespace-map-all=/data/tablespace
```

### Параметр цели (`--target`) {#target-option---target}

Цель восстановления.

Определяет цель восстановления при `--type`, равном `lsn`, `name`, `xid` или `time`. Если цель предшествует последней копии и `--type` не равен `time` или `lsn`, укажите набор резервной копии параметром `--set`.

```yaml
example: --target=2015-01-30 14:15:11 EST
```

### Параметр действия при достижении цели (`--target-action`) {#target-action-option---target-action}

Действие при достижении цели восстановления.

При `hot_standby=on` (значение по умолчанию начиная с PostgreSQL 10) этот параметр одинаково управляет поведением кластера при достижении цели или исчерпании WAL в архиве.

При `hot_standby=off` в PostgreSQL >= 12 значение `pause` действует как `shutdown`. При `hot_standby=off` в PostgreSQL < 12 значение `pause` действует как `promote`.

Поддерживаются следующие действия:

- `pause` - Приостановка при достижении цели восстановления.
- `promote` - Повышение до первичного сервера и смена временной шкалы при достижении цели восстановления.
- `shutdown` - Остановка сервера при достижении цели восстановления. (PostgreSQL >= 9.5)

```yaml
default: pause
example: --target-action=promote
```

### Параметр исключения цели (`--target-exclusive`) {#target-exclusive-option---target-exclusive}

Остановка непосредственно перед достижением цели восстановления.

Определяет, исключается ли сама цель из восстановления (по умолчанию включается), и допустим только при `--type`, равном `lsn`, `time` или `xid`. Например, при `--type=xid` и `--target=1007` параметр `--target-exclusive` исключит содержимое транзакции `1007`. Дополнительные сведения приведены в описании `recovery_target_inclusive` в документации PostgreSQL.

```yaml
default: n
example: --no-target-exclusive
```

### Параметр целевой временной шкалы (`--target-timeline`) {#target-timeline-option---target-timeline}

Восстановление по временной шкале.

Дополнительные сведения приведены в описании `recovery_target_timeline` в документации PostgreSQL.

```yaml
example: --target-timeline=3
```

### Параметр типа (`--type`) {#type-option---type}

Тип восстановления.

Поддерживаются следующие типы восстановления:

- `default` - Восстановление до конца потока архива.
- `immediate` - Восстановление только до достижения согласованного состояния базы данных.
- `lsn` - Восстановление до LSN (номера позиции в журнале), заданного в `--target`. Поддерживается только в PostgreSQL >= 10.
- `name` - Восстановление до точки восстановления, заданной в `--target`.
- `xid` - Восстановление до идентификатора транзакции, заданного в `--target`.
- `time` - Восстановление до времени, заданного в `--target`.
- `preserve` - Сохранение существующего файла `postgresql.auto.conf` или `recovery.conf`.
- `standby` - Добавление `standby_mode=on` в файл `postgresql.auto.conf` или `recovery.conf`, чтобы кластер запустился в режиме резервного сервера.
- `none` - Файл `postgresql.auto.conf` или `recovery.conf` не записывается, поэтому PostgreSQL попытается достичь согласованности с помощью сегментов WAL в `pg_xlog`/`pg_wal`. Предоставьте необходимые сегменты WAL или используйте настройку `archive-copy`, чтобы включить их в резервную копию.

ПРЕДУПРЕЖДЕНИЕ:

Следует избегать восстановления с `type=none`, поскольку по его завершении временная шкала не увеличивается. Это может привести, например, к попытке PostgreSQL архивировать дублирующийся WAL, которая будет отклонена; в результате диск может заполниться, а PostgreSQL — аварийно завершиться с panic. Кроме того, такие средства, как `pg_rewind`, могут работать некорректно или вызывать повреждение данных.

Для копий остановленного кластера значение `type` восстановления по умолчанию — `none`, поскольку при `wal_level=minimal` восстановление на заданный момент времени невозможно. Если `type` задан явно, он применяется, так как восстановление на заданный момент времени из копии остановленного кластера возможно при `wal_level > minimal`.

```yaml
default: default
example: --type=xid
```

## Общие параметры {#general-options}

### Параметр разрешения запуска от root (`--allow-root`) {#allow-run-as-root-option---allow-root}

Разрешение запуска команды от пользователя root.

По умолчанию только команда `restore` может выполняться от пользователя root, поскольку она предназначена для тщательного управления принадлежностью файлов. Выполнение других команд от пользователя root может привести к созданию файлов (например, в репозитории), принадлежащих root, и, как следствие, недоступных для пользователя PostgreSQL, что вызовет сбой последующих команд.

Включите этот параметр, чтобы запустить команду от имени root. Однако гораздо лучше запускать pgBackRest от пользователя, владеющего репозиторием и кластером PostgreSQL.

```yaml
default: y
example: --allow-root
```

### Параметр размера буфера (`--buffer-size`) {#buffer-size-option---buffer-size}

Размер буфера для операций ввода-вывода.

Размер буфера, используемый для копирования, сжатия, шифрования и других операций. Количество используемых буферов зависит от параметров, и каждая операция может использовать дополнительную память, например, сжатие `gz` может потребовать дополнительно 256KiB памяти.

Допустимые значения: `16KiB`, `32KiB`, `64KiB`, `128KiB`, `256KiB`, `512KiB`, `1MiB`, `2MiB`, `4MiB`, `8MiB` и `16MiB`.

```yaml
default: 1MiB
example: --buffer-size=2MiB
```

### Параметр команды pgBackRest (`--cmd`) {#pgbackrest-command-option---cmd}

Команда pgBackRest.

pgBackRest может формировать командную строку, например когда команда `restore` создаёт настройку restore_command. В этом случае используется команда, которой был запущен процесс pgBackRest, если не задан параметр `cmd`.

ОСТОРОЖНО:

Использование обёртки для команды pgBackRest может привести к непредсказуемому поведению и не рекомендуется.

```yaml
default: [path of executed pgbackrest binary]
example: --cmd=/var/lib/pgsql/bin/pgbackrest_wrapper.sh
```

### Параметр команды SSH-клиента (`--cmd-ssh`) {#ssh-client-command-option---cmd-ssh}

Команда SSH-клиента.

Позволяет задать конкретную команду SSH-клиента, если нужен другой клиент или команда `ssh` отсутствует в $PATH.

```yaml
default: ssh
example: --cmd-ssh=/usr/bin/ssh
```

### Параметр уровня сжатия для сети (`--compress-level-network`) {#network-compress-level-option---compress-level-network}

Уровень сжатия для передачи по сети.

Задаёт уровень сетевого сжатия, когда `compress-type=none` и команда выполняется на другом сервере, чем репозиторий. Сжатие уменьшает сетевой трафик. Когда `compress-type` не равен `none`, настройка `compress-level-network` игнорируется и вместо неё используется `compress-level`, чтобы файл сжимался только один раз.

```yaml
default: 1
allowed: [-5, 12]
example: --compress-level-network=1
```

### Параметр файла конфигурации (`--config`) {#config-option---config}

Конфигурационный файл pgBackRest.

Используйте этот параметр для указания другого файла конфигурации, отличного от файла по умолчанию.

```yaml
default: CFGOPTDEF_CONFIG_PATH "/" PROJECT_CONFIG_FILE
example: --config=/conf/pgbackrest/pgbackrest.conf
```

### Параметр каталога включаемых конфигураций (`--config-include-path`) {#config-include-path-option---config-include-path}

Путь к дополнительным файлам конфигурации pgBackRest.

Файлы конфигурации с расширением `.conf`, находящиеся в указанном каталоге, объединяются с файлом конфигурации pgBackRest в единый файл конфигурации.

```yaml
default: CFGOPTDEF_CONFIG_PATH "/" PROJECT_CONFIG_INCLUDE_PATH
example: --config-include-path=/conf/pgbackrest/conf.d
```

### Параметр каталога конфигурации (`--config-path`) {#config-path-option---config-path}

Базовый путь файлов конфигурации pgBackRest.

Эта настройка переопределяет базовый каталог по умолчанию для параметров `--config` и `--config-include-path`, если они не заданы явно в командной строке.

Например, передача только `--config-path=/conf/pgbackrest` приводит к установке значения по умолчанию для `--config` в `/conf/pgbackrest/pgbackrest.conf` и значения по умолчанию для `--config-include-path` в `/conf/pgbackrest/conf.d`.

```yaml
default: CFGOPTDEF_CONFIG_PATH
example: --config-path=/conf/pgbackrest
```

### Параметр дельта-восстановления и копирования (`--delta`) {#delta-option---delta}

Восстановление или резервное копирование с использованием контрольных сумм.

При восстановлении по умолчанию предполагается, что каталоги данных и табличных пространств PostgreSQL существуют, но пусты. Этот параметр выполняет дельта-восстановление с использованием контрольных сумм.

При резервном копировании этот параметр использует контрольные суммы вместо временных меток, чтобы определить, нужно ли копировать файлы.

```yaml
default: n
example: --delta
```

### Параметр тайм-аута ввода-вывода (`--io-timeout`) {#io-timeout-option---io-timeout}

Тайм-аут ввода-вывода.

Тайм-аут, в секундах, используемый для соединений и операций чтения/записи.

Операция чтения или записи не обязана полностью завершиться за это время, но *какое-то* продвижение должно произойти, хотя бы на один байт.

```yaml
default: 1m
allowed: [100ms, 1h]
```

Тайм-аут протокола.

### Параметр stanza (`--stanza`) {#stanza-option---stanza}

Определение stanza.

Stanza — конфигурация кластера баз данных PostgreSQL, которая определяет его расположение, способ резервного копирования, параметры архивирования и т. п. Большинство серверов баз данных содержат только один кластер PostgreSQL и, соответственно, одну stanza, тогда как на серверах резервного копирования есть stanza для каждого кластера, требующего резервного копирования.

Может возникнуть желание назвать stanza по имени первичного кластера, но лучше выбрать имя, описывающее базы данных в нём. Поскольку имя stanza используется для первичного сервера и всех реплик, уместнее выбрать имя, отражающее назначение кластера, например app или dw, а не локальное имя кластера, такое как main или prod.

```yaml

```

## Параметры для сопровождающих {#maintainer-options}

### Параметр принудительного задания версии PostgreSQL (`--pg-version-force`) {#force-postgresql-version-option---pg-version-force}

Принудительное задание версии PostgreSQL.

Указанная версия PostgreSQL будет использоваться вместо версии, автоматически определённой по `pg_control` или заголовкам WAL. Это полезно главным образом для форков PostgreSQL или версий в разработке, в которых эти значения отличаются от версии выпуска. Версия, которую PostgreSQL сообщает через `server_version_num`, должна совпадать с принудительно заданной.

ПРЕДУПРЕЖДЕНИЕ:

Используйте этот параметр осторожно: `pg_control` и заголовки WAL всё равно будут читаться в формате, ожидаемом для указанной версии, то есть в формате официальной версии PostgreSQL с открытым исходным кодом. Если форк или версия в разработке меняет формат полей, от которых зависит pgBackRest, это приведёт к неожиданному поведению. В общем случае параметр будет работать как ожидается только тогда, когда форк добавляет все собственные поля структур *после* стандартных полей PostgreSQL.

```yaml
example: --pg-version-force=15
```

Способ формирования отпечатка сервера репозитория SFTP следует выбирать в соответствии с `repo-sftp-host-key-hash-type`. Отпечаток можно получить командой `awk '{print $2}' ssh_host_xxx_key.pub | base64 -d | (md5sum or sha1sum) -b`. Ключи сервера ssh обычно находятся в каталоге `/etc/ssh`.

### Параметр типа проверки ключа сервера SFTP (`--repo-sftp-host-key-check-type`) {#sftp-host-key-check-type-option---repo-sftp-host-key-check-type}

Тип проверки ключа сервера SFTP.

Поддерживаются следующие типы проверки ключа сервера SFTP:

- `strict` - pgBackRest никогда не добавляет ключи серверов в файл ~/.ssh/known_hosts автоматически и отказывается соединяться с серверами, ключ которых изменился или отсутствует в файлах известных серверов. При этом пользователь должен вручную добавлять все новые серверы.
- `accept-new` - pgBackRest автоматически добавляет новые ключи серверов в пользовательский файл известных серверов, но не разрешает соединения с серверами, ключи которых изменились.
- `fingerprint` - pgBackRest сравнивает ключ сервера с отпечатком, заданным параметром `repo-sftp-host-fingerprint`.
- `none` - Ключ сервера не проверяется.

```yaml
default: strict
example: --repo1-sftp-host-key-check-type=accept-new
```

### Параметр размера части загрузки в хранилище репозитория (`--repo-storage-upload-chunk-size`) {#repository-storage-upload-chunk-size-option---repo-storage-upload-chunk-size}

Размер части загрузки в хранилище репозитория.

Объектные хранилища, такие как S3, позволяют загружать файлы частями, если файл слишком велик для размещения в памяти. Даже если он помещается в память, ограничение объёма памяти для загрузок позволяет использовать её экономнее.

Больший размер части обычно повышает производительность, поскольку уменьшает число запросов загрузки и позволяет загружать больше файлов одним запросом, а не частями. Недостаток — повышенное потребление памяти. Поскольку буфер части выделяется каждому процессу, большие значения `process-max` увеличивают общий расход памяти.

Допустимые размеры частей зависят от типа хранилища и платформы. Например, минимальный размер части в AWS S3 — 5MiB. Терминология также различается: при поиске минимальных и максимальных значений используйте «part size» для AWS S3, «chunk size» для GCS и «block size» для Azure.

Если файл больше 1GiB (максимального размера, который PostgreSQL создаёт по умолчанию), размер части постепенно увеличивается вплоть до максимально допустимого, чтобы завершить загрузку файла.

```yaml
default (depending on repo-type):
    azure - 4MiB
    gcs - 4MiB
    s3 - 5MiB

allow range (depending on repo-type):
    azure - [4MiB, 1GiB]
    gcs - [4MiB, 1GiB]
    s3 - [5MiB, 1GiB]

example: --repo1-storage-upload-chunk-size=16MiB
```

### Параметр проверки сертификата хранилища репозитория (`--repo-storage-verify-tls`) {#repository-storage-certificate-verify-option---repo-storage-verify-tls}

Проверка сертификата хранилища репозитория.

Позволяет включать и отключать проверку TLS-сертификата сервера хранилища (например, S3 или Azure). Отключать проверку следует только при тестировании или в других случаях использования самоподписанного сертификата.

```yaml
default: y
example: --no-repo1-storage-verify-tls
```

Устаревшие имена: repo-azure-verify-tls, repo-s3-verify-ssl, repo-s3-verify-tls

### Параметр целевого времени репозитория (`--repo-target-time`) {#target-time-for-repository-option---repo-target-time}

Целевое время репозитория.

Целевое время определяет момент, на который команды читают репозиторий в хранилище с версионированием. Это позволяет прочитать состояние репозитория на определённый момент времени и восстановить данные, удалённые или повреждённые по ошибке пользователя либо вредоносным ПО.

S3, GCS и Azure поддерживают версионирование, но обычно оно отключено по умолчанию. Помимо включения версионирования, может быть полезно включить блокировку объектов в S3 и обратимое удаление в GCS или Azure.

Если указан параметр `repo-target-time`, необходимо также указать `repo`. Версионирование, вероятно, поддерживается не всеми типами репозиториев, и в целом при восстановлении разумно обращаться к одному конкретному репозиторию.

Временные метки хранилища сравниваются с указанной по условию <=; миллисекунды, если они указаны, отбрасываются.

```yaml
example: --repo-target-time=2024-08-08 12:12:12+00
```

### Параметр типа репозитория (`--repo-type`) {#repository-type-option---repo-type}

Тип хранилища репозитория.

Поддерживаются следующие типы репозиториев:

- `azure` - Azure Blob Storage Service
- `cifs` - Аналогичен `posix`, но отключает ссылки и fsync каталогов
- `gcs` - Google Cloud Storage
- `posix` - Файловые системы, совместимые с Posix
- `s3` - AWS Simple Storage Service
- `sftp` - Secure File Transfer Protocol

При использовании смонтированной NFS в качестве репозитория `posix` к pgBackRest применяются те же правила, что описаны в документации PostgreSQL: [Создание кластера баз данных — файловые системы](https://www.postgresql.org/docs/current/creating-cluster.html#CREATING-CLUSTER-FILESYSTEM).

```yaml
default: posix
example: --repo1-type=cifs
```

## Параметры stanza {#stanza-options}

### Параметр пути PostgreSQL (`--pg-path`) {#postgresql-path-option---pg-path}

Каталог данных PostgreSQL.

Следует указать значение `data_directory`, сообщаемое PostgreSQL. Хотя его можно получить из разных источников, разумно задать его явно на случай, если эти источники будут недоступны при восстановлении или резервном копировании остановленного кластера.

При каждом резервном копировании работающего кластера параметр `pg-path` сверяется со значением, сообщаемым PostgreSQL, поэтому его следует всегда поддерживать актуальным.

```yaml
example: --pg1-path=/data/db
```

Устаревшее имя: db-path
